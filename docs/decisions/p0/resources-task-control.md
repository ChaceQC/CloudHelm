# P0.3 资源占账与 Task 控制决定入口

> 决定修订：p0-resources-r1；契约修订：p0-decisions-r1
> 记录日期：2026-10-14（Asia/Shanghai）
> 范围：P0.3-02a 的资源契约冻结。本文不建立持久账本、执行器或 P1 服务，不表示资源、部署或人工验收通过。
> 权威依据：D03 v4.7.1 §4.2～4.4.2；身份/摘要继承 D02 v4.7.0 §1.4。未改变总体 v4.7 的边界或状态所有权。

本文负责资源；Task 的完成来源、唯一报告、人测真实结论、取消传播和晚到事实由 [Task 控制决定](task-control.md) 承接，并以 D01 §2.1～2.2、D02 §7/§11 为权威。Task 取消、完成、Run 结束或 DBOS 队列槽释放都不是资源释放证据。

## 1. 已有证据与本决定的支持边界

[D03 §4.2～4.4](../../design/03-workspace-build-resources.md#42-共享宿主资源池与计量) 是资源计量、准入、调整和释放的唯一规则来源。[Compose/Remote 接缝记录](../../acceptance/p0/compose-remote.md) 只有 WSL 隔离实验的有限进程、占用标记和回执证据，没有产品共享资源账本、整组硬配额或真实磁盘回收证据。

[实际拓扑记录](topology.md) 保留 r1 的 WSL 与 s2413 交付候选快照；当前用户已选择 s2413 同机 Hub/Runner/交付验证，2026-10-15 的 [新快照](../../acceptance/p0/topology-s2413-r2.md) 与 [受控方案](s2413-development-envelope.md) 分别维护实际事实和实施前置。角色与控制方案已明确，硬配额生效、产品身份网络、DNS/TLS 和容量支持仍须实际取证。瞬时可见内存、磁盘空闲或 Docker 版本不能作为已分配容量。本文的 4GiB、7GiB 固定例子都是契约输入；D03 的 4 核/8GiB、开发共享 4GiB、CPU 3000m 是设计初值，不能写成实测承诺。

首版选择一份共享池账本、整组静态配额、全部运行中原位调整明确拒绝、停止后重新分配。保留占用 K 和未知上界 U 均在账本侧计量；本修订不开放容量侧 D 转记，故公式中的 D=0。该选择属于 D03 允许的实现子集，不改变未知占用和连续计量要求。

## 2. 宿主身份、资源向量与硬限

`host_resource_pool_id` 标识真实共享宿主的一份资源池，`physical_host_id` 是基础设施负责人核实后由 Hub 登记的稳定宿主标识；`executor_instance_id` 单独标识 Runner 实例，并对应 D02 的 `executor_id`。注册表必须证明一份实际物理预算只有一个池归属；hostname、Runner 进程号、Docker daemon 或 WSL 发行版名字不能自行创建第二份宿主容量。无法证明独立资源或共享关系时，相关注册及准入保持关闭。

同宿主的多个 Runner 共享预算、未释放预留、保留字节、未知占用、冲突键和类别槽。独立 Runner 只有在物理容量、配额及边界分别核验后才另计；增加 Runner 不增加 DBOS worker、内存额度或重执行槽。首版每池重执行槽最多 1，普通预览与人测共享最多 1 个预览槽；配置为 0 可关闭该类准入，增加并发需后续测量和评审。

|字段|单位与首版约束|
|---|---|
|`memory_mib`|MiB 整数；申请量、初始占账和整组硬限相等。4GiB=4096MiB，不使用十进制 GB 混算|
|`cpu_millicores`|毫核；1000m=1 vCPU。由经核验的整组 quota/period 限制最大消耗；`cpu_period_us` 记录周期，shares/weight 不能替代硬限|
|`disk_bytes`|实际存储分配字节；包含下载、解包、镜像/共享层、缓存、工作文件、卷、日志及并存中间物的新增峰值|
|`pids`|组级 PID/task 整数；申请量、初始占账和硬限相等。Linux pids 计数含线程，具体语义由执行器证据绑定|
|`heavy_slots`、`preview_slots`|分别为重执行和共享预览类别整数槽；由实际准入门禁强制，而非 DBOS 队列槽的投影|
|`conflict_keys`|最多 64 个排序、去重的稳定键，独立判冲突，不相加；覆盖工作区写权、环境实例或受控端口等实际互斥对象|

向量所有字段均为 `0..2^53-1` 严格整数，拒绝布尔值、字符串及小数；固定默认 0 在摘要前物化。`request_vector` 表示需求，`accounted_vector` 表示准入承诺，`hard_limits` 表示可能仍生效的执行上限。初次申请和每个调整目标都必须满足逐维 `hard_limits <= accounted_vector`；调整未决的保守占账可以高于已确认上限。

`resource_group_id` 与不可变 `resource_group_digest` 绑定完整资源组说明。配额能力证据必须覆盖所有同时存活的服务、数据库、浏览器、构建器、容器和全部子进程，以及全部写入路径和受控镜像/构建后端；仅限制一个容器或定期观测目录大小不成立。子组上限合计不得超过父级占账，新增子进程必须留在同一已批准边界内。CPU quota 不承诺瞬时采样或控制请求时延，后者留待 P1/P2 实测。

## 3. Hub 原子整组准入与执行器边界

按 [D03 §4.3](../../design/03-workspace-build-resources.md#43-hub-原子准入与执行器确认)，创建与查询保持 `reservation_id`、`operation_id`、池、执行器、`hub_incarnation`、`resource_generation`、资源组和稳定冲突键。`ResourceRequest` 是应用层完成身份解析后的候选；Hub 受控分配 `reservation_id`，本模块不生成身份或公开提交 API。调用者、owner/scope、租约、权限和控制修订由外层应用命令及权威记录提供，不能从向量校验成功反推授权。

1. 当前访问与命令权限校验后，在调用者/业务范围内先查持久幂等身份和规范摘要。同身份同摘要返回原分配与原接受结果；不同摘要拒绝，不用修订冲突掩盖成功重投。初始 `request_digest` 永久保持原值。
2. Hub 短事务锁定共享池账本或比较其条件版本，同时检查授权、期限、当前推进资格、能力、冲突键和整组向量。所有 `reserved`、`active`、`releasing`、`orphaned` 的未释放维度均计入 A；同一池的其他 Runner 不能被遗漏。整组不能准入就整组不启动；子步骤消费父级份额，不重复申请重执行槽。
3. 事务内保存预留、领域事件、必要 Outbox 与 WorkflowBinding；若使用已核验的同库 DBOS 入队能力，也属于此 UnitOfWork。网络、等待、进程/容器创建均在事务提交之后。
4. 执行器使用宿主共享本地账本/锁，以原身份、摘要、incarnation、generation 和执行器身份去重，持久保存接受或拒绝事实。Hub 事务与本地事务分别原子，不宣称跨机器原子或 exactly-once。
5. 接受后、真正启动前再次检查当前授权、期限、推进资格、维护状态、物理容量、冲突与整组硬限，持久绑定 ProcessBinding 和已确认分配修订。启动被拒绝时，在同一启动锁内持久写入 `closed_unstarted` 并封闭所有晚到/重复消息；无法封闭则保持 unknown。
6. 回执丢失、拒绝或超时先查询原身份，不创建第二份分配。接受只证明可靠接收；单纯没看到进程、租约过期或任务终态均不能证明不会晚到启动。仅按第 5 节分维证据释放。

本修订采用下列计量；账本对每笔字节及未知占用保留唯一来源，已在实测基线排除的占用不得再次计入 U：

```text
A[d] = sum(全部未释放分配的 accounted_vector[d]) + K[d]
C[d] = min(配置预算[d], 排除系统/平台必要保留和池外占用后的实测总量[d])
A[d] + U[d] + 新整组占账[d] <= C[d]
```

实测总量不是已扣除池内预留的瞬时 free；不能再减一次完整预留。未归属占用有可信上界才可计 U，没有上界时首版关闭该池的新准入。硬限无法覆盖、实际超额或容量下降时限制新准入并安全收束，不提高预算掩盖偏差。`validate_admission` 只检查所给快照的向量、成员身份、冲突和重复计量条件；实际唯一宿主登记、锁、事务、证据真实性与新鲜度留给 P1 实现。

## 4. 独立调整身份、修订与未知结果

[D03 §4.3.1](../../design/03-workspace-build-resources.md#431-调整身份修订与生效顺序) 的语义保留；本契约采用以下显式字段映射，不修改历史远端 schema：

|本契约字段|D03 字段/含义|
|---|---|
|`ResourceAdjustment.resource_adjustment_id`|`adjustment_id`，独立调整身份；查询和重投保持原值|
|`ResourceAdjustment.request_digest`|`adjustment_digest`，本次调整的规范摘要；不能覆盖创建摘要|
|`ResourceAllocation.creation_request_digest`|初始不可变 `request_digest`，与原 `ResourceRequest.request_digest` 对应|
|`allocation_revision`、`expected_allocation_revision`|`reservation_revision`、`expected_reservation_revision`；首次已确认分配为 0|
|`target.accounted_vector`、`target.hard_limits`|完整 `target_accounted_vector`、`target_hard_limits`；内存/PID 目标占账等于拟施加硬限|

摘要使用 [身份与权限决定](identity-permissions-migrations.md) 的 D02 §1.4 版本化 UTF-8/JCS 信封，覆盖调用者/scope、命令类型、原分配与执行器身份、预期修订及完整目标。创建摘要另覆盖资源组、目标池、需求/占账/硬限、CPU 周期及稳定冲突键；不从未经规范化的部分字段自行哈希。秘密只保留引用和版本。

两端必须在当前权限检查之后先查询原调整身份，再检查新命令的预期修订：同身份同摘要返回原拒绝/成功结果或待核对进度；异摘要拒绝。新身份的旧修订返回冲突；同一分配已有 pending/unknown 调整时拒绝第二份调整。无变化目标登记可重投的无变化结果，不推进修订。`validate_new_adjustment` 仅用于完成持久去重后的新请求，不实现或替代该去重过程。

首版未取得任何资源维度/方向的真实运行中调整证据，**所有改变现有占账或执行硬限的原位请求明确拒绝**，不先改 Hub 数字，也不假装调整成功。停止后按第 5 节核对，保留仍存磁盘字节，再以新的 `reservation_id` 申请；旧 operation、池、执行器、incarnation、generation、资源组及冲突边界不能借一次调整替换。未知旧执行或未决调整不能用新身份绕开。

拒绝首版入口不省略未决语义。`PendingAdjustmentAccounting` 冻结以下规则，供纯逻辑检查与后续能力实现；它本身不产生已接受的调整：

```text
B_hold[d] = max(B_old[d], B_target[d])
本次需新准入的增量[d] = B_hold[d] - B_old[d]
```

扩额先在 Hub 短事务持久占账，再由执行器核实并提高上限；一维缩小不能抵扣另一维扩额。缩额先取得覆盖整组、全部子进程、后续入口及必要实际用量的持久生效证据，再减少占账；用量暂低于目标不代表硬限降低。磁盘目标不得低于仍归本分配的实际字节和后续并存峰值，停止尚未确认时不得缩额。

部分生效、回执丢失、两端修订不一致均保持 pending/unknown、逐维 B_hold 和原已确认修订。新准入快照必须同时包含被引用的未决调整，其身份、修订和占账须与分配吻合，不能只传扩额前的较小余额。全部目标安全生效后才记录 `expected_allocation_revision + 1`，原身份重复回执不得重复减账或推进修订。只查询原调整；只有证明从未生效且晚到路径封闭，或证明安全回到旧上限并封闭调整，才恢复旧占账。否则继续保守占用，仅允许核对及有权安全停止。真实方向能力开放前须增加执行证据并重新评审，不能由本次数学通过自动开放。

## 5. 分维释放与连续磁盘保留

按 [D03 §4.4.1](../../design/03-workspace-build-resources.md#441-分维释放与磁盘保留)，释放输入绑定完整 `AllocationIdentity` 和已确认修订。`closure_evidence_ref` 必须指向同一启动锁/账本下的完整组停止或 `closed_unstarted` 事实，并证明全部子进程与晚到启动路径已封闭；`closure` 字段本身不构成证明。未知停止或缺少该证据继续保留全部占账。

确认闭合后，可归还 CPU、内存、PID 和运行槽；互斥键还需证明对应写入者/服务终止，并另查保留对象是否具有独立冲突，不能单凭向量为零释放写权。历史硬限保留在不可变执行记录中，闭合后的有效执行硬限归零。

磁盘单独取受控后端实际分配字节与引用关系证据。已停止且证明不能再写后，未消费承诺可以归还；仍有 7GiB 镜像、缓存或中间物就仍计 7GiB。GC 已请求、删除 API accepted、容器退出、卷名消失均不能减少这笔字节，开放文件、共享层和延迟回收必须核对。真实实际字节超出原承诺时先进入偏差核对及限制准入，本纯投影拒绝把它当作正常释放。

需关闭原分配时，本修订只允许将全部剩余字节转为一笔有界 ledger 保留记录；`retained_object_id` 指向这一整组的不可变字节归属清单。`DiskRetentionTransfer` 保存 `transfer_id`、规范摘要、完整来源身份及修订、保留对象、池、字节数、保留上限、UTC 观测时间和转记证据；同身份异摘要拒绝，同身份重投查询原记录。

每端在共享池同一账本事务中先建立 K 的唯一归属，同时减少原分配，不存在先释放后补记的窗口；同一端不能同时把原余额和 K 计两次。跨端回执丢失时 Hub 保留原占账，查询原 transfer，未核对前不先释放。首版不接受部分转记或容量侧模式。保留上限只限制存储占用，不授予新增写入权；新增字节、复制、写时复制和额外元数据必须重新准入。共享物理层只登记一次，多个逻辑引用不能复制这份字节。

`project_release` 只投影调用方已核实的事实，返回剩余分配、有效硬限与已转记字节；它不会停止进程、删除文件、写事务或真的转记。原调整仍未决时先保留完整占账，安全停止后继续用原调整身份核对闭合，再进行释放投影；不能用停止字段抹掉未决调整。`validate_admission` 会继续把输入保留记录计入池中，并拒绝同一整笔来源的重复计量。保留字节只有在真实回收并核对剩余引用后才减账；期限到达不自动释放。

## 6. 契约产物、必要检查与未决门禁

实现位于 [resource_contracts.py](../../../packages/contracts/p0/resource_contracts.py)，复用 `decision_common.py` 的不可变 `Contract`、有界身份、摘要和修订类型。`P0ResourceContracts` 提供聚合 schema 入口。所有嵌套向量/记录不可变，序列有界；所接收的外层账本快照由调用方掌握。它不是完整业务 ResourceReservation 存储模型，owner/租约/授权、原请求保存、运行事实及证据读取由后续权威模块实现。

[check_decision_resources.py](../../../scripts/p0/check_decision_resources.py) 导出 `run_checks() -> dict[str, bool]`，失败抛异常。固定例子覆盖：4GiB 正常向量及 5GiB 硬限拒绝、实测总量封顶、多 Runner 四种未释放状态共同计量、未知上界拒绝、未知调整逐维取大/不推进修订、首版调整拒绝，以及停止后 7GiB 留账/转记仍阻止再分配。例子全部使用合成引用及摘要形状，不是独立验收资产或真实宿主证据。

```powershell
wsl.exe -d Ubuntu-24.04 --cd /mnt/e/Project/CloudHelm -- /home/cloudhelm/.local/bin/uv run --locked --offline python scripts/p0/check_decision_resources.py
```

实际运行结果由 [PROJECT_PROGRESS.md](../../../PROJECT_PROGRESS.md) 和统一出口证据记录；类型/数学检查不代表并发原子性、持久幂等、内核配额、完整进程停止、真实磁盘回收或 P1 资源验收。旧 `remote-plan.schema.json`、远端探针和历史 InputSet 保持原字节。

|未决输入/能力|责任角色|关闭的入口与复核点|
|---|---|---|
|实际 Hub/Runner 角色、宿主唯一映射、容量基线及必要系统保留|基础设施、资源负责人；项目负责人确认角色|对应池注册和真实准入保持关闭；P1.3 前按拓扑及双方注册事实核验，同机 light/独立 Runner 分列|
|全组 CPU 周期/quota、内存/PID、全部磁盘写入路径、受控目录/配额与后端证据|执行器、构建、存储负责人|所需维度不能施加硬限就拒绝分配；P1.3 取得真实 4GiB/5GiB、共享 Runner 和 7GiB 残留证据|
|Hub 事务、本地共享账本/启动锁、持久去重、晚到封闭、未知上界及转记一致性|资源、执行器、数据库负责人|不把纯校验接成真实准入/释放许可；P1.3 验证基本路径，P4 扩展重启、损坏、接管与代次恢复|
