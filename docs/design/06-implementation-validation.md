## 1. 实施原则

保留完整多 Agent 开发、远程交付与持续运维目标。先验证组件接缝和最小执行闭环，尽早接入真实 Agent 与两个开发会话，再扩大可靠性、运维和产品能力。沿用 v4.4 的 P0～P6 划分并增加本版要求；v4.3 旧编号不兼容，既有验收须逐项核对，不因版本变化自动标记完成。本版全部阶段仍为设计待实施；新增规格、估算和退出条件不表示相关实现或验收已经发生。

选定 PydanticAI 协议运行时、DBOS 唯一持久执行底座、模块化单体、完整远端执行计划、Compose 支持子集与薄扩展。应用命令统一事务，长任务提交与等待分开，Release 与环境配置分层。普通部署在线取许可，本机应急采用预先配置的人类授权与持久维护门禁。初期 FastAPI/DBOSClient、单 DBOS worker 与 PostgreSQL 同库不同 schema；两档 Runner 沿用相同基础执行协议，默认无 Conductor。

基础 Desktop 随阶段交付。当前授权、幂等、秘密保护、执行隔离、未知结果门禁和基本取消随 P1 建立；P4 扩大故障覆盖和恢复自动化，不把安全前提延期补做。P0 固定核心不变量和首条链路接口，其余 API/schema 随对应领域冻结。

每阶段交付实际实现、版本化契约、使用说明和验收记录。只验证该阶段的关键风险和实际改动，已通过场景不为普通文档改动重复运行。设计更新不表示实现或验收已经完成。

## 2. P0 架构接缝

交付三组可运行的接缝验证及其决策记录，证据收束为第 2.2 节的六张验证卡；锁定 PydanticAI、DBOS、SQLAlchemy/驱动、PostgreSQL、Compose 的具体版本和兼容矩阵。当前三组接缝和六张卡均为待实施、待验证，不因本次规格补齐而获得通过结论。

|接缝|交付与验证|必须明确的边界|
|---|---|---|
|Runtime 与 Gateway|模型准入、长任务提交回执、按需等待、历史保存、批次和续接|accepted 不等于执行完成；不依赖未核验的部分结果；原 tool-call 结果不覆盖|
|DBOS 与业务状态|UnitOfWork 跨模块事务入队、身份/摘要、有界工作流、可靠续接及优先级能力|任一参与写入失败整体回滚；原 Run 重放与新 Run 续接分开；物理并发不随队列增加|
|Hub 与 Remote Agent|完整计划、在线许可、账本、失联与重复投递；应急身份/门禁/交还契约|普通与本机授权来源明确；维护门禁先于启动且重启保留；P4 前不声称应急已可用|

同时冻结 Runtime 输入/TurnResult、提交/等待工具契约、Task/Session/Run/Workflow/Operation 映射、工程引用核心语义、PlanStep/许可、应急身份与维护门禁、Compose 两阶段解析、Release/EnvironmentConfigRevision 边界及首条链路错误/权限语义。核验应急本机身份映射、认证、作用域、期限和独立撤销流程；先交付隔离开发启动与最小诊断入口。

核验 PydanticAI 官方 DBOS 接入对实际请求拦截、SDK 自动重试、流式回调、历史续接及序列化的影响。完整历史和实际秘密不能因默认 SDK 行为进入不受控检查点；记录可直接复用、需要薄适配和不支持的能力。不得以文档中的示例 API 代替真实接缝结论。

### 2.1 首条交付链路实施规格

以一个包含前端、后端、数据库、迁移和健康检查的项目作为端到端参照。首批参照组合选定 React、FastAPI、PostgreSQL 和线性 Alembic 修订链；实际参照样例、初始 commit、依赖与 SDK 版本及支持证据由 P0 核验并锁定。此处选定组合不表示样例、具体版本或支持验收记录已经存在。P0 同时记录需求修订、独立验收资产及其修订和选择依据；没有可核验证据的项目仍记为未决，不编造提交或版本号。

参照拓扑固定为 Linux x86_64 Hub、Linux x86_64 开发 Runner 和独立 Linux x86_64 交付机器；同机 light 与独立 Runner 的数据分别记录。P0 选择并记录实际 OS 发行版与内核、CPU/内存/Swap、磁盘和存储路径、工作区/缓存/制品配额、网络和身份连接方式。P0/P1 同时形成支持矩阵：受支持的 Compose 字段及拒绝行为、构建器和构建输入、数据库迁移模式、预览域名与证书模式、浏览器与 Desktop/Tauri/WebView 组合。矩阵逐项注明已决定的范围、验证证据和不支持时的用户可见错误；未核验的值保持未决。

每个检查点固定输入、完成判定和失败后的对象保留、重试授权。完整流程按下表记录：

|检查点|固定输入|完成判定|失败保留与重试授权|
|---|---|---|---|
|Task 启动|需求与验收修订、发起者与当前授权、预算、目标项目及请求的资源范围|任务级授权、需求/验收修订与预算检查通过后，可靠建立 WorkItem 和初始推进请求；此处不等待模型额度或整组物理资源。模型与物理资源在各自执行启动前分别重新准入，容量不足的步骤排队|保留命令回执、拒绝原因及已分配身份；同一请求按原幂等身份查询或重投，改变输入须由有权发起者提交新修订，资源容量不足时保留任务并排队|
|长工具提交|Operation 身份、规范化请求摘要、提交者及其授权范围、步骤/依赖语义|可靠接受回执已持久化；accepted 只证明请求已可靠接收，不证明物理资源已预留、远端步骤已启动或执行结果已产生。实际远端新步骤须在启动副作用前按 D04 取得当前许可并分别通过资源准入，结果另行查询|保留原 Operation、Attempt、提交授权与回执；同义重试查询/关联原操作，摘要变化不得复用原身份，未知副作用须先核对，远端新步骤按 D04 当前许可准入|
|固定候选|最终集成 commit、构建输入和依赖锁、正式验收资产修订、候选及制品身份|输入集与候选不可变；后续开发不能改变本轮验证输入|保留候选、已生成制品和失败记录；重做固定输入须由有权项目角色发起，新代码或验收修订产生新候选|
|候选验证|候选与 InputSet、方法/正式验收资产版本、制品摘要、执行环境及必需检查|所有必需项均完成且通过，证据对该候选当前适用|保留每次验证输入、日志摘要和结果；同输入重试按规则登记新验证轮次，改变代码、资产或环境时创建新输入集，不得沿用旧通过结论|
|可选人工测试|是否启用、候选与测试范围、指定测试者、环境实例及访问授权|关闭时不创建等待或通过记录；开启时分别记录通过、返工、明确跳过或未完成，只有有权人类可提交结论|保留测试轮次、已提交反馈和环境故障；环境重建须经授权并产生新实例，超时/失联/故障不得自动通过，修复候选后旧页面不得确认新候选|
|Task 完成|当前主体与幂等身份/摘要、Task 业务版本和控制修订、输入有效性版本、需求/验收修订、最终集成版本及必需证据、人测门槛/策略及真实结论、范围内写 Operation 的收尾事实|按 D01 2.1 与 D02 7.2、11 的当前门禁，在同一短事务内形成唯一完成报告并关闭普通推进资格；必需输入与证据有效，可能改变交付或完成依据的写操作已结束、已停止或可靠封闭为未启动。解除等待本身不是通过证据|不满足时保留原状态并返回阻塞对象；已完成回执丢失按原身份查询/重投，新键命中 completed 返回原报告，不另验收或生成第二份报告。未知写入先核对，完成与失效/唤醒竞争按同一版本门禁处理；独立归属对象按自身权限继续|
|形成 Release|完整制品集合、运行契约、迁移修订及适用证据、发布策略|必需制品与证据齐全并满足发布策略后形成不可变 Release|保留候选、拒绝原因与未完成检查；修订输入形成新候选/Release 轮次，继续发布须由发布策略授权|
|执行 Deployment|Release 身份、已批准计划摘要、环境配置修订、目标起始基线、批准者与授权范围|实际目标事实和后置条件证明结果；仅在批准仍适用且新步骤取得当前有效许可时启动|保留原 Plan、Operation、许可、目标账本和实际状态；失败或未知先查询/核对原操作。若输入、Release/环境配置摘要和起始前提未变且原批准仍有效，沿原计划续行，并为每个新步骤检查当前许可；若计划摘要、配置、起始前提或批准变化，先重新解析计划并由有权者重新批准。核对前不盲目创建新操作或重放可能已执行的步骤|
|关闭 Incident|持续业务恢复窗口、观测覆盖、通知/确认、相关修复 Task 与操作记录|按业务持续恢复规则满足关闭条件；通知送达本身不作为人工确认或恢复证据|保留 Incident、观测缺口、处置与未完成 runbook；只有有权事件处置者可继续或关闭，证据不足时保持打开|

Task completed 只表示开发与验收条件完成。Release、Deployment 和 Incident 继续按各自业务对象的生命周期决定，不由 Task 状态代替；关联记录应能串起输入、候选和证据，同时保留每个对象独立的结论，参照 D01 2.1～2.2。

### 2.2 六张 SDK 接缝验证卡

三组接缝继续表示集成关系，以下六张卡是有限的取证单元，不另建一套平台工作流。每张卡独立记录：卡 ID 与状态、实际组件/SDK/驱动/系统 schema/运行环境版本、固定输入及故障注入位置、预期与实际观测、可复现操作和脱敏证据引用、直接复用/受支持薄适配/不支持的逐能力结论，以及失败阻塞入口、解决责任人和复核期限。复用结论必须基于所记录版本的实际行为；空白、未执行和无法观测均不能填写为通过。

|卡 ID 与范围|固定输入与最低观测证据|权威规则与失败阻塞入口|
|---|---|---|
|SDK-01 事务交接|固定一个跨模块命令及身份/摘要，分别在领域写入、事件、WorkflowBinding 和入队处失败，观察所有参与写入整体回滚；成功提交后丢回执重投仍关联原身份且业务版本只推进一次|D01 1.1；D02 1.1、1.4。阻塞依赖同事务交接的应用命令与工作流入口|
|SDK-02 真实模型请求|固定模型输入和预算，逐次观察正常请求、校验修复、SDK 自动重试、压缩及恢复后新请求的实际出站边界；每次出站前均有当前门禁和费用准入，未知费用可定位原 ModelRequestRecord|D01 第 6、8 节；D02 11、12.2；D03 第 8 节。阻塞不能逐次拦截的模型调用、重试或恢复路径|
|SDK-03 工具与流式回调|固定带副作用的工具批次和流式事件，覆盖回调重复、断流及工作流重放；所有副作用经 Gateway 和当前门禁，回调或重放不额外启动 Operation|D01 5.2、第 8 节；D02 第 9、11 节。阻塞缺少门禁或去重证据的工具与流式路径|
|SDK-04 历史、批次与续接|固定合法消息历史、混合工具批次、提交回执与等待结果；观察原 Run 崩溃恢复和等待后新 Run 的身份差异、合法历史导入及早到/重复结果，原 tool-call 提交回执不被最终执行结果覆盖|D01 5.1～5.2；D02 1.3、12.2。阻塞相关批次导入、历史恢复与新 Run 续接|
|SDK-05 检查点与保留|固定含秘密引用和大对象引用的成功、失败、重试及清理场景；检查所有持久化边界只保存允许内容，脱敏引用足以恢复，仍被等待/恢复/去重所需的引用不先被清理|D02 第 8 节、12.2；D05 第 3 节。阻塞不能证明数据边界的持久执行及可能破坏恢复的清理入口|

本版六张卡的状态统一为“未验证”，未运行 SDK 或实际故障实验。P0 实施时先尝试候选版本的受支持接口；能力不足时选择经核验版本或薄适配并补齐相应卡。改变事务保证、持久调度职责或执行门禁的方案须回到权威文档评审，不以操作 DBOS 内部表补齐。Compose 与远端许可接缝仍按第 2.1、2.3 节及第 16 节形成专项证据，不能因六张 SDK 卡存在而省略。

### 2.3 可信时间与预览访问的前置决定

可信时间协议由 D04 8.2.1 维护。P0 的决定记录至少锁定许可时间戳的时间域：严格 UTC，或相对 Hub 签发方的授权时间；记录选项、理由与证据，不能在签发、接受和启动之间混用解释。记录误差上界的组成与计算依据，包括可信样本、采样误差、网络延迟及样本老化；普通 NTP“已同步”不构成严格误差上界证明。若选择相对 Hub 映射，验证认证许可通道与映射建立方式；若要求真实 UTC，补足时源和绝对误差依据。

P0 同时固定墙钟与单调时钟的分工、休眠/重启/虚拟机暂停后的失效条件和恢复条件，以及失信时拒绝新副作用、在途步骤按安全边界收束的可观测结果。恢复必须重新取得可信样本，先核对原步骤是否已经启动，确认未启动后才申请新许可；不得刷新旧许可的启动窗口，也不因时间失败自动获得应急授权。P1 在实际 Hub—Remote Agent 链路核验边界：`T+u` 等于过期时刻即拒绝；跨过启动窗口、重启或映射失信后旧 grant 不获新启动权；已经部署的业务继续按自身运行契约工作。具体阈值及公式只引用 D04，不在本文件另设数值版本。

预览的 P0 决定记录另按 D05 4.2～4.4 锁定声明支持的浏览器、外部浏览器、Tauri/WebView 票据交付路线，允许的原始端口/地址族/访问方清单，以及撤销关闭时限和控制失联界限的具体值、计时起点与失败行为。须显式评审撤销请求到全部代理确认之间的承诺；未冻结或未经支持的路线保持不启用，P2 才按第 4.1 节取得实际证据。

P0 退出条件：三组接缝可运行，六张卡逐项有版本化结论，关键不变量具备直接证据，首条链路规格和契约决定可实施；不支持或未决项有具体阻塞入口、责任人及解决决定，受影响功能不得进入后续阶段。时间协议和预览前置选择有明确决定，P1/P2 的实际链路证据不得由 P0 决定记录替代。P0 不要求提前冻结全平台所有 API，也不建设完整产品底座。

## 3. P1 最小执行闭环

使用已知的小型前后端数据库项目，交付基础身份、目标配对、受控 Git 与工作区、增量开发环境、受限构建、本地账本、资源准入、Compose 两阶段解析、薄扩展、不可变 Release、环境配置修订、计划审批和独立目标部署。基础 Desktop 可以提交、批准、查询和取消；本机应急未完成 P4 验收时保持未配置/不可用。

业务与 DBOS 同事务入队、稳定请求摘要、当前授权、秘密隔离、原子制品落盘和基本事件恢复随链路交付。默认支持有限步骤及可验证的迁移方式；未知结果保持阻塞，尚无自动恢复能力时明确进入人工核对，不尝试猜测重做。

退出条件：

- 已知项目通过构建和制品验证，在另一台机器按完整计划运行；Hub 离线后业务和目标重启仍可运行。
- 重复提交只关联原计划/Operation，已完成步骤不重复执行；失联时后续变更等待许可。
- 基本取消、安全停止、无权限、秘密不出界、沙箱与 Git 边界以及资源准入成立。
- 跨模块原子写入/入队、基础 worker 重启和未知结果门禁有证据；旧备份恢复入口默认禁止自动执行。
- 同一制品分别绑定两个测试配置形成计划，身份保持不变；必需参数缺失、变体不匹配及参数化越权被拒绝，秘密不进入解析输出。开发依赖缓存和版本化测试数据可以重建。
- 完成一次实际同机 4 核 8GB 已知项目交付测量，记录真实拓扑及 D03 的内存/CPU 预算执行情况；建立独立 Runner 的注册、能力匹配和分离统计，不能混记为同机通过。
- 按 D03 4.2～4.4 对同一共享宿主多 Runner 的并发资源申请、重复投递、执行器已接受但回执丢失、停止结果未知取得基本证据。Hub 数据库事务与执行器本地账本分别核验；未知占用继续保留并阻塞冲突资源，不描述为跨机器原子事务。
- 按 D03 4.3.1、4.4.1～4.4.2 取得三项直接证据：4GiB 执行池拒绝总硬上限为 5GiB 的组合；扩额已生效但回执丢失时不退账，未知调整按逐维保守值继续计量；构建退出但留下 7GiB 数据时，该字节仍被占账或从可分配容量中连续扣除，不能作为空闲再次分配。证据同时记录原分配、调整身份/修订、组级实际限制及释放/保留归属；首版不支持运行中调整时证明入口明确拒绝，并验证停止后重新分配路径。
- 按 D04 9.1～9.2 与 8.2.1 核验首批迁移许可、结果查询及停止边界：成功由迁移修订和后置检查支持，回执丢失先查询原操作，未知结果不得盲目重放或自动回滚。Task 取消的归属与传播按 D01 2.1～2.2、D02 7.1/12.4 留有基本证据。
- 按第 2.3 节及 D04 8.2.1 在实际链路取得可信时间边界和失信恢复证据；P0 方案决定不作为许可已正确执行的证明。Task 完成按第 3.1 节取得当前已交付能力范围的命令、唯一报告及普通推进关闭证据。

Registry、外部 CI 和完整运维 adapter 可在 P5 补齐；不能通过发送源码到目标临时构建替代制品交付。

### 3.1 Task 完成的分阶段退出证据

完成权威规则归 D01 2.1，执行收尾与当前推进资格归 D02 7.2、11、12.5。下表按能力出现的阶段递增取证；任何阶段一旦引入相关入口，就同时交付对应完成门禁，不能以完整 Agent 链路尚未完成为由允许该入口绕过。

|阶段|必须取得的完成证据|
|---|---|
|P1 命令与最小执行链路|覆盖允许及拒绝的来源状态、当前访问权限、唯一报告与一次版本推进。完成回执丢失后分别验证同键同摘要返回原结果、同键异摘要拒绝、新键命中 completed 返回原报告且不重新验收；当前链路可能写入交付范围的 Operation 若结果未知则阻止完成。完成提交后原执行身份不得新增普通写意图|

每份证据记录命令/Task/控制及输入修订、完成报告、在途写 Operation、实际允许或阻塞入口和竞争顺序。完成后的清理、费用/结果核对以及独立归属的人测、Release、Deployment 等流程依据自身权限继续；其事实不能反推 Task 普通推进仍然开放，Task 终态也不代替物理资源释放证明。

## 4. P2 Agent 完整链路

接入真实单 Agent 代码生产、工作项与正式验收资产修订、ContextPackage/ModelRequestRecord、有界 Run、长工具提交/等待、费用准入、独立验证审查和项目合并队列。补齐工作区人工接管、交还、增量预览与独立候选验证，并交付可选的固定版本沙箱临时部署和人类测试；Agent 代码使用同一 P1 链路。

交付统一工程引用、InputSet、证据适用性和必要影响索引。长任务提交回执可让 Session 继续独立工作，需要结果时登记等待；协议交接形成新 Run，当前 Run 崩溃恢复原身份。正式验收从固定受控来源加载，开发代码不能替换入口、关键断言或跳过规则。

退出条件：从真实需求到修改、人工介入、验证、审查、构建和批准部署形成完整链路；旧 Run 无法在交权后写入，交还差异送达并使相关证据复核。固定候选后恢复开发不会改变验证输入；预览实际修订可识别。缺失必需验收或私改跳过规则不能通过。模型真实请求和内部重试受预算约束，unknown 保留待核对，重放不重复计费。测量增量循环、构建/联调、队列与控制响应。

可选人工测试验收覆盖：未开启时不创建等待且不生成通过记录；开启后真实临时运行并向指定人类交付入口/说明；只有人类可以提交通过或显式跳过，问题反馈产生返工与新候选。超时/环境失败不自动通过，重建与版本变化重新判断适用性；测试资源、路由、身份及临时数据按约定回收。平台须实现两条分支，不要求每个业务任务都执行人工测试。

### 4.1 预览隔离最低退出证据

P2 必须为以下六组行为取得直接证据，并按 D05 4.1～4.4 的权威规则核验：

|证据组|最低证明要求|
|---|---|
|管理会话隔离|预览服务及代理拿不到管理认证材料；管理 Cookie 的作用域符合策略，专用会话凭据由代理消费而不转交项目上游|
|跨 origin 写入防护|由预览 origin 发起的越权访问与伪造管理写入被拒绝，CSRF/CORS 在实际链路生效|
|Tauri 原生能力隔离|预览脚本不能调用 Tauri IPC、文件或其他原生能力，也不能导航进入保有原生权限的页面|
|票据、会话、路由及已有连接撤销|按 D05 4.2 验证并发原子兑换、重放、响应丢失及撤销竞争，不产生第二份权限或静默续期。按 D05 4.3 从外部客户端、无权网络和其他沙箱验证原始前后端、HMR/流式端口旁路被拒绝，覆盖实际启用的 IPv4/IPv6。按 D05 4.4 验证已建立 SSE/WebSocket/其他流式连接真正关闭、逐代理确认、确认丢失、控制失联及重启，测量撤销请求至实际生效的时间；只拒绝新握手不通过|
|固定版本与旧页面|实际运行版本可核对；旧测试轮次的页面不能为新候选提交结论。环境重建后旧票据、会话、路由和旧页面重连不恢复权限或自动绑定新候选|
|秘密保护|经实际交付、跳转、失败与重试路径证明票据从未进入 URL 的 query、fragment、路径段；票据只经受保护通道到平台兑换端，兑换后丢弃。票据、临时账号材料和秘密值不进入通知、日志或诊断附件，取证仅保留脱敏结构及标识|

每份证据绑定候选、InputSet、制品摘要、环境实例、策略修订、实现版本和实际客户端版本；人测另绑定 HumanTestSession 与测试轮次。入口证据记录来源、地址族及端口，撤销证据记录授权修订、代理身份/启动代次、连接类型、请求/确认/生效时刻。浏览器证据还记录浏览器版本，原生路径记录实际 Tauri/WebView 版本。浏览器通过不代替 Tauri/WebView 原生能力隔离及票据交付证据。

P0 冻结的撤销关闭期限和失联检测界限须有具体值及起点，P2 核验达到边界、超时和恢复的行为；Hub 已保存撤销意图而代理未确认时仍为待确认，不能写成已即时撤销。参数未定、入口旁路未封闭、已有连接关闭未知或超出已评审承诺均阻塞对应 P2 支持结论。DNS/TLS 不满足策略、票据过期、权限撤销和环境回收的用户可见行为也纳入结果；人测超时、失联、环境故障或未反馈保持未完成。P6 扩展不同客户端与安装升级组合后才形成最终支持矩阵。

此阶段只确认单 Agent 工程链路，不以独立审查角色代替 P3 的两个开发会话协作验收。

## 5. P3 多 Agent 协作

交付至少两个开发 Agent 的独立工作区、角色策略、任务图、正式契约、直接消息、收件箱确认、可恢复等待、冲突处理与返工。两个开发会话围绕同一真实前后端需求协作，最终进入同一项目合并和交付链。

退出条件：契约确认后可并行实现，联调由精确产物解锁；循环等待、无进展和预算耗尽有明确升级方式；协调者依据持久业务记录接管。覆盖回复早到、重复结果、Run 结束/续接间崩溃、暂停收信、框架新 run_id、运行中契约变化及人工接管。一个长任务 unknown 只阻塞实际依赖它的工作，不把无关工作项强制纳入完成屏障。

同时记录首轮单/多 Agent 的质量、耗时、费用、冲突和无效通信，尽早检查协作假设。P3.4 执行前按第 11.3 节提交冻结包，以第 11.1 节字典采集可复算记录，并按第 3.1 节完成并发终态证据。P6 扩大重复实验和统计，不能到最终阶段才首次验证协作是否有效。

## 6. P4 可靠性与恢复完善

扩展崩溃、接管、部分部署、撤权竞争、迁移与补偿、Hub 旧备份、账本丢失和工作流升级。交付本机应急固定恢复、维护门禁、显式交还、分级备份及用户可操作恢复入口，并形成审计和兼容矩阵。

退出条件：旧进程未确认停止前不释放冲突资源；中间状态和漂移可核对；普通许可与独立本机授权的期限、撤销窗口和作用域符合 D04/D05。本机门禁阻止旧许可及重连 Hub，重启/授权到期不自动交还；只执行已支持恢复动作，未知数据库状态拒绝回退。恢复覆盖一致性数据库/文件引用、单项目数据与账本，新信任和逐资源核对前不自动出队；按预先固定 RPO/RTO 记录实际恢复结果，未达标明确报告。

普通 worker 重启覆盖在 P1，P4 验证停止准入、在途核对、兼容升级、缺失旧代码、旧备份和跨端恢复。若存在旧实现，按 D02/D04 显式迁移 v4.3/v4.4 语义；无旧实现时只交付约束，不编造迁移成功记录。隔离回放不能接触真实执行器或复用旧许可。

P4 扩大 P1 资源与许可基线，留下共享资源账本损坏、重启后的未知占用、执行器接管、撤权到实际停止的计时及远端已接受动作处置证据。恢复与接管必须先按 D02/D03 核对原身份、物理状态和冲突资源，再决定是否重新授权；本机授权到期或撤销不能被描述为已自动停止远端副作用。

## 7. P5 持续运维与扩展

交付有界日志/指标、关键业务/外部入口探测、外部 Hub 存活检查、ObservedState/DriftRecord、Incident、可靠通知与确认升级、固定诊断和获批 runbook。修复 Task 从实际运行基线建立，使用获准紧急优先级/预算并跟踪主分支同步。补齐支持清单中的 Registry、外部 CI 和观测 adapter，分别验证权限、幂等、身份及容量。

退出条件：管理通道与业务健康分开；Desktop 关闭后通知仍发送，渠道接收不冒充人工确认，失败/未确认会升级。runbook 或 Task 成功不直接关闭 Incident，业务持续恢复后才 resolved。普通构建占用、普通预算耗尽和主分支未发布功能不会被静默忽略，紧急修复仍遵循单重执行及统一交付。独立 Runner 与适配器声明可用/受限/不支持范围，不以扩展 Runner 等同于多 DBOS worker。

## 8. P6 产品与最终评估

完成 Desktop 项目、需求、团队、diff、证据、预览、审批、部署和 Incident 体验，以及 Windows/Linux 安装、升级、断线同步和权限变化处理。形成最终支持矩阵，逐项记录 OS/架构、Hub/Runner/交付拓扑、浏览器、Tauri/WebView、安装与升级版本、预览路径的支持/受限/不支持状态及依据；浏览器验收不能代替 Tauri 原生隔离验收。整合 P0～P5 实现和证据完成完整产品验收。

形成同机 light 与独立 Runner 两档容量报告、单/多 Agent 对照、缓存对照、成功交付成本、失败/人工介入记录及答辩材料。同机档位在真实 4 核 8GB 整机测量；独立档位以 4 核 8GB Hub 为基线，报告全部执行节点配置与总资源。

退出条件：无项目开发工具链的桌面可使用完整闭环，预览隔离与批准对象清晰，续接/授权等待/结果未知有准确提示；实验可追溯且报告覆盖率。允许得出受限通过、不支持或多 Agent 未优于单 Agent 的结论，完整目标依据实际验收确认。

|发布与交付|Compose 两阶段解析，Release/环境分层，同制品晋升及构建变体边界明确；普通计划在线许可，本机应急固定动作及交还可核对|
|安全与客户端|身份和权限由服务端校验，预览隔离有效，秘密材料受控，客户端同步保持状态一致|
|持续运维|业务探测、通知确认升级、紧急修复与持续恢复判定；独立运行、分级备份、应急和受控升级|
|容量与成本|执行遵循资源与费用预算，支持范围由真实整机测量和质量、时间、成本评估确定|

验收记录包含实现版本、运行环境、操作引用、预期与实际结果及支持范围，敏感字段只保存标识。远程交付、资源隔离和恢复能力在真实目标环境验收。

## 10. 两档部署容量测量方法

同机 light 使用整机受限为 4 vCPU、8GB RAM 的 Linux Ops Hub，外部模型 API 和另一台交付机器。独立 Runner 档位使用相同的 Hub 硬件基线，并记录各开发执行节点和交付目标配置，分别统计并给出总资源；不能只报告 Hub 的 8GB 而省略远端构建开销。记录 OS、架构、SSD/其他磁盘、Swap、项目 commit、工具链和全部常驻组件，不能只限制高配宿主中的一个容器。

记录空载、DBOS 入队/有界推进/检查点恢复、持久 Session 等待与定时容量、依赖安装、前端构建、后端测试、一次浏览器检查、预览竞争及归档交付的内存/CPU/磁盘峰值与耗时。分别记录 API 与 DBOSClient 池、worker 的 DBOS/模型池、PostgreSQL 活跃连接与写入、队列等待量、检查点增长和控制队列延迟；防止多个小池合计超过数据库上限。

核对 D03 的 2GB 常驻平台、1GB 操作系统/缓存、1GB 突发余量和最多 4GB 开发执行共享预算；这些是初始规划，报告同时列出实际占用和不足项。验证全部开发进程的 CPU 总配额、构建/测试内部并发、预览与测试资源合计、资源不足准入，以及重任务期间许可、取消和心跳响应。两个活跃 Task、三个模型请求和一个预览只作数量上限，不把配置值直接当作同时满负载通过的证据。

测量 API 延迟、数据库连接、任务排队、步骤许可及取消响应；阈值在执行前按支持范围固定，不在结果出来后为通过而修改。沿用 P1/P2 早期记录，最终报告比较变更后的资源趋势。DBOS 不需要独立服务的事实不能代替 SDK 和数据库增量的测量。

持续观察不少于 24 小时，混合代表性任务与空闲，检查泄漏、残留容器、资源预留、Session/WaitCondition 和 DBOS 定时/历史增长、指标行数、日志增长和清理引用。加入依赖缓存命中/失效、预览休眠恢复、短冻结候选采集、人工交接及紧急修复排队的代表性场景，分别记录等待和执行耗时。通知、外部探测和备份的外部资源单列，不隐藏在 Hub 容量内。支持结论分为通过、受限通过、不支持；单 worker 不替代多 worker/Conductor 验收。

## 11. 多 Agent 与版本化证据实验口径

论文主线集中回答：在需求、契约、源码和构建输入持续变化的多 Agent 开发中，版本化输入与证据协议如何减少错误解锁和无效返工，并影响交付质量、成本及人工介入？实验结论必须对应实际实现和独立验收记录；不把一次演示或隔离模拟写成生产能力已经成立。

任务集覆盖三类变化：单模块修改、跨前后端契约修改、数据库或发布影响修改。每项任务固定原始需求、验收资产和成功条件，记录变化版本、输入范围与独立验证结果。

|证据组|对照问题|主要指标|
|---|---|---|
|版本化证据决策|输入变化后系统是否拒绝过期结论、阻止错误解锁并只要求必要复核|失效证据拒绝次数、错误解锁判定、复核范围、影响传播延迟及错误结果的实际影响|
|单/多 Agent 交付|多开发会话相对单会话是否改善结果|通过率、质量问题、总耗时、全部费用、token、冲突、返工、无效通信、人类次数与耗时|
|反馈与独立验证|人工反馈和独立验证是否发现并消除问题|发现问题、重复缺陷、修复轮次、反馈到修复时间、最终残留问题及复核覆盖|

### 11.1 可复算指标字典

P3.4 执行前冻结字典修订和原始记录格式。每条记录至少关联实验运行、协议修订、任务/变化修订、条件与重复序号、相关输入/消费者/消息/操作身份、观测时点及证据来源；统计表保留分子、分母、去重键、状态和排除理由，不能只保留最终百分比。一次运行的开始点、观察截止点与成功条件均由冻结包给出，原始失败记录不可被重做覆盖。

|指标|计数单位与去重|分子、分母及必须并列的信息|
|---|---|---|
|错误允许与错误阻塞|固定输入、消费者、依赖判定规则及判定时点的一次决策为单位；相同决策的传输重投/重放去重，输入或判定时点改变后的新决策另记|错误允许率＝错误允许数／独立判定应拒绝数；错误阻塞率＝错误阻塞数／独立判定应允许数。分别保留系统允许/阻塞与独立允许/拒绝的计数，另列无法判定、观测缺失及分歧；不能通过全部拒绝只报告低错误允许率|
|必要复核完成与额外复核|同一变化及评估时点的复核项按对象、方法修订和固定输入去重；独立必要集合 B、系统要求集合 R、实际完成且有可核对结论的集合 C 分别保存|必要完成覆盖为 C 与 B 的交集大小除以 B 的大小；额外复核比例为 R 中不属于 B 的项数除以 R 的大小。保留三集合清单和未完成原因；C 表示完成取证，失败结论也保留，不等于通过集合|
|返工与可避免返工|以独立可定位的返工事件为单位，绑定触发、受影响范围和开始/结束；同一事件的多条消息与多次记录不重复计数|每个事件只有一个互斥主因：正常需求变化、实现缺陷、错误解锁、错误失效、集成冲突或外部故障；可另标促成因素，但不相加为事件数。依据冻结规则独立判断可避免性，报告全部事件、各主因与可避免子集；无法归因单列|
|无效通信|按唯一消息 ID 与接收者组合计数；广播给多个接收者分别计，传输重投去重；语义重复但 ID 不同的消息保留供分类|每个组合按冻结优先规则归入有效、语义重复、过期、无关接收者或不可处理内容之一；无法判定另列。无效通信比例为后四类组合数／全部组合数，同时给出分类计数和判定覆盖率|
|人工介入|以一次有明确开始/结束和目的的介入事件计数，关联参与者与运行；按常规审批、人测、接管、故障恢复分类|分别报告至少一次介入的运行数／全部已开始运行数、事件次数和主动人工分钟。主动分钟按每名参与者的实际操作区间去重后相加；等消息、排队、模型或环境的被动等待另列，不计入主动分钟|
|交付成功与耗时|按实验运行计数，重做分配新运行 ID 并关联原失败运行；从冻结的开始点计时至成功、终止或观察截止|成功率＝截止前满足独立成功条件的运行数／全部已开始运行数。失败、预算终止、取消及观察截止仍未完成分别列数与实际已耗时；截尾不能记作零耗时或从分母消失。仅成功运行的耗时统计明确标为条件统计，并同时报告全部运行结果|
|独立质量与反馈修复|缺陷按独立可复现的问题身份和候选去重；同一缺陷再现记关联复发，不因消息多而增数。反馈到修复以首次有效反馈到独立验证修复通过为区间|报告已验证候选数、发现/残留/复发缺陷及预先冻结的严重度；无候选、覆盖不足或未完成检查记未知，不等于零缺陷。修复未完成按截止点保留截尾区间，不只统计已修复问题|
|影响传播与实际下游影响|按输入变化事件及受影响消费者记录变化提交时点、首次正确拒绝/复核决定和实际后续动作；同一变化重放去重|报告传播延迟及未达到正确决定的截尾；使用预先确定的可比较计时来源。决策错误与实际下游影响分别记录，只有真正执行并观测下游才登记实际返工、额外耗时或费用|
|费用、usage 与覆盖率|以每次真实出站模型请求为单位，使用 ModelRequestRecord 去重；所有成功、失败、重试及恢复后新请求纳入，保留提供方、模型/价格修订、币种和计价依据|费用覆盖率＝费用已可核实请求数／全部真实出站请求数；usage 覆盖率＝冻结的必需 usage 字段齐全请求数／全部真实出站请求数，两者分别报告。保留已知费用小计、未知请求及其原因，未知不记零；已知 token 按输入、缓存、输出等实际字段分列，缺字段不补零|

复核公式固定为 `|C∩B| / |B|` 与 `|R−B| / |R|`。例如 B＝{A,B}、R＝{A,B,C}、C＝{A,C} 时，必要完成覆盖为 1/2，额外复核比例为 1/3；安排了复核不代表已经完成。各运行先报告本身分子/分母，再按冻结的汇总方式报告总体值，不能在结果出现后选择对结论更有利的平均方式。

全部成功及失败请求费用都属于交付成本。成功交付成本的目标口径为全部实验费用／成功运行数；零成功时不可计算。存在未知费用时完整总费用及完整单位成本仍未知，可另给“已确认费用小计／成功运行数”的下界并同时展示费用覆盖率，不能把下界作为完整成本。费用与 usage 缺失分别记 unknown，不能用其中一项覆盖率推断另一项。

### 11.2 独立判定与两类对照的解释边界

独立真值依据冻结的需求、契约、代码差异和独立验收规则产生，记录判定人或独立检查方法、修订、理由及证据。被评系统自己的 `valid`、依赖图或 Agent 自述可以作为被观察数据，不能同时作为判断其正确性的独立标准；B 不能直接复制系统的 R。无法判定、审阅分歧、观测缺失均单列并保留原记录，不能默认正确或选择性删除。冻结包规定分歧复核流程、最终裁决或保持未决的规则及判定覆盖率；未决量较大时限制结论范围。

|对照|固定条件与唯一变化|可支持的结论|
|---|---|---|
|隔离事件轨迹对照|对同一输入、证据、消费者和判定时点，比较“只按完成状态”与“按输入版本及证据适用性”两种依赖规则；只改变判定规则|可以比较错误允许、错误阻塞和复核选择。没有真正执行下游时，不能计算实际节省的返工、时间或费用；若执行下游，另记录受控执行条件与实际证据，不从判定差异直接换算收益|
|真实单/多 Agent 交付对照|两边采用相同证据门禁、正式验收策略、工具权限、共享总资源、总预算和人工规则；固定模型/版本、初始输入及外部条件，变化是开发会话组织方式|可以评估所测任务上组织方式的整体质量、耗时和成本收益；不能把所有差异归因于版本化证据机制，也不能把额外节点资源或额外人工作为免费条件|

隔离对照不得关闭、放宽或替代实际系统的版本证据生产门禁。真实单/多 Agent 条件按冻结任务重复，记录顺序、随机因素、失败与波动；总资源包含全部 Runner/目标相关开销，总模型预算包含所有会话及失败请求。P3 用少量样本检查假设与测量流程，P6 在预定总预算内重复并报告样本量、覆盖率和不确定性。简单任务若多 Agent 增加成本或时间，应如实报告，不为演示外观扩大团队。

### 11.3 P3.4 实验冻结包

P3.4 的前置交付是一份有唯一修订和确认日期的冻结包；数据采集开始前必须完成以下内容，缺项则阻塞对应实验入口：

|冻结内容|最低记录|
|---|---|
|任务与变化触发点|任务集、原始需求/契约/候选与独立验收资产、成功条件、变化内容及触发时点/条件；记录任务取得或创建来源，不能从结果倒选样本|
|指标字典与判定责任|第 11.1 节单位、原始字段、去重键、分子/分母、汇总算法和第 11.2 节独立依据；指定数据采集、独立判定、分歧复核与报告责任人/方法，保留裁决依据|
|重复与执行顺序|各条件的预定重复次数、顺序/交错或随机规则及种子、模型与工具版本、全节点共享总资源、缓存与外部环境控制；不能只为失败一侧临时增加重复|
|预算、开始与停止|单次和总费用/时间/资源/人工预算、已开始的判定点、预算耗尽/安全失败/外部故障的停止条件、观察截止及截尾记录方式；停止后不偷偷补足为成功|
|失败、重做与排除|预先可用的失败分类、允许重做条件与新运行关联、允许的排除理由及审批记录。原失败和重做费用保留，全部已开始运行仍进入主表成功率分母；若另做排除后的辅助分析，明确其不同分母及理由|
|零分母、未知、分歧与截止|零分母统一为不可计算并保留计数；未知/缺失/分歧分别编码，不能记零或自动通过；预定裁决期限、截止后补证处理和快照版本。已知部分统计同时给覆盖率，必要时给未知可能影响的范围，不以删除未决记录改善结论|

P3.4 退出时交付冻结包、逐运行原始记录、独立判定、可复算汇总与限制说明；任何因试运行而修改的协议都保留旧修订及修改原因。P3 后若调整任务、门禁、指标、预算或统计协议，先冻结新修订，P6 分开报告旧协议探索结果与新协议结果；未经明确说明及可比较性论证，不合并为同一结果集。

### 11.4 缓存辅助实验

缓存是独立辅助实验，不与 Agent 数量、审查策略或输入语义同时改变。比较每轮重拼与稳定前缀/增量追加，固定语义输入和验收，分别记录冷启动、连续请求和压缩切换；交错或随机安排顺序，记录调用间隔与提供方缓存条件。无法保证物理冷缓存时注明限制。提供方能力和 usage 取自真实记录；无法取得 usage 时只报告输入稳定性，缓存收益记为未知。费用包括缓存创建/读取、输出、失败请求和压缩，命中率只作为诊断指标。

DBOS 接管通用持久调度，平台保留需求/契约、审批、资源、Git 集成、Release/Deployment 和真实操作核对。不得一边引入 SDK，一边继续实施旧的通用 WorkflowJob 队列和调度租约。官方依据由 D02 维护。

## 15. 建议代码组织

实现代码按以下目录组织。运行入口与逻辑模块分开，逻辑模块可以共享进程部署。

```text
cloudhelm/
  apps/desktop/                 # 管理客户端
  services/hub-api/             # FastAPI + DBOSClient，不启动执行运行时
  services/hub-worker/          # PydanticAI/单 DBOS 运行时，统一注册各领域工作流
  services/dev-runner/          # 受信任开发执行器
  services/remote-agent/        # 完整计划的有限步骤执行、许可校验与本地账本
  modules/identity/             # 身份、策略与审批
  modules/projects/            # 项目、仓库及需求版本
  modules/collaboration/       # 工作项、依赖、决策、消息及业务等待/续接工作流
  modules/agent-runtime/       # PydanticAI 适配、Session/有界 Run、请求、上下文及推进工作流
  modules/workflow/            # 公共 DBOS 接入、WorkflowBinding、版本注册与恢复门禁
  modules/execution/           # Operation、Attempt、步骤及资源
  modules/workspaces/          # 增量环境、写入权交接、候选采集与沙箱生命周期
  modules/integration/         # 合并队列、正式验收资产、验证和审查
  modules/tool-gateway/        # 工具鉴权及路由
  modules/delivery/            # 两阶段解析、Release/环境修订、计划/许可和应急事实核对
  modules/operations/          # 业务探测、通知、Incident、修复关联与恢复流程
  modules/sync/                # Outbox、业务事件、快照与客户端游标
  modules/artifacts/           # 内容存储、索引与清理
  integrations/                # DBOSClient 封装、Git、CI、模型、MCP 和观测适配
  packages/contracts/         # API/事件/执行 schema，共享工程引用和 Runtime 契约
  database/migrations/         # 业务 schema；DBOS 系统迁移单独受控执行
  infra/ops-hub/
  infra/remote-target/
  examples/standalone-project/
  docs/design/
  docs/acceptance/
  tests/
```

各业务模块的 application 层保存命令处理器和所属工作流，通过 UnitOfWork 与领域接口组织短事务，领域服务不自行提交。通用事务基础仅封装数据库会话生命周期，不承载业务规则。跨模块依赖避免循环导入与任意写表；实际目录可调整，但不改变 D01 状态所有权。DBOS 只在受信任 Hub；执行器实现平台协议和本地账本，应急入口属于 Remote Agent 的受限本机管理能力。共享工程引用不改变权威所有者，公共 workflow 层不反向依赖全部业务模块。

|P2/P4|模型已计费但响应/检查点未知|保留原请求和未知费用；新增真实请求重新准入，不重复结算|
|P4|PydanticAI/工具历史变化、兼容补丁、缺失旧代码|旧流程可恢复或明确 waiting_upgrade；不无条件套用新步骤序列|
|P4|恢复旧备份，远端比备份新，Run 已结束而 Session 仍在等待|启动门禁生效；核对真实操作和等待；新控制信任建立前不恢复执行|
|P4/P6|清理期间等待条件、InputSet、证据或恢复仍引用内容|所需历史和制品仍存在，去重窗口保持有效|
|P5/P6|独立 Runner 能力不足、断线、工作区迁移|按真实节点准入；占用/来源明确；Hub 与全部节点资源分别报告|
|扩展前|多 DBOS worker、新旧应用版本、Conductor 故障|故障转移、版本路由和物理核对明确；独立 Runner 验收不能替代|

### 19.3 关键路径与阶段记录

原始量级加入约 25% 的接缝返工和环境差异缓冲后为 156～254 人日；按每月 20 个有效工作日，单人全职约 8～13 个月，论文正文另计。这些数值保持为待核实前提下的规划基线，新增适配和资产建设等单列工作确认后重新汇总，不承诺维持原上界。关键路径为 SDK/事务接缝 → 可靠执行闭环 → 单 Agent 生产与证据 → 多 Agent 协作 → 恢复与运维完整性 → 最终产品验收。Desktop 随阶段交付；Linux 构建环境、执行器账本、客户端基础和适配器可在相应契约冻结后并行，真实机器验证、人类验收和集成仍遵守前置依赖。

统一阶段记录模板：

- 阶段/工作包 ID、原估算、实际投入、剩余估算。
- 估算前提和支持矩阵修订、组合/适配器数量、额外子包及其依据、重估日期与相对原估算的差额；尚不能估算的项明确标记待估。
- 未决决定、受阻范围、解决责任人与下一检查点。
- 已实现：附实现版本或 commit 及对象引用。
- 自动验证：附方法版本、输入集、环境、结果与证据引用。
- 人工验收：附验收人、范围、时间和结论。
- 未完成：列明剩余退出条件及其阻塞范围。

本版 P0～P6 状态均为“设计待实施”。记录模板中的实现、自动验证和人工验收只有在对应证据形成后才更新；不得从估算表或历史修订追踪推断当前进度。
