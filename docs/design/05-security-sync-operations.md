## 1. 身份、权限与威胁边界

|身份|允许的职责|隔离要求|
|---|---|---|
|User / Desktop Session|获授权的项目操作、审查与审批|登录凭据保存在 OS 凭据存储，不进入 SQLite 普通缓存|
|Agent 身份|代表明确用户与 Task 的受限工具调用|能力不超过用户、任务与资源策略的交集，不能代替人类批准|
|hub-api / DBOSClient|业务命令、入队、查询及受控流程管理|仅经领域授权操作；数据库权限不下发 Desktop 或 Agent|
|hub-worker / PydanticAI / DBOS|执行有界 Run 和所属领域工作流，调用受控工具|受信任控制面进程；模型输出不授予宿主权限，原始 SDK 管理接口不向普通用户暴露|
|Git 服务|仓库元数据、受控提交与远端认证|不运行仓库提供的宿主脚本|
|Runner|开发沙箱、进程、资源与受限构建|宿主接口不向 Agent 或生成代码开放|
|Remote Agent|完整计划的唯一物理步骤推进、诊断和固定 runbook|machine identity 与人类/开发身份分开；普通步骤在线取许可，本机应急独立核验第 2.2 节授权|
|本机应急管理员|安装时明确授权的目标机管理员，主动确认固定恢复计划及交还|独立身份校验、有限资源/动作与期限；不授予 Agent，不从 Hub 普通会话继承|

采用 system/project/environment scoped RBAC，结合资源归属和当前策略。owner、developer、reviewer、operator、deployment_approver、auditor 是建议角色；服务端决定权限，UI 隐藏按钮不能替代检查。

### 1.1 首条链路动作权限矩阵

每次读取、命令、反馈提交、批准和物理执行都按当前身份、资源归属、对象版本及策略重新判权。批准只覆盖明确的对象摘要、资源和有效期，不自动转成其他动作的权限；下表给出首条链路的最低规则。

|身份|动作|资源作用域|当前权限检查时机|审计主体|明确拒绝原因|
|---|---|---|---|---|---|
|项目所有者|管理项目配置和职责；控制有权管理的 Task；在个人流程中批准本人提交的具体候选或计划|明确归属的项目、Task、候选、计划摘要及目标环境|每次读写命令时；批准提交时和后续步骤许可签发前再次核对权限、对象版本和策略|实际操作的人类用户、会话及关联项目/Task/批准记录|项目或对象不归属此人、授权失效、对象已变化；团队或重要环境缺少独立批准者|
|开发者|在获准工作区开发、提交候选并控制获授权范围内的 Task；不包含部署批准|获准项目、工作区、Task、输入集合和候选|工作区写入或命令入场时，以及候选提交时检查当前归属、写入权和版本|实际开发者及其工作区、Task、候选版本|缺少项目/Task/工作区权限、写入权已交接、输入或候选版本过期；开发者身份本身不含部署批准权|
|审查者|读取授权范围内的固定产物并提交审查结论；不得签发执行步骤许可|指定项目、候选、InputSet、审查任务及其固定摘要|读取时和提交结论时复核审查分配、候选版本及适用性|实际审查者及其审查任务、产物摘要和结论|审查分配或资源范围不匹配、候选已变化或证据失效；请求步骤许可属于越权动作|
|指定测试者|进入指定人测预览，提交通过、需要修改或明确跳过的人工反馈|获准项目、候选、InputSet、环境实例、HumanTestSession 和测试轮次|票据兑换时、每次访问时及反馈提交事务内检查身份、权限、版本、期限和会话状态|实际测试者及测试轮次、候选、反馈和提交时间|未获指定、对象或轮次不匹配、票据/会话过期或撤销、环境已回收、反馈已关闭|
|部署批准者|批准固定计划摘要、起始状态、目标环境及声明的影响|获准项目、具体候选/制品、DeploymentPlan、目标环境和环境配置修订|批准提交时检查当前授权与摘要；步骤许可签发及执行前复核批准仍有效且目标未漂移|实际批准的人类身份及批准记录、计划摘要和目标|缺少独立批准资格、资源或摘要不匹配、计划/配置/策略已变化、批准过期或已撤销|
|Agent|在委托范围内查询、提出命令和 Operation 请求；不得冒充人类提交人工审查、人测结论、跳过或批准|当前委托用户、Task、会话、输入引用及策略允许的资源|Gateway 每次调用时；写入命令和每项步骤许可签发前再次检查委托、Task 状态和资源权限|Agent 身份，并保留实际委托人、Task、会话和命令关联|委托缺失/过期/超范围、Task 已取消或权限已撤销；要求冒充人类提交人工结论、跳过或批准时拒绝|
|执行器|仅接收和推进绑定到本机身份的已授权计划步骤，记录物理事实|单一执行器身份、Operation、步骤、输入摘要、资源范围、控制代次和期限|收到许可时、开始副作用前及后续新副作用前核对许可、期限、撤销、计划摘要和本机事实|执行器 machine identity 与 grant/批准/Operation 引用分别记录|许可不存在、过期、撤销、摘要或机器身份不符、资源越界或缺少所需人类批准；机器身份不能替代人类授权|
|本机应急管理员|确认预先固定的本机恢复动作并执行交还|目标安装、执行器、资源、动作及期限均由独立 EmergencyAccessProfile 预配置|本机入口认证时和每项动作前核验 OS 身份、配置完整性、范围、到期与撤销状态|实际本机管理员、installation/executor 身份、Profile ID/revision 和动作记录|应急配置未启用、身份不匹配、动作/资源超范围、期限届满、配置已撤销或可信时间不足|

个人流程允许所有者自批；团队和重要环境继续按现有策略要求独立批准。开发者角色不自动包含部署批准权，审查结论不签发步骤许可，Agent 与执行器均不能替代人类签名或确认。本机应急权限必须独立预配置允许范围、有效期限和撤销方式，不从 Hub 普通会话、Agent 或机器身份继承。

Task 取消权按 [D01 第 2.2 节](01-domain-collaboration.md) 单独判定，与 Deployment 批准权限相互独立。Task 取消后，只保留对原 Operation 的查询、协议允许的安全停止请求、后置条件核对和事实归档等受限控制权，遵循 D02 第 7.1 节；这些动作不新建执行意图。新增补偿、回滚、迁移或其他副作用仍须按自身资源范围取得授权和必要审批。

DBOS application_name、queue_name 和 workflow_id 仅用于路由与关联，不构成项目授权边界。客户端查询与恢复先解析 WorkflowBinding 并校验资源权限；DBOS 管理端口、直接数据库连接和可选 Conductor 控制台只对获准运维身份开放。fork、rewind、强制恢复和删除历史具有独立审计，不允许 Agent 直接调用。

PydanticAI 的角色配置、工具批准、MCP、workspace 和事件回调不能绕过 Gateway。框架工具参数合法不等于业务授权；协调、开发、验证和审查角色的能力由当前用户、Task 与资源政策交集决定。

仓库、附件、网页、日志和其他 Agent 的内容作为数据处理。Gateway 验证能力、路径、输出限额及授权，不能因工具标记为只读而忽略敏感数据访问。

初期面向受信任平台所有者管理的项目，不宣称普通 Docker 能隔离任意敌对租户。需要敌对多租户时增加独立 Runner 或更强沙箱，并重新验证宿主、网络与缓存边界。

Remote Agent 的 Docker 管理权限具有较高宿主影响面。项目命名空间用于防误操作与资源归属，不等于可以抵御具有 Docker 管理权限的恶意主体。

## 2. 配对、通道与能力

初次机器配对使用短期单次挑战，绑定目标、操作者和有效期，建立独立 machine identity。后续凭据支持轮换和吊销；执行器校验当前获准的 Hub incarnation、操作摘要、资源、期限和代次。

Desktop、Runner 和 Remote Agent 通道均认证并验证 TLS 对端。SSH 引导只执行已说明的安装步骤，日常操作统一走执行协议。管理员可经受控本机控制台或获准 SSH 登录使用第 2.2 节应急入口；SSH 登录本身不替代应急授权，也不作为 Hub 自动部署通道。

固定只读诊断可按策略自动运行；重启、配置修改、回滚和数据操作必须有对应授权及审批。普通权限撤销后 Hub 拒绝新步骤许可并发送取消，执行器获知后拒绝尚未开始的动作，运行中操作按 D02/D04 安全停止或核对。本机应急使用预先配置的独立权限，不自动继承普通角色；撤销语义见第 2.2 节。离线撤权存在受限窗口，不能声称即时撤销；实际许可使用和影响保留审计。

### 2.1 计划与步骤许可的信任边界

完整计划经认证通道提交，规范化摘要绑定批准内容；步骤许可绑定计划、Operation、步骤输入、执行器、控制代次、资源代次及期限。Remote Agent 持久登记已接受许可，不能由另一执行器复用；相同许可重投只返回既有执行结果。

普通步骤许可签发在 Hub 检查当前权限、暂停/取消、恢复门禁、secret 状态和 D04 前置条件；执行器使用前核对本地事实、维护门禁和期限。审计只保存标识和授权范围，不包含秘密值或可复用认证材料。v4.7.0 保留在线逐步骤许可，并提供预先配置的人类本机应急授权；既有业务继续运行、普通部署与人工恢复分别管理。

### 2.2 本机应急授权与维护门禁

应急能力默认未配置；只有部署所有者在可信安装/配对期间明确授权目标机管理员，并在目标端完成确认，才可启用。EmergencyAccessProfile 固定 profile_id/revision、installation/executor 身份、允许资源与动作、管理员身份映射、认证方式、有效期限、最大执行时长、策略来源及撤销记录。Hub identity 模块保存签发与审计，Remote Agent 保存已验证配置、独立信任根和使用记录；旧 Hub 备份或数据库里的批准行不能自行恢复该权限。

本机受限管理接口通过 OS 身份和预先登记的本机认证材料验证操作者，校验配置完整性、作用域和期限。P0 冻结 Unix socket/受限管理命令的权限、身份映射与认证实现，P4 验证。普通网络 API、模型工具、Agent 身份及 Desktop 会话不得调用本机入口。配置、认证材料和信任根受最小文件权限保护，不进入模型、诊断包、业务归档或普通日志；目标 root 仍属于高信任边界，不宣称能抵御恶意 root。

离线只能基于目标端最后接受的有效应急配置判断授权：已知撤销即时禁止新动作，未送达撤销可能在原授权截止前不可见。安装时明确接受最大离线授权窗口，期限或时钟可信度不足时拒绝新动作，不自动延长。普通 RBAC 撤销不被描述为已同步撤销本机独立权限；撤销流程须通知目标并记录确认，失联时显示“撤销待送达/最迟失效时间”。应急续期或扩权要求重新完成可信授权流程，不能凭旧配置离线自签延长。

应急认证通过不等于立即执行。Remote Agent 先在持久账本登记范围内维护门禁，拒绝所有新普通变更，包括尚未使用的旧许可、更高 generation 和重连 Hub 命令；已执行进程仍按 D02 核对。固定恢复计划由人类确认摘要，授权只覆盖该计划、动作与期限。实际步骤、失败及交还遵循 D04 第 8.5 节，维护门禁不因超时、注销、重启或更换控制身份自动消失。

初始能力不更换配置或 secret 版本，不启用已知撤销材料。离线使用当前运行材料的允许期限、用途及撤销可见性须在应急政策中明确；若材料要求在线验证或已不满足离线条件，动作拒绝。应急不能保证在凭据被上游撤销时业务仍可恢复，不能为恢复服务回滚到已撤销版本。

解除门禁需要本机管理员与当前获授权 Hub 对同一恢复事实完成显式交还；原授权已到期时允许最小只读核对，新增变更或重新建立管理身份须重新授权。所有冲突操作必须有确定边界，未知影响不强制清零。范围、操作者、配置版本、计划、确认与交还结果审计关联，实际秘密及认证材料不记录。

## 3. 凭据版本与秘密材料

SecretReference 至少包含用途、所属项目/环境、提供方、不可变 version_id、状态及访问策略。实际秘密值由受控凭据模块解析，模型只接触用途和不含值的引用。

首版可采用加密持久存储，解密密钥与数据库备份分开管理，通过受限服务身份访问；支持外部凭据后端时，adapter 必须说明版本固定、轮换、吊销和恢复能力。若后端只能返回 latest，不满足固定版本要求，需经受控机制固化版本或拒绝相应部署。

轮换创建新版本，明确旧版本是继续有效、停用还是已撤销。DeploymentPlan 固定版本引用，执行前再次检查可用性；不能自动把旧计划解析为新值，也不能回滚到已撤销凭据。

目标端仅持久保存当前运行及明确保留恢复所需材料，使用最小文件权限和适合的加密/挂载方式。业务独立重启需要能在不联系 Hub 的情况下读取获准材料。环境变量等注入方式的可见性应在安装说明中如实列出，不承诺对目标 root 隐藏。

读取、修改和排障配置时不得显形输出密钥。禁止实际值进入模型输入、聊天、审计正文、客户端 SQLite、可分享制品及普通日志；受保护的凭据存储和目标运行所必需的受限材料属于专门管理范围。审计只记录版本与操作身份，不上传容易枚举的秘密明文哈希。

PydanticAI 的消息、错误、工具结果和流式事件可能进入日志与检查点；上下文组装和模型请求入口按当前权限过滤，框架 run_id 只作关联不作授权。完整历史放入受保护存储，权限变化时切换必要的上下文代次，不能为续接保留被撤销的敏感内容。

DBOS 会持久保存工作流及步骤输入输出，实际 secret、数据库连接凭据和完整认证响应不得作为这些参数或结果。步骤内部按用途即时解析受控 SecretReference，仅返回非敏感摘要或状态；异常、SDK 日志和追踪属性同样过滤。备份 DBOS 系统 schema 时继承控制面数据的访问与保留策略。

脱敏是补充措施；私有依赖令牌不复用生产凭据，生成代码不能访问长期管理凭据。秘密暴露处置需轮换/吊销并按保留策略清理受影响内容，不以删一条聊天消息宣称已经消除外部传播。

## 4. 预览域名与浏览器隔离

管理端与预览端必须使用不同主机名，优先不同站点域；每个预览实例独立 origin。不同端口不隔离 Cookie，因此禁止仅用同主机不同端口实现管理与预览隔离。

管理 Cookie 使用 host-only、Secure 和 HttpOnly，并配置适当 SameSite、CSRF 防护及受限 CORS。管理会话不通过父域 Cookie 与预览共享，管理认证材料不进入预览代理或项目应用。预览专用的平台访问凭据由代理消费并从上游请求中移除，不转发给项目应用；管理 API 不向任意预览域开放带凭据访问。

访问票据短期有效、单次使用，绑定当前用户、项目、环境实例、访问用途、权限和授权期限；固定候选访问另绑定候选与 InputSet，人测访问还绑定 HumanTestSession 与测试轮次。票据全程只经受保护通道交付和兑换，不进入任何 URL 的 query、fragment 或路径段，兑换后丢弃。通知和浏览器打开链接只包含不授予访问权的资源标识。路由绑定固定沙箱、上游端口、协议及有效期，不能通过用户提供任意上游地址绕过访问范围；兑换、入口和撤销分别遵循第 4.2～4.4 节。

Desktop 使用无 Tauri 原生能力的独立受限 WebView 或外部浏览器；拒绝主窗口 IPC 和跳转到具备原生能力的页面。终止预览时撤销路由、票据与预览会话，并清理实例相关存储。

安装预检要求管理和预览域名、DNS、证书及客户端信任链均可用。可使用公网域名或受控内网 DNS/证书，但不能默认忽略证书错误。只有 IP 的环境须先完成受控名称与信任配置；未配置时预览显示不可用，不能把该配置标为完整验收通过。

### 4.1 P2 预览隔离与撤销证据规格

本节是预览隔离、撤销和证据适用性的权威安全要求，以下六类证据构成 P2 最低出口。D06 第 4.1 节应引用本节并定义证据采集与退出判定；实现或证据不得弱化这里的约束。

|证据类别|必须证明的结果|
|---|---|
|管理会话隔离|所有管理会话 Cookie 与认证材料均不发送、不复制到预览代理或预览服务；管理 Cookie 保持 host-only、Secure、HttpOnly 及适用的 SameSite/CSRF 设置。预览 Cookie 按第 4.2 节限定主机、Path、属性及期限，平台访问凭据被代理消费且不出现在项目上游请求中。通过实际请求与代理转发证据核验。|
|预览来源写入防护|来自预览 origin 的越权请求及伪造管理写入均被拒绝；以实际跨源请求证明 CSRF 防护和 CORS 策略生效，不能只以配置存在作为通过。|
|Tauri 原生能力隔离|预览脚本无法调用 Tauri IPC、文件系统或其他原生能力，也不能跳转进入具有原生权限的页面；独立 WebView 与外部浏览器分别记录实际边界。|
|票据、会话、路由撤销|过期、已消费或撤销票据不能兑换；并发兑换至多创建一个会话，兑换成功但响应丢失后不补发凭据、不产生第二份权限或静默续期。按第 4.4 节取得撤销意图、每个代理的拒绝新访问及关闭已有 SSE/WebSocket/其他流式连接的确认、实际耗时和失联/重启证据；单纯禁止新握手不通过。按第 4.3 节从外部、声明无权的网络及其他沙箱验证原始前后端、HMR 和流式端口均不能绕过入口，覆盖实际启用的 IPv4/IPv6。|
|固定版本与旧页面|实际运行候选/修订可核对并与授权输入一致；旧人测页面不能为新候选提交通过或其他结论。环境重建使用新实例与新授权，旧票据、会话、路由及旧页面不能恢复访问或自动绑定新候选。|
|秘密保护|票据、临时测试账号秘密和其他真实秘密不进入通知、URL、日志或诊断材料，也不在界面显形。实际交付和兑换证据覆盖 query、fragment、路径段、跳转与失败/重试路径；票据只进入平台控制的兑换端，兑换后丢弃，不交给项目应用。取证仅保存脱敏结构、标识和检查结果，不保存票据、Cookie 或测试账号秘密的真实值。|

每条证据绑定候选、InputSet、制品摘要、环境实例、策略修订、实现版本和实际客户端运行时类型/版本；人测另绑定 HumanTestSession 与测试轮次。入口证据记录测试来源、目标地址族/端口和结果，撤销证据记录授权修订、代理身份/启动代次、连接类型和确认时刻。运行时字段须能区分实际浏览器与 Tauri/WebView 版本。浏览器通过不能覆盖或代替对应 Tauri/WebView 环境的证据；未实际验证的客户端交付路线保持待验证，不能声称可用。

### 4.2 访问授权、票据交付与原子兑换

访问授权以 `access_authorization_id` 和 `authorization_revision` 关联用户、资源绑定、权限、策略修订、绝对到期时刻及撤销状态；这些标识本身不授予访问权。票据使用不可预测的秘密值，服务端只保存受保护的校验摘要、状态及关联标识。兑换记录以 `redemption_id` 关联票据与唯一 `preview_session_id`，审计不保存可复用的票据或会话凭据。人测绑定包含候选、InputSet、制品摘要、环境实例、HumanTestSession 和轮次，任一变化均不得沿用旧授权。普通可变开发预览绑定开发工作区、环境实例与用途，按 D03 第 2.1 节展示实际运行修订；其体验反馈只能作为问题线索，不能用开发预览授权冒充固定候选的人测授权。

固定访问流程如下：

1. 管理端在当前认证会话下申请访问。服务端重新核验实际用户、项目与实例归属、当前访问权限、策略和环境/授权期限；固定候选/人测访问同时核验候选、InputSet、人测会话及轮次，可变开发预览核验工作区与用途。同一授权申请重投不新建第二份授权或延长期限；无权的资源标识不能用于领取票据。
2. 服务端签发短期单次票据，票据期限不超过授权及环境实例的有效期限，经受保护的响应或平台控制的客户端通道交付。通知、待办和打开浏览器的链接仅传递无授权能力的资源标识；收到链接的客户端仍须完成当前认证和申请。票据不进入 URL、剪贴板、模型上下文、项目页面或通知正文。
3. 平台控制的兑换端点从受保护请求体接收票据，校验目标 origin、当前授权、用户绑定、候选/轮次、实例、期限及撤销状态。兑换页面、路径与响应由平台独占，不能由项目路由、脚本或 Service Worker 接收票据；受信任交付端与兑换端的请求来源及 CSRF 约束在 P0 冻结。兑换处理和响应禁止缓存，日志与诊断不采集秘密请求体或认证响应。
4. 在同一短事务内，以票据尚未使用及当前 `authorization_revision` 为条件，原子提交票据消费、唯一兑换记录与专用会话；与撤销及授权修订互斥，不能先创建会话再异步标记票据已用。该会话只允许原授权绑定的环境实例，不将票据或平台会话凭据交给生成的应用。事务成功但响应尚未送达时发生撤销，返回的会话也必须被当前访问检查拒绝。
5. 客户端丢弃票据，后续仅以专用会话访问无秘密 URL。代理在每次新请求及升级握手前核验当前授权与固定上游，登记 SSE、WebSocket、HMR 及其他流式连接的会话、实例、授权修订、代理身份和到期边界；不能先放行长连接再补登记。撤销、到期或环境结束按第 4.4 节拒绝新访问并关闭已有连接。
6. 重建生成新的环境实例和访问授权。旧链接只能作为资源查询入口重新鉴权，旧票据、会话、已缓存页面和自动重连均不能恢复旧权限或取得新实例权限；新候选必须重新绑定人测轮次与授权。

若使用 Cookie 承载专用会话，首版采用实例独立主机上的 host-only Cookie，不设置 Domain，并要求 Secure、HttpOnly 和 `Path=/`；可使用符合这些约束的 `__Host-` 前缀。SameSite 的具体值由 P0 针对所声明的浏览器、外部浏览器与 Tauri/WebView 交付路线分别验证后冻结，不能为跨站跳转成功而无审查地放宽。会话期限不得超过原授权/环境期限，访问或重试不滚动续期。代理移除平台 Cookie、平台 Authorization 及相关内部头后才转发项目请求，并过滤项目上游对平台保留 Cookie 名称和认证头的覆盖；项目自身获准的业务 Cookie 与平台凭据分开处理。

并发与丢失响应使用以下确定行为：

|情形|服务端与客户端行为|
|---|---|
|多个请求同时兑换同一票据|只有一个事务能消费票据并创建会话，其余拒绝；不签发等价的新票据或第二个会话，不延长任何期限。|
|兑换事务失败或未提交|不产生会话或已消费状态；在原票据仍有效且当前授权仍成立时可重试，由同一原子条件决定是否成功。|
|兑换已经提交，但响应或 Set-Cookie 丢失|票据保持已消费。重投不补发 Cookie、不返回会话凭据，也不重新创建权限；客户端只可用已经收到的专用 Cookie 查询原会话是否可用。没有可用 Cookie 时回到管理端，显式申请重新授权。|
|为丢失响应重新授权|先撤销本次申请关联的旧授权、未消费票据与可能存在的会话，并按第 4.4 节确认旧访问关闭，再创建新授权/票据。重新授权单独审计，不能作为兑换重试静默延长原授权。|
|错误或状态查询|未经当前鉴权的调用只获得不泄漏资源、用户或会话信息的拒绝结果；持有非秘密 `redemption_id` 或资源 ID 不能恢复凭据。管理端在当前权限范围内可查询原申请/兑换状态，查询不授予访问权。|

浏览器从可信管理页面 POST 兑换后跳转到无秘密 URL 是候选交付方式，尚未证明适用于所有客户端。外部浏览器不能仅靠系统“打开链接”传票据，应在该浏览器完成管理端认证和受保护交付；独立 WebView 必须验证交付期间与项目内容之间的隔离。P0 分别记录浏览器、外部浏览器和实际 Tauri/WebView 的可实施方案，P2 取得实际证据。未验证路线不启用，不以 URL 票据作为降级方案。

### 4.3 原始端口与旁路入口

预览前端、后端及受支持的 HMR/流式入口，只能经当前授权的预览入口访问。原始服务端口仅对获准代理及必要的环境内部组件开放；项目配置、开发服务器和构建脚本不能另行发布绕过授权的宿主端口、直接地址或替代入口。代理转发目标来自已授权实例的固定映射，不接受项目或请求方任意指定上游。

P0 固定获准访问方、服务/协议/端口及启用地址族清单；新增前后端端口、HMR、WebSocket 或流式服务必须先纳入同一入口和撤销规则，再允许对外使用。Runner 负责限制端口发布和网络可达范围，代理负责当前访问授权，二者不能互相代替。必要的环境内部访问也须有明确组件与网络范围，不能以“内部网络”为由放行其他沙箱。

P2 从实际外部客户端、声明无权的网络位置及另一个沙箱访问原始前后端、HMR 和流式端口，分别记录成功拒绝或不可达的网络证据，并验证获准入口能完成相应交互。清单覆盖实际启用的 IPv4/IPv6、全部服务端口及代理之外的可达地址；未启用的地址族记录禁用依据。只有反向代理配置、禁用 host 网络、绑定回环地址或容器已经退出，均不能单独证明旁路已经封闭。

### 4.4 撤销生效、连接关闭与代理确认

本节细化既有“终止已经建立的连接”要求的执行和证据，不将仅拒绝新握手视为撤销完成。环境暂停、回收、到期或用户权限撤销均进入相同关闭协议；反馈提交仍在服务端事务内检查当前权限及人测轮次，不等待网络连接关闭后才拒绝过期或撤权反馈。

|阶段|必须成立的事实与记录|
|---|---|
|撤销意图提交|Hub 在事务内记录 `revoke_requested_at`、原因和新的 `authorization_revision`，禁止新签发、兑换及后续访问授权，并固定必须确认的可服务代理集合与连接范围。事务提交仅证明撤销已请求，状态显示“撤销待确认”。|
|各代理执行|每个代理按授权修订关闭相应路由，拒绝新请求/升级握手，终止已登记的客户端及上游连接，并清理会话可用状态。先封闭新连接入场再遍历已有连接，防止关闭过程插入未登记连接；过期或旧修订消息不能重新开启路由。|
|逐一确认|代理返回身份、启动代次、已应用的授权修订、拒绝新访问的时刻、连接关闭完成时刻及范围内剩余连接数。只有入口已拒绝且相关连接为零才可确认；确认重投只合并同一事实，不能代替另一代理。|
|实际生效|全部仍可能服务该授权的代理均确认关闭，或失联代理已取得可靠的网络/运行隔离及连接终止证据后，才记录 `revoke_effective_at`。新增/替换代理也必须先同步当前撤销状态再加入服务集合，不能利用集合快照遗漏恢复入口。|
|逾期或结果未知|记录未确认代理、未关连接、截止时间及原因，持续显示“撤销待确认/超时”，保持禁止新授权并执行已授权的隔离处置。Hub 写库、撤销消息已发送、健康检查失败、DNS 已移除或会话 Cookie 已删除均不能单独证明现有连接已关闭。|

P0 必须冻结两个有限参数及其计时起点：从 `revoke_requested_at` 到所有相关入口拒绝且已有连接关闭的最大时限 `preview_revoke_timeout`，以及代理无法证明控制通道仍有效时的最大检测间隔 `preview_control_max_gap`。为每次撤销持久记录相应截止时间，控制失联检测加连接清理必须落在撤销关闭上限内；P2 逐代理测量实际耗时并覆盖达到边界、超时和确认丢失。参数必须明确到具体数值且有失败行为，未冻结数值或没有证据不能通过 P2；它们不能被无限重试重置。

代理无法取得当前授权时拒绝所有新访问和兑换；控制通道断开、校验失败或超过 `preview_control_max_gap` 时关闭相关已有长连接，不用最后一次允许记录继续放行。代理重启先处于拒绝服务状态，重新核对当前 Hub、授权修订、实例、路由和撤销记录后才能接流量；持久化会话、旧连接恢复信息或旧路由配置不能自行恢复访问。失联后仅等待会话自然到期不满足关闭协议，代理断电/进程退出也需外部可达性和连接终止证据才能代替确认。

v4.7 区分撤销请求与实际生效，不以 Hub 已保存意图宣称“立即不可访问”。若所选代理、通道或检测机制只能保证有界延迟，P0 必须显式评审并记录对第 7.1 节“立即不可访问”承诺的修订，冻结可接受上限、界面状态和验收标准；未经该决定，不能把有限超时参数当作已接受的延迟承诺。P2 既要验证生效后拒绝新连接，也要保留从请求到生效期间已有 SSE/WebSocket/其他流式连接真正终止的证据；断线及重建后旧页面的重连不得重新授予权限。

## 5. 数据、事件与 API 契约

PostgreSQL 保存当前业务状态、执行索引、EventLog、Audit、Outbox 和 DBOS 系统记录。light 采用同一数据库：业务 schema 由领域服务与 Alembic 管理，dbos schema 由 SDK 支持的初始化/迁移流程管理；权限、连接池和保留策略分别配置，禁止手写 SQL 修改 DBOS 内部状态来推进流程。事务入队由 D02 规定。

大文件、截图、报告及长工具输出进入受控制品存储；遥测使用有界聚合或可选专业后端，不逐采样写业务事件。DBOS 工作流查询与执行轨迹用于诊断，不能成为另一套业务权威数据库。

|资源|主要 API 范围|
|---|---|
|项目与任务|/api/projects、/api/tasks、工作项和 pause/resume/cancel 命令|
|协作|会话、messages、decisions、AgentSession inbox、ContextPackage 与请求记录|
|开发与集成|workspaces、sandboxes、previews、integrations、merge-queue、verifications、reviews|
|交付与运维|release-candidates、releases、deployments、remote-targets、environments、operations、incidents、observations、drifts|
|授权与同步|auth、role-bindings、approvals、snapshot、events|

P0 冻结核心不变量、Runtime/执行映射、首条链路路径、权限及错误语义；完整 API 按 P1～P5 所属领域逐步冻结并生成契约。写命令支持幂等键和必要的 expected_version；响应返回业务资源及异步操作位置。冲突、过期计划、资源不足、权限不足和结果未知分别编码，不统一变为普通服务器错误。

schema_version 管理 API/事件/执行协议兼容，软件版本独立管理。不兼容时拒绝新变更并显示升级要求；设计文档版本不参与网络协议协商。

## 6. 快照与事件流无缺口恢复

业务事务写 Outbox。分发器读取已提交 Outbox，在独立短事务中锁定持久流计数器，分配递增游标、保存 DispatchEvent 并标记该 Outbox 已分发；全部同事务提交。轻量模式单分发者，未来多分发者也必须保持这一提交顺序约束。

可用 DBOS 定时触发有界分发批次，长定时等待使用独立维护容量而非占满 control，但 EventLog/Outbox/DispatchEvent 仍由 sync 模块维护，保留既有提交顺序与去重。DBOS 通知、工作流流式输出和内部历史不直接作为 Desktop 的业务事件游标；模型 token 可走短期展示通道，正式工程状态仍通过本节事件协议恢复。

不能使用业务表自增 ID 直接推断提交顺序。DispatchEvent 游标只表示分发顺序，事件同时携带 aggregate_id、aggregate_version、event_id、schema_version 和授权范围。

snapshot 在同一个一致性读取视图中读取已提交分发游标 C 与授权业务状态，返回状态、版本、删除墓碑和 C。客户端随后接收游标大于 C 的事件；快照里已包含但尚未分发的变化可能再次出现，以聚合版本去重，允许重复但不丢变化。

删除墓碑防止迟到的创建/更新事件复活已删除资源。墓碑只在相关 Outbox 全部分发且相关事件已早于可接受重放窗口后清理；资源 ID 不复用。大快照分页使用同一已冻结快照标识，不能逐页读取不同时间的状态；快照生成和保留有大小及期限限制。

游标过期返回重建指令。Hub 从旧备份恢复后使用新的流身份，旧客户端游标强制重新建立快照，不能把新流数字当作旧流的延续。

订阅、补发和快照均按当前权限检查。权限变化使相关订阅关闭并触发缓存范围重建；在线客户端清理撤销范围，离线客户端在下一次连接时处理。不能承诺服务端立即抹除已离线设备上曾获授权的数据，客户端缓存仍需本地保护和保留策略。

## 7. Desktop 产品行为

主要视图包括项目、需求、团队职责与依赖、代码 diff、验证报告、预览、部署及 Incident。默认展示目标、关键决策、阻塞、交付和费用；执行尝试、输入引用和原始输出在详情中可追溯。

用户补充需求产生版本与 D01 适用性影响分析；Run 结束、Session 等待、工具已接收、物理执行完成与 WorkItem 验收分别显示。人工接管展示等待写入者停止、已接管和交还核对；预览展示实际运行修订及过期状态。暂停和取消显示执行器确认进度。审批页展示起始环境、目标制品、环境配置修订、数据库影响、停机与补偿范围。

部署页区分期望版本、每服务实际版本、观测时间和历史操作结果。等待资源、等待回复、waiting_authorization、本机维护和执行未知有不同恢复提示；Hub 未连通时不伪造已知本机最新状态。本机应急需管理员在目标入口操作，Desktop 可在同步后展示事实与交还状态，不提供绕过本机认证的快捷按钮。不得要求用户手工编辑内部租约或数据库状态。

Desktop SQLite 仅保存草稿、界面设置、可重建缓存及游标，权威状态在 Hub。文件上传下载经授权 API，桌面端不安装或运行项目工具链。

### 7.1 人工测试交付与访问

Desktop 提供“临时部署并交给人类测试”的可选操作，展示被测版本、自动检查结果、测试环境状态、建议测试步骤、有效期与资源占用。指定具有项目/候选访问权限的人类测试者，通过待办交付；启用通知渠道时使用持久 Outbox 和授权范围内的最小通知。通知发送、入口打开和自动探测成功只表示交付进度，不能自动提交人工结论。

测试入口沿用[第 4.2 节](#42-访问授权票据交付与原子兑换)的身份绑定、受保护票据交付与原子兑换规则，以及第 4.1、4.3 节的管理会话、原生能力和旁路隔离要求。人测额外绑定 HumanTestSession、测试轮次、候选/InputSet、环境实例及当前用户。测试账号只访问隔离数据，通过受保护页面领取或短期登录交换；秘密保护遵循第 3 节，反馈附件沿用上传授权、大小限制与敏感信息处理。

反馈页提供“通过”“需要修改”“跳过”，显示实际被测版本与范围；提交时校验人类身份、当前权限、session/输入版本及会话是否仍可接受结论。过期或被替代的页面不能对新版本提交通过。结果可追溯到测试者和时间，Agent 整理反馈不能冒充人类确认。“跳过”明确标为未执行或未完成人工验证，不能显示绿色通过；正式部署仍独立审查和审批。

环境暂停、回收、到期或权限撤销时，访问关闭、已有连接处理、逐代理确认及有界延迟承诺统一遵循[第 4.4 节](#44-撤销生效连接关闭与代理确认)。按 D03 核对运行资源并保留已提交反馈。测试者可申请恢复/重建或显式跳过；关闭 Desktop、离线、未点击按钮都不是默认同意。该流程在 P2 随 Agent 交付链实现，平台验收需分别覆盖开启和不执行两条路径，不能把功能可选解释为实现可缺失。

产品必须对访问状态给出可解释反馈：DNS、TLS 或信任链不满足时显示具体原因；票据过期时提供重新授权入口；权限撤销时阻止新访问和反馈提交，并显示已有连接的关闭确认状态；环境回收时显示“已回收”，并仅向有权限者提供重建入口。超时、失联、环境故障或尚未收到人工反馈均保持未完成，不能推定通过或跳过。

人测的资源排队、环境就绪、活动、空闲回收、硬到期、续期和让出规则以 D03 第 2.3.1 节为准，本文件不复制其时间或资源参数。回收不自动删除已完成的人测结论、反馈及适用证据；重建须产生新的环境实例/授权并继续绑定原候选与对应测试轮次，旧票据、会话和页面不得随重建复活；更换候选须重新绑定轮次及授权。P2 的六类最低出口见第 4.1 节；P6 完成 Windows、Linux、实际 WebView、安装升级和断线场景的最终支持矩阵。

## 8. 观测、漂移与 Incident

Remote Agent 上报服务标识、镜像身份、非敏感配置摘要、secret 版本标识、健康、最近 Operation、执行代次和观测序号，分别保存 observed_at、received_at 和来源。按代次及序号处理迟到数据，不按到达顺序覆盖新状态。

基础观测通过容器、日志与网络探测完成。业务应用可以提供 /health、/ready、/metrics、优雅退出及受鉴权诊断接口，具体地址和探测方式写入运行契约；不强制业务引入 CloudHelm SDK 或共用平台数据库。诊断查询同时限制目标地址、权限和输出，避免成为访问任意内网服务的通道。

DesiredState 由 delivery 管理；ObservedState 和 DriftRecord 不修改历史 Release。默认报告漂移，恢复批准版本或接受外部变更均须走受控流程。无法验证来源的外部镜像不直接作为可信回滚版本。

管理通道离线显示最后观测及未知状态，独立 HTTP 探测另行呈现。重连先同步实际状态、未完成操作和代次，再处理仍有效的请求；过期请求不得作用于已经变化的容器。

日志在目标端轮转，初始查询上限为 500 行、1MiB，并限制时间窗、并发和尾随期限。需保留的证据脱敏后进入制品存储。默认每 30 秒采样，1 分钟聚合保留 24 小时、5 分钟聚合保留 7 天，实际参数依容量修订。

指标限制集合、标签基数、全局行数和字节配额；接近上限时降采样并标记缺口。仅状态变化与 Incident 进入业务事件，原始采样不进入 EventLog。需要长期数据时接入 Prometheus/Loki 等 adapter，查询仍返回来源和数据窗口。

告警按分组、持续时间、去重、静默、冷却和恢复规则创建/更新 Incident。运维 Agent 使用有界证据提出假设；固定只读诊断可自动执行，有副作用操作执行获批有限步骤 runbook，沿用执行账本及当前授权。业务恢复、通知和修复基线按下列规则处理，不以 runbook 成功或 Task 完成直接关闭 Incident。

ProbePolicyRevision 固定环境/服务、关键接口或用户路径、探测位置、成功断言、超时、频率、连续失败/恢复阈值与观察窗口。容器检查、目标内部业务探测和外部入口探测分别保存来源与时间，管理通道失联只说明观测能力下降。探测默认只读且有资源/请求配额；确需业务写入的合成探测须明确授权、隔离测试身份、数据范围和清理，不任意调用生产动作。

Hub 至少配置一条不依赖 Hub 自身进程/数据库的外部存活检查及通知路径，可复用成熟外部监控服务或独立探测节点。未配置时明确“控制面故障通知未覆盖”，不能把同机心跳脚本声称为独立监测。目标端和外部探测的视角、权限、保留及费用进入安装清单与容量记录。

### 8.1 通知、确认与恢复判定

Incident 保存严重程度、责任人、业务影响、首次/最近证据及当前探测政策。NotificationPolicyRevision 明确渠道、接收范围、确认期限、重试上限、升级对象及静默范围。创建/变化事件与通知 Outbox 同事务提交；发送由有界 DBOS 流程处理，使用稳定通知身份去重，渠道调用及失败都有记录。通知正文最小化，链接须重新鉴权，不发送秘密或整份敏感日志。

通知状态区分待发送、渠道已接收、失败/未知和人工已确认；渠道 HTTP 成功不表示人员已读。发送回执丢失先按渠道能力查询，无法确认时允许有界重发并保留潜在重复说明；人工确认按通知/Incident 身份幂等。超出发送或确认期限按政策升级，渠道全部失败保留故障，不将其自动关闭。Desktop 退出不终止通知流程。

处置成功后进入业务观察，只有所需探测在固定窗口内持续达标、证据新鲜且没有相关未解故障才转为 resolved；采集缺口或管理失联不能当作恢复。人工确认或政策规定的关闭条件满足后才 closed。窗口内复发回到调查/处置阶段，关闭后复发按关联 Incident 记录；历史部署、Task 与 runbook 结果不被改写。

### 8.2 从 Incident 到紧急修复

修复 Task 固定 incident_id、EnvironmentBinding、观测时间、实际服务向量、数据库/配置版本、关联证据、修复验收要求与来源基线。实际状态完整对应 Release 时从该 Release 的精确源码/构建输入建立修复分支；主分支未发布功能不自动进入修复。部分部署或手工漂移时先核对真实向量，创建有来源的修复候选/输入集合，不能强贴单个 Release 标签。

紧急级别和 EmergencyBudget 按 D03 第 4.1 节授权，Agent 只能申请，不能自行提升。普通构建占用或预算耗尽时显示实际阻塞与获准选择；不强杀迁移，不绕过物理占用或验收。修复仍使用正式验收、制品证据、Release 和部署计划，目标在修复期间发生变化须重新核对基线。

修复 Task 的显式目标分支可以是基于线上版本的维护分支，仍经项目级合并队列按精确 SHA 验证；不能为合入主分支顺带发布未验收功能。创建向主分支同步的关联工作项并跟踪冲突/验收。修复代码完成、上线、业务恢复和主分支同步分别记录；原故障只按第 8.1 节业务条件 resolved，不等待无关工作也不提前伪造恢复。

## 9. 备份与旧控制面恢复

备份覆盖同一数据库中的业务与 DBOS 系统 schema、权威仓库或必要镜像、制品索引与必要内容、凭据恢复安排，以及恢复所需的版本记录。业务状态、WorkflowBinding、队列、消息和检查点使用一致性数据库备份，不分别截取不同时间的导出。备份清单同时记录 PydanticAI/DBOS 版本、系统 schema、工作流应用版本和可恢复代码/镜像；包括 Session 历史、WaitCondition、推进去重记录、InputSet/证据引用及远端计划关联，不能只备份活跃工作流。

数据库与文件内容通过备份清单引用一致版本；暂缺的制品明确标记不可用，不把索引存在当作内容存在。普通 worker 重启与恢复旧备份采用不同入口，不能把恢复旧数据库视为一次普通 DBOS.launch。

恢复流程：

1. 隔离或停止旧控制面写入，新 Hub 以 recovery 模式启动；不调用 DBOS.launch，不启动 DBOS worker 的出队、自动重放或定时新变更，仅开放受控恢复管理接口。
2. 校验业务与 DBOS schema 的一致性、SDK/工作流代码兼容、制品引用和凭据可用性，生成新的控制实例身份；不能仅从旧数据库计数器继续分配代次。
3. 通过获授权的恢复流程与各执行器建立新 incarnation 的信任，执行器持久保存并拒绝旧 incarnation 新命令；先读取并保留目标本机维护门禁，建立新信任不自动解除应急接管。
4. 按 D02 核对旧进程、本地账本、实际服务、数据库版本和资源占用；旧 incarnation 的既有进程仍须确认结束或纳入接管。
5. 将恢复的 WorkflowBinding、DBOS 未完成流程/检查点、Session/WaitCondition、推进去重记录、Outbox 与远端事实逐项对照，包括本机恢复计划、实际变更和待交还记录。通过领域恢复命令补录实际操作，未知操作保持核对；不手工伪造 DBOS step 成功，也不批量重放旧队列或发送过期通知。
6. 建立新的有效环境状态与流身份，逐项登记流程允许恢复的范围，重新评估待执行计划、审批、凭据及应用版本。已结束 Run 的待决条件只在重新获准后产生新的续接，旧步骤许可不随数据库恢复重新生效。确认新门禁对每个副作用步骤生效后，才启动 DBOS 并允许已核对流程推进；其余流程保持业务阻塞，不能靠 DBOS 自动重放重新获得许可。

恢复授权不能由旧数据库里一条“恢复成功”记录自行证明。需验证目标身份和恢复操作者，旧实例隔离、凭据轮换及目标确认形成审计证据；随机生成一个 incarnation 字符串不足以建立信任。

Remote Agent 丢失本地账本时以新执行器身份重新接入，禁止报告所有旧操作均未执行。若维护/应急记录无法还原，普通变更与应急能力均保持禁用，先核对实际资源并重新建立可信身份和授权；不能仅从旧备份复活应急权限。离线目标保持受限状态，不妨碍已部署业务继续运行；不能为了让 Hub 显示正常而停止业务。

### 9.1 分级备份、恢复目标与演练

|保护范围|责任与备份内容|恢复边界|
|---|---|---|
|Hub|平台管理员；一致性业务/DBOS 数据库、权威 Git、制品及内容清单、兼容代码、凭据恢复安排|整机丢失按本节 recovery 流程，恢复前不自动推进|
|单项目业务|项目数据责任人；业务数据库、上传文件/对象、卷及应用所需一致性标记|隔离恢复并验证后，经获批计划替换明确目标；不回滚整个 Hub|
|执行器|目标管理员；本地账本、维护/交还记录、资源归属和身份恢复安排|材料缺失以新身份核对，旧备份不证明远端未执行|

BackupPolicy 固定责任人、范围、频率、保留、异机/外部存储位置、加密与密钥恢复方式，以及 RPO（最大可接受数据丢失窗口）和 RTO（目标恢复时限）。参数须在启用保护前由责任人确认，以实际恢复演练测量；无成功备份、长期未演练或超出目标时显示未保护/受限，不用“备份任务成功”代替恢复能力。4 核 8GB 基线不包含外部备份容量，报告分别核算。

复用 PostgreSQL 原生一致性备份/WAL 或成熟备份工具，以及支持版本清单的文件备份工具。数据库与业务文件需要共同的一致性点或应用规定的维护/停止写入窗口；普通复制运行中数据库文件不视为有效备份。外部备份凭据与解密材料按第 3 节管理，校验日志只保存引用。

单项目误删先恢复到隔离数据库/目录，核对数据完整性、关联对象和 schema，再生成带备份恢复点、当前目标基线、停写范围及失败策略的恢复计划。替换前确认目标无冲突操作，结束后检查业务并保留原数据的受控恢复引用；数据恢复可能丢失恢复点之后的合法写入，必须在审批中明确。此流程不使用本机应急初始有限动作绕过数据库恢复审批。

演练覆盖 Hub 丢失、单项目误删、账本丢失和备份材料缺失，记录实际恢复点、耗时、人工步骤、未恢复内容与远端核对结果。通知责任人并修订未达标措施；不为文档变更重复执行整套恢复实验。

## 10. 升级、卸载与验证

Desktop、Hub、Runner、Remote Agent、业务项目分别升级，安装记录包含兼容矩阵。Hub 同时记录 PydanticAI、DBOS SDK、DBOS 系统 schema、业务 schema、消息格式、工具包和工作流 application_version。业务 Alembic 与 SDK 系统迁移分别执行，启动前校验兼容；不能假定回退 Python 包即可回退数据库或已记录的工作流步骤。升级期间按 D02 处理未完成流程和实际操作。

默认不部署 Conductor。未来引入时，核验其部署/许可条件、认证、可见数据、远程管理权限及失联恢复，纳入备份和容量清单；不把可选管理服务失联直接判为业务服务故障。

卸载单个业务项目只作用于绑定资源，默认保留需恢复的数据卷与记录，不删除 Hub、Remote Agent 或共享审计。清除实际凭据材料需结合仍在运行的服务及回滚策略处理。

### 10.1 平台自身开发、诊断与隔离回放

提供版本化开发启动配置，固定 API、单 worker、PostgreSQL、测试 Runner 和示例目标的启动顺序与兼容依赖。开发环境使用独立数据库、制品路径、身份和网络范围，启动时校验环境标记；不得默认连接生产执行器或导入生产凭据。配置样例只列字段与注入方式，读取和诊断不得显形输出密钥。

应用代码热重载与持久工作流恢复分开：API 开发重载不能启动第二个 worker；改变工作流步骤/消息格式时使用经验证的兼容补丁，或明确停止并重建专用开发数据，不能热加载新代码后盲目重放旧检查点。开发重建工具校验专用环境和目标目录，不作用于受管生产数据。

按 command_id、Task、Run、ModelRequestRecord、Operation 和 workflow_id 聚合有界诊断信息，包括版本、输入引用、状态、关联错误和资源占用；权限检查后导出脱敏诊断包。默认不导出完整模型历史、仓库、秘密或可复用认证材料。日志、trace 属性和异常同样过滤，索引存在不代表内容可分享。

回放区分只读轨迹查看与隔离行为复现。后者使用记录过的脱敏模型/工具结果、隔离数据库和 fake/test adapters，固定时钟及必要输入，禁止接入真实目标和生产凭据；它只能证明该输入下的行为，不代替真实集成验收。需要真实执行时创建正常获授权的业务意图并走 Gateway、预算和执行协议，不能借回放复用旧许可绕过门禁。

### 10.2 可重复升级流程

1. 固定待升级的软件、SDK、schema、工作流、消息和执行协议兼容矩阵，检查所有目标/Runner 能力并生成升级记录；应急模式使用中时禁止对相关执行器直接升级。
2. 停止新业务准入，保留控制、结果接收和核对能力，盘点队列、Session 等待、物理操作与维护门禁。可兼容流程按明确政策保留；不可兼容流程在安全边界完成或授权处理，未知操作不清空。
3. 取得一致性备份与可恢复代码/制品，核验恢复材料和已演练路径；关键材料不足不开始破坏性迁移。
4. 分别执行受支持的业务迁移和 DBOS 系统迁移，在关闭自动恢复的启动模式校验兼容性；单 worker 旧实例退出后才启动新实例。
5. 验证只读查询、事务命令、入队与受限恢复、执行器通信及授权门禁，再逐步恢复获准业务准入；旧流程不兼容时保持 waiting_upgrade。
6. 失败时区分软件回退、向前修复与数据恢复。数据库/工作流已产生不兼容变化时不得仅降级包；需要旧数据恢复时转入本节 recovery 流程并核对远端已发生影响。保留结果和未恢复范围，不以安装成功代表升级成功。

安装、升级、诊断和恢复提供可执行入口及用户说明，能力和失败提示与协议保持一致。P0/P1 建立隔离开发及诊断基础，P2/P3 验证工具续接和人工交接，P4 完成本机应急、旧备份、升级与撤权竞争，P5 交付通知/修复闭环，P6 汇总安装及恢复验收。实际结果在交付记录维护，不写成已通过的设计事实。
