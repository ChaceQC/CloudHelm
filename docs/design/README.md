## 2. 版本规则

1. 总体设计使用 `vM.N`，配套专题使用 `vM.N.P`；前两位必须相同。当前总体设计为 `v4.7`，各专题的修订组合见下表。
2. 同一总体基线内，专题澄清、补充与修订递增第三位；可以独立递增，但同时更新下方清单和依赖兼容说明。
3. 改变三端边界、状态所有权、安全不变量或交付语义时，显式评审总体版本，不以第三位隐藏不兼容变更。
4. 总体版本变化后，各专题完成核对才迁移到新前两位，初始修订号为 0；旧文档归档，不自动批量改号假定兼容。
5. 版本写入页首，专题文件名稳定。文档版本与软件、PydanticAI/DBOS SDK、数据库、工作流应用及执行协议版本分别管理。

|文档|当前版本|对齐总体|
|---|---|---|
|本索引、D03|v4.7.1|v4.7|
|D01、D02、D04～D06|v4.7.0|v4.7|

D03 v4.7.1 澄清费用按供应商 usage 与版本化官方模型价格计算，保留计算金额、账单金额和未知占账的区别。该澄清不改变三端边界、状态所有权或执行协议；旧记录不自动获得新费用证据，缺少适用字段时仍为 unknown/null。

所有文件以 UTF-8 保存。读取配置及排障不得显形输出密钥；文档仅使用字段名、用途和资源标识，不包含实际凭据。

## 3. 文档维护

修改设计规则时，同步更新负责文档、受影响引用、验收要求和版本清单。实现进度及实际验收结果在交付记录中维护，设计正文说明系统结构、行为和约束。

本版沿用 v4.5 的架构及 P0～P6 划分，在 v4.6 参照规格上闭合资源、完成和预览协议，并细化接缝、时间、实验与估算证据。旧记录必须逐项核对，不能自动认定新要求通过。各领域业务工作流与规则一起维护，公共 workflow 层仅承载引擎接入、身份映射和恢复门禁。协议初值、SDK 锁定、支持矩阵和实际估算在对应阶段的记录中确认，未决项同时记录影响范围和解决决定。

### 4.1 继承的容量基线

Ops Hub 维持 4 核 8GB 的规划基线；同机 light 与独立 Runner 两档使用同一 Hub 基线，独立执行节点另外配置。既有 GB 容量标签按 D03 第 4.2 节的 GiB/MiB 契约统一解释：常驻平台 2GiB、系统/缓存 1GiB、突发余量 1GiB、开发执行共享上限 4GiB（4096MiB），开发执行 CPU 总配额初始不超过 3000m（3 vCPU）。实际准入以预算和扣除必要保留后的实测容量较小值为限。

模型真实请求上限 3、活跃开发 Task 上限 2、重执行上限 1、按需预览上限 1；数量上限不承诺同时满额运行。紧急任务改变获准排队顺序，不增加物理并发，也不借应急预算释放未知费用。D03/D06 记录实际容量与支持范围，设计参数不表示验收通过。

### 4.2 继承的 v4.5.1 可选沙箱人类测试

针对 AI 生成代码补充可选的实际操作测试，默认关闭，由用户按任务/候选选择。开启后在 Hub 开发沙箱或获准独立 Runner 临时运行固定版本，提供入口和测试说明，记录人类结论与反馈；未开启、明确跳过、未反馈和通过分别表示。问题反馈进入返工，新版本重新测试，临时环境按期限及资源策略清理。

前版在 v4.5 总体边界和正常部署审批内增加可选人测，默认未启用，专题当时采用 v4.5.1 与 D02 v4.5.0 的组合。v4.6 继续保持按任务/候选选择，并补充资源时间、撤销和阶段证据。新增会话/状态及控制字段在实现时单独协商 API/schema 兼容，旧客户端不得将未知状态显示为通过；文档修订不表示临时环境已部署或人类已验收。
