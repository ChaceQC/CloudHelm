## 1. 发布对象与项目契约

ReleaseCandidate 固定项目最终集成提交、验证证据及构建输入引用。BuildRun 和必要自动检查通过后，领域服务校验来源、摘要、运行验证和策略；用户未开启人工测试时按原流程创建不可变 Release，开启时先进入 human_test_pending，按 D03 第 2.3 节完成临时部署与人类测试。只有有效人类通过记录或有权用户明确跳过才解除该等待；自动检查失败仍阻止发布，不能用人工通过/跳过覆盖。失败保留原候选和构建记录，不用新产物覆盖原 Release。

发布工作流及部署提交、授权、查询和核对工作流由 delivery 定义并由 DBOS 执行，delivery 保留业务结果所有权。Remote Agent 是完整部署计划的唯一物理步骤推进者，Hub 只接收账本事实并判定业务结果，不另建逐步下发循环。WorkflowBinding 关联固定业务对象和推进修订；恢复使用原 BuildRun/Operation 查询既有结果。引擎的 SUCCESS 不独自构成 Release 或 Deployment 成功证据。

### 1.1 字段唯一来源

|来源|权威内容|引用方式|
|---|---|---|
|Compose 受支持子集|service key、镜像/构建声明、启动命令、网络、卷、端口、健康、重启及资源，以及允许参数化的位置|版本化源文件及解析输入，运行字段只在此处定义|
|ProjectDescriptor 薄扩展|构建目标选择、验收入口、迁移顺序/兼容条件、配置 schema、证据和发布政策|通过稳定 service key 和工程引用关联，不重复声明 Compose 运行字段|
|EnvironmentConfigRevision|实际环境参数、受控资源绑定、不可变 secret 版本引用|独立配置修订；不等于包含 Release 期望的 EnvironmentRevision，不从临时 shell 隐式取值|
|Release Manifest|固定制品、可参数化运行契约、配置 schema、迁移及适用证据|环境无关或明确标注构建变体适用范围的派生快照，不独立修改或反向充当源|
|DeploymentPlan|Release、环境配置修订、起始状态、解析器版本及最终规范化部署规格|环境绑定结果，审批后不可变；实际秘密只保留引用|

Compose 与薄扩展各自选定唯一权威位置，可在仓库或平台版本化存储；来源变更显式迁移。配置 schema 标记敏感字段但不含值。迁移的应用命令在固定制品内执行，薄扩展说明何时执行及安全条件，不开放任意宿主脚本。

### 1.2 支持子集与两阶段解析

首条链路支持单目标、多服务、项目内网络、受管命名卷、环境配置引用、服务健康与固定镜像。源码 build 可供 Hub 受限构建使用，最终目标配置必须替换为已验证制品；目标禁止 build，归档模式禁止自动 pull。

特权容器、Docker socket、设备直通、任意宿主 bind mount、host 网络和未经批准的外部共享资源默认拒绝。include/extends、复杂 profiles、外部文件与插值能力在 P0/P1 形成逐项兼容表；未支持的能力拒绝并指出位置，不能静默忽略。获准例外也须在同一解析与策略入口验证。

第一阶段形成 Release：

1. 固定 Compose/薄扩展源版本、文件集合、构建参数、CLI/解析器版本；显式区分构建时值、运行时参数和 secret 引用。
2. 在受限解析环境核验支持子集、唯一字段来源、service key、路径、资源政策及参数 schema。使用 Compose 标准解析能力和经过核验的受限参数映射；缺失变量不能静默变为空值，不从 Hub 环境或越界文件继承输入。
3. 固定可参数化运行契约及允许绑定的位置、类型、范围，构建并核对最终镜像身份，按固定测试配置生成制品证据，形成 Release Manifest。测试配置是证据输入，不自动成为生产默认值。

第二阶段形成 DeploymentPlan：

4. 将固定 Release 与一个 EnvironmentConfigRevision 绑定，校验参数、资源、secret 引用、目标能力和当前策略，生成最终规范化部署规格及摘要。
5. 最终规格不得新增未获准服务、替换镜像身份或改变未声明可变的拓扑/命令；改变这些内容须形成新的契约/Release。参数展开后重新执行安全检查，不能借变量绕过挂载、网络或资源限制。
6. 绑定起始环境和实际状态，补做环境配置、迁移前提及目标检查，形成并批准计划。执行器只消费该计划的固定结果，不重新解析工作区源码或操作者环境。

两个阶段分别保存有界、去秘密值的来源、解析输入引用、解析器版本、诊断和摘要。secret 只保存版本引用；必要敏感解析在受控临时内存/运行材料中进行，持久输出及审批正文还原为引用。Compose 标准化不等于安全校验。P0/P1 核验参数映射、外部文件读取、插值和秘密展开；无法支持的参数化明确拒绝，不用占位值生成假定可部署的最终规格。

现有 Compose 导入返回差异与兼容报告，由用户确认无法无损映射的配置。工具不支持无损环境分离时明确限定适用环境；不得由模型在每次发布时重新推断。

### 1.3 工程引用与 Release 准入

Compose、薄扩展、构建 InputSet、镜像、验收资产及验证报告统一使用 D01 工程引用。delivery 创建 Release 前检查制品及来源证据的当前适用性，包括该候选已选人工测试的结论或显式跳过记录；计划阶段另检查对应环境证据，分析未完成或来源缺失保持待复核。迁移旧 Descriptor/环境已绑定 Release 必须显式拆分并产生新修订，不能用批量改版本号假定语义等价。

已有不可变 Release 也可按用户选择发起同样的沙箱人工测试，记录作为外部关联证据，不回写 Manifest。若用户选择将该测试作为本次部署前检查，DeploymentPlan 的创建/执行须确认适用结论或显式跳过；记录测试通过不签发生产步骤许可。未开启不增加等待，关闭已经选择的测试必须走显式跳过命令，不能静默删除未解决反馈。跨环境复用仅限仍适用的测试范围，沙箱测试不证明生产配置与数据条件正确。

部署前选择的人工测试及被测输入引用随 DeploymentPlan 固定，批准后变更选择或输入须重制计划并重新审批；人类提交测试结论只更新关联证据，不修改计划正文。自动检查、目标前提和正常授权仍需独立满足，显式跳过仅解除这项可选等待。

## 2. 完整 Release Manifest

|内容|固定引用|
|---|---|
|source|权威仓库、精确 commit、构建输入摘要、BuildRun、工具链与执行提供方|
|services|稳定 service key、OS/架构、各平台不可变制品身份|
|runtime|固定运行契约、配置 schema、允许参数化的位置与约束、端口/卷/资源/依赖/健康/重启规则；不混入目标环境实际值|
|migrations|迁移制品、顺序、适用数据库版本、兼容条件及恢复限制|
|verification|源码证据、正式验收修订、制品扫描、最终镜像运行验证、测试配置及审查引用|
|descriptor|Compose 源/参数化契约、ProjectDescriptor 薄扩展修订、解析器版本及规范化摘要|
|variant_scope|构建时参数、OS/架构等变体身份与限制；不得把编译进产物的环境差异当作运行时可切换参数|

只变更一个服务也产生完整新 Release，未变服务沿用已核验的不可变制品。数据库等第三方依赖固定镜像身份并声明数据卷要求；固定镜像不意味着允许自动升级或回退数据目录格式。

Release 可以部署到多个符合契约的环境，每个环境绑定独立推进。同制品晋升保持镜像身份，复用仍适用的源码/制品证据，并补做目标环境配置、数据库前提和业务探测；不要求把无关检查全部重跑。编译期前端地址等变化会产生新的 BuildRun、制品和 Release/构建变体，须重新验证，不能声称仍是同一镜像晋升。首条验收采用单目标；多目标分别保存计划与结果，不宣称跨目标原子切换。

## 3. Registry 与归档交付

|模式|传输与启动|身份验证|
|---|---|---|
|Registry|目标按获准 digest 拉取|记录 index/platform digest，核对目标架构与容器实际镜像|
|归档|受限 HTTPS 下载，完整校验后 load，使用 Release/服务专属本地标签启动|先校验 archive SHA-256，再校验 image ID/config digest、OS 和架构|

归档摘要、image config digest 和 Registry manifest digest 含义不同，字段不得混用；docker load 后没有 RepoDigests 不应误判为可跳过身份核对。

归档模式禁止 Compose 自动 pull/build，执行前将专属标签核对至获准 image ID，启动后再核对容器实际 image ID。受管变更在目标执行锁内进行；管理员手工改写标签作为漂移处理。

下载授权绑定目标与 Release，支持断点续传、临时文件、限速、超时和过期清理。续传清单仍绑定同一内容摘要；完整校验前不得 load。预检计算归档、镜像加载及临时解包的并存空间。

## 4. 环境绑定、命名空间与资源占用

Environment 表达项目内逻辑环境；EnvironmentBinding 关联 project_id、environment_id、target_id、installation_id，是单目标部署与执行锁的基本范围。同一项目的 test 与 prod 即使使用同一机器也必须有不同绑定。

Compose project、目录、网络、卷和服务标签由稳定安装标识生成，保存到绑定记录；用户可见名称不直接作为全局资源键。重命名项目不改变资源归属。重新安装与接管已有资源需显式绑定，不能仅凭名字相同就接管。

端口、显式共享网络和外部卷建立目标主机级资源声明。Remote Agent 在本地主机资源锁内核对持久占用记录及实际系统状态，再登记使用者。卸载只释放自身资源；共享卷必须显式允许共享，不能默认共享。

外部管理员可能绕过平台修改资源，因此预检成功不能保证后续端口绑定必然成功；运行失败仍按部分更新记录，不自动清除其他项目资源来“修复”。

## 5. DeploymentPlan 与起始基线

计划内容规范化后生成 plan_digest，批准后不可原地更改。至少包含：

|分组|必要信息|
|---|---|
|目标|Release/Manifest 摘要、EnvironmentBinding、目标平台、获准服务制品|
|起始状态|expected_environment_revision、起始 Release 或明确的首次安装标记、必要的实际服务向量、配置版本及数据库前置条件|
|运行输入|Release 参数化契约、EnvironmentConfigRevision、最终规范化部署规格及解析器版本、不可变 secret 引用版本、网络及卷资源声明|
|执行|有限类型的具名步骤、顺序、固定输入摘要、前后置条件、停机范围、迁移、健康窗口、开始期限/最大时长及资源需求|
|失败处理|允许的补偿、准确目标版本、数据库兼容条件、何时进入人工核对|
|授权|所需策略、批准对象、有效期限、逐步骤启动许可要求、安全停止点和失联行为|

起始状态只包含影响执行安全的字段；心跳时间、瞬时 CPU 和日志数量不进入审批摘要。允许变化的字段必须显式列出，不能使用“无重大变化”作为无法判定的规则。

首次安装需证明绑定内不存在未登记的运行资源；缺少历史 Release 不代表目标一定为空。实际观察过期或结果未知时，先刷新和核对，不直接审批执行。

## 6. 审批与执行前条件更新

个人项目默认自动开发、验证、审查和构建，所有者可批准自己提出的部署。团队或重要环境可以要求独立审查及禁止自批；Agent 永远不代表人类批准，项目设置不能弱化环境强制策略。

构建前批准仅在项目策略要求时启用，绑定仓库、提交、构建输入及证据。部署批准绑定 plan_digest、目标、配置和 secret 版本、审批身份及策略版本。执行前重新检查当前策略与凭据状态；内容变化重新生成计划和批准。

审批待决只保存 DeploymentPlan、Approval 和业务等待条件，不占常驻 DBOS 编排工作流。批准事务按稳定身份更新业务状态、创建 WorkflowBinding 并入队部署提交流程。通知只携带批准记录引用；提交时重新读取 plan_digest、身份、当前策略和期限，不能只凭一条消息执行。

计划获批后，业务记录、WorkflowBinding 与 DBOS 入队按 D02 同事务提交。取得绑定执行权后，Hub 通过 expected_environment_revision 条件更新登记 active_deployment；Remote Agent 接收完整计划和原 Operation，取得本地锁并核对实际状态、操作代次和前置条件。队列分区只能辅助串行化，不能替代绑定执行权与目标本地锁。Hub 事务与远端变更不是分布式事务，崩溃窗口按 D02 查询和恢复。

若 A→B 和 A→C 均已获批，B 完成后，C 不能继续使用基于 A 的迁移和补偿。基线不匹配产生明确的 replan_required 原因；生成替代 DeploymentPlan 并重新审批，旧计划和批准保留历史。

## 7. 期望状态的提交时机

EnvironmentRevision 为递增的期望状态修订，保存 Release、EnvironmentConfigRevision 及批准证据。新增配置修订或生成计划本身不改变当前期望；预检通过、准备开始首次普通副作用前，以条件更新创建新的期望修订并登记执行操作。该命令按 Deployment/Operation 身份去重，避免检查点丢失时重复递增。本机应急期间先在本地保存实际恢复事实，重连后按第 8.5 节显式核对登记新的期望修订，不伪造过去已经存在的 Hub 批准。

如果此时控制面崩溃，期望可能已经推进而目标未改动，恢复查询 Operation 后继续验证或记录失败，不以旧观测立即判断业务已失败。active_deployment 在实际执行未知时不能直接释放。

已批准的失败补偿恢复旧版本时，登记新的期望修订，引用原计划的补偿批准及执行证据；不把修订号倒退，不把原更新改为成功。失败且无法补偿时保留目标期望、实际混合状态及失败原因，默认不自动反复趋近目标。

人工决定接受部分状态或外部变更时，需形成新计划或可追溯的受管配置/版本记录。不能将混合服务状态直接贴上某个未经验证 Release 的标签。

## 8. 完整计划执行、许可与健康检查

### 8.1 Hub 与 Remote Agent 的分工

Hub 负责编制和批准不可变计划、提交固定计划及 Operation、签发当前步骤启动许可、接收事实、核对和计算 Deployment 业务结果。Remote Agent 负责唯一的步骤推进、本地锁、账本、实际进程及后置检查。完整计划重投按 operation_id + plan_digest 去重；本地已有计划时查询原执行，不另起执行循环。

首版 PlanStep 限于制品准备、运行输入检查、迁移、服务更新、健康验证和已批准补偿等类型，使用稳定 step_id、类型版本、input_digest、前后置条件、时限、取消方式和失败分支。执行器报告支持的类型/版本；遇到未知类型拒绝整计划，不按未知字段猜测执行。步骤包含固定制品和参数引用，不接受任意宿主 shell、模型临时插入步骤或无限自定义循环。

计划规定前序失败时停止或进入已批准补偿；受控执行器按记录推进有限步骤，不承担平台通用队列、跨任务调度或 DBOS 重放。物理步骤事实由 Remote Agent 账本产生，Hub 的 StepExecution 为回报投影，不能反向伪造执行器成功。数据库变更仍以数据库自身账本为必要证据。

### 8.2 步骤启动许可

普通受管计划的每个新变更步骤在线请求一次短期启动许可。请求携带 Operation/计划/步骤/输入摘要、executor 实例、资源代次、前序结果引用及当前实际状态。Hub 经当前策略、暂停/取消、恢复门禁、计划有效期、secret 状态、资源及前置条件检查后返回受认证完整性保护的许可。本机应急必须通过第 8.5 节和 D05 的专门入口，不能让普通计划改一个标志就跳过在线许可。

许可绑定 grant_id、operation_id、plan_digest、step_id、input_digest、executor、hub_incarnation、generation、环境执行身份，以及第 8.2.1 节的时间域、时间纪元和有效期限；其唯一授权是当前具名步骤。Remote Agent 在本地锁内再次检查身份、代次、期限、维护门禁和实际前置条件，持久登记许可接受与步骤 intent 后才能启动。维护期间即使 Hub 签发更高 generation 的普通许可也不得开始。重投相同许可查询原步骤，不获得第二次执行权；许可失效后须先按第 8.2.1 节核对原步骤并可靠封闭旧启动路径，只有确认未启动才可重新取得当前许可。

初始前置条件使用计划起始环境版本；本次部署登记新 EnvironmentRevision 后，后续步骤校验 active_deployment、该执行修订、计划规定的中间状态及前序后置证据。不能每一步都要求仍处于首次安装前状态，也不能跳过外部漂移检查。Hub 对回报落后于当前请求的情况先核对，不只凭远端一条“上步完成”就签发许可。

已接受许可到进程启动存在受限窗口，撤权与远端接受不构成原子操作。许可期限和允许时钟偏差限制这一窗口；撤权后拒绝新许可并发出取消，执行器在获知撤权后拒绝尚未开始的动作。系统不能承诺离线即时撤销已接受动作。开始期限与最大执行时长分开，许可到期不意味着应强杀正在执行的迁移。

### 8.2.1 许可时间协议

启动许可同时携带 `issued_at`（Hub 签发时刻）和 `expires_at`（失效时刻）；有效期按 `expires_at - issued_at` 计算。首条链路暂以 30 秒作为待实测初值；P0 冻结初始值及测量判据，P1 实测后确认或调整正式值。两时间戳必须属于协议选定的同一 `time_domain` 和 `time_epoch`，这两项随许可一起接受认证完整性保护，不能只靠接收端配置猜测。`time_epoch` 标识一段连续且受支持的授权时基，与控制身份 `hub_incarnation`、资源 `generation` 分开管理；旧时基不能因数值相近而转换成新时基的许可。

首批候选是复用认证许可通道，建立执行器本地单调时钟到 **Hub 授权时间** 的相对映射。P0 必须选择并冻结一种时间域，不能把候选写成已验证能力：

|互斥选项|时间含义与必要证据|
|---|---|
|相对 Hub 授权时间，首批待验证候选|Hub 在每个 `time_epoch` 内使用已选定的连续单调时基签发许可和产生时间样本；执行器证明相对该时基的当前时间区间。它不声称真实 UTC 准确性，普通系统墙钟不参与许可判定|
|严格 UTC，仅在 P0 明确选用时启用|Hub 与执行器须提供对应时源的绝对误差依据，并覆盖采样、保持、跳变及失源条件；许可时间区间须包含这些误差。普通 NTP 的“已同步”状态或近期偏差测量不能单独证明严格误差上界|

相同许可协议版本及一次执行只使用冻结的选项；不支持该时间域的执行器拒绝许可，不自动回退到另一个分支。P0 同时冻结时钟 API、样本格式与认证绑定、误差计算和依据、漂移与最大样本龄、失效检测、时间纪元更新及支持的操作系统/虚拟化组合；P1 才在实际 Hub—Remote Agent 链路取得证据。未能证明所需误差上界或失效检测能力的组合，禁用普通新步骤入口，不把一次测量通过当成对任意硬件和运行条件的保证。

计时职责按下表分开，不能混用：

|时钟或记录|职责|
|---|---|
|所选授权时基|定义 `issued_at`、`expires_at` 与可信时间样本。相对分支由 Hub 单调时基定义；UTC 分支须另有绝对误差证明|
|执行器本地单调时钟|记录请求发出/收到样本、样本年龄、首次接受至实际启动的间隔，并在本地锁内复核；记录对应进程/主机时钟连续性身份，不能跨重启直接比较旧读数|
|普通系统墙钟|用于展示、日志关联和人工审计，并标明来源；不能替代单调间隔，也不能凭校时成功直接为许可授信。选择 UTC 分支时，只有纳入误差证明的 UTC 读数才可进入授权计算|

相对 Hub 时间候选按以下方式形成保守误差区间；P0 应在决定记录中固定实际采用的公式、证据和不适用条件：

1. 执行器在单调读数 `m0` 发出带唯一随机请求标识的采样请求，在 `m1` 收到受认证响应。Hub 的样本 `H_s` 必须采自该次请求处理期间；响应绑定请求标识、Hub/执行器身份、`time_domain` 和 `time_epoch`。历史响应或重投响应不能伪装成刚取得的新样本。
2. 以 `e_s` 覆盖 Hub 取样位置、时钟读取/精度及编码误差；将完整实测往返区间按已证明的时钟区间误差和相对速率上界转换为授权时基上的 `r_bound`，其中须覆盖执行器两端采样误差及途中等待。收到响应时采用保守区间 `[L0, U0] = [H_s-e_s, H_s+e_s+r_bound]`。这里使用整个往返上界，不假定两个方向延迟对称；即使把区间中点记作估计时间，也不意味着已经证明单程延迟等于往返的一半。
3. 以 `m1` 为锚点，把后续单调间隔换算为授权时基单位的名义经过时间 `Δm`，并把换算误差 `e_elapsed(Δm)` 和随样本老化累积的相对漂移上界 `d_age(Δm)` 加入区间：`L = L0 + Δm - e_elapsed - d_age`，`U = U0 + Δm + e_elapsed + d_age`。漂移边界及其适用条件须有依据，不能从一次短采样推定；超过冻结的最大样本龄、观察到跳变或不能计算上界时，映射失信。采样、往返、换算和老化的各项来源及计算结果均保存为可核对的时间证据。
4. 取 `T = (L+U)/2`、`u = (U-L)/2`，在接受许可和实际启动前分别重算并核验。只有 `u <= 2 秒`，且整个 `[T-u, T+u]` 位于 `[issued_at, expires_at)` 内才允许，即 `T-u >= issued_at` 且 `T+u < expires_at`。`T+u == expires_at` 必须拒绝；不能证明 `u`、`u` 超限或时间域/纪元不匹配也必须拒绝。UTC 分支若被选用，须改用已冻结的绝对时间误差证据，不能继续套用相对分支而称为真实 UTC。

许可首次接受到实际启动的间隔由持续有效的本地单调时钟限制在最多 5 秒，间隔误差也须计入该上界。接受记录持久保存首次接受锚点及所属时基/映射；投递到本地队列不算实际启动。执行器在实际启动边界再次核验时间区间、首次接受间隔及当前门禁；不能证明仍在窗口内就拒绝启动。正常续采可信样本可以更新区间，不能重置首次接受锚点；重投同一 `grant_id` 只查询原结果，不重新接受或重开 5 秒窗口。

时基连续性和映射按下列规则失效：

|事件|失效与拒绝规则|
|---|---|
|Hub 授权时基所在进程/主机重启、休眠恢复、虚拟机暂停恢复，或时基来源/连续性改变|Hub 停止沿用旧时基签发，建立新 `time_epoch` 后重新提供样本；执行器获知变化后废弃旧映射，拒绝用旧纪元样本或许可重建启动权|
|执行器进程/主机重启、休眠恢复或虚拟机暂停恢复|本地映射和未启动许可的接受窗口失效；账本持久化不使旧单调读数、旧许可或旧接受窗口重新有效|
|任一端检测到回拨/跳变、单调时钟与授权时基关系丢失、样本超龄或误差上界不再成立|立即停止接受和启动新副作用，废弃受影响映射，并可靠封闭其尚未启动的旧许可；不能靠重新校墙钟消除失信记录|

休眠/暂停期间单调时钟是否继续推进、恢复事件能否在新步骤启动前可靠识别，都属于支持组合的待验证条件；无法覆盖这些条件就不启用该组合。Hub 侧变化到远端获知并非原子操作，对尚未获知变化的已接受动作仍只能承诺第 8.2 节的有界窗口，不能宣称离线即时撤销。

重新取得符合当前时间域、纪元和误差要求的样本后，先按 D02 核对原 `operation_id + step_id` 的执行账本、实际进程和必要的数据库证据。已开始的步骤只核对原结果或按既定安全边界收束；结果未知继续 `needs_reconciliation` 并保留冲突锁和占用。只有证明原步骤未启动，且在本地启动锁下持久封闭全部旧许可启动路径后，才可申请新的 `grant_id`，保持原 `operation_id` 与 `step_id` 并重新检查当前授权。重新可信、新纪元、重新连接或重投都不能复活失效的旧许可，也不能给它重新开启启动窗口。

许可撤权后不得签发新许可。失信、过期或收到撤权都不证明已运行步骤已经停止，不能因此强杀已开始的迁移；这些步骤按既定安全边界收束并保留事实。已部署业务继续按其运行目标和重启策略运行。时间失败不自动授予本机应急权限，第 8.5 节的应急授权仍独立核验。许可有效期仅约束步骤开始，不等于步骤运行时长；每种 `PlanStep` 类型的最大运行时长仍须在 P0 单独冻结。未冻结支持边界的类型列入不支持清单，在执行器能力清单和计划编译诊断中记录类型及拒绝原因，并在计划编译前拒绝。

P1 的实际链路最低验收覆盖：`T+u == expires_at` 拒绝；许可仍未到期但接受至实际启动已超过 5 秒时拒绝；`u` 无法证明、超限或映射失信时拒绝；执行器重启/休眠/暂停后拒绝旧许可；Hub 重建纪元并重新协商后拒绝旧纪元许可与样本；恢复可信但原步骤未核清时不签发新启动权；确认未启动并封闭旧路径后仅新 `grant_id` 可获得当前授权。重复消息、正常续样和恢复操作都不得重开旧接受窗口。决定记录与证据归档见 D06，本文不把这些场景标为已验证。

许可身份与重投规则遵循 [D02 第 1.3、1.4、2 节](02-execution-recovery.md)，其中新身份摘要的权威定义见 D02 第 1.4 节；本节新增时间域和纪元须纳入许可 schema、摘要与能力协商后才启用。普通许可的动作权限和当前授权遵循 [D05 第 1.1、2.1 节](05-security-sync-operations.md)；D05 第 2.2 节规定的是独立本机应急授权来源，不替代普通许可。

### 8.3 失联与重新连接

|位置|默认行为|
|---|---|
|计划未接受或变更步骤未取得有效许可|等待连接和重新校验，不开始变更|
|步骤许可已接受、动作尚未开始|仍须满足第 8.2.1 节的可信时间和首次接受窗口；失效后封闭旧启动路径，核对未启动才可申请新许可|
|步骤许可已接受、动作已开始|仅按该步骤规则完成或收束到安全点，保留结果|
|即将开始普通后续变更/重试/补偿步骤|在线取得新的步骤许可；失联不凭历史批准继续|
|业务已经运行|保持运行，管理通道离线不改变容器运行目标|
|步骤实际结果未知|needs_reconciliation，保留冲突锁和占用，查询后再决定|

已知在等待授权的部署保留当前业务阶段并设置 waiting_authorization 原因，不伪装成失败或 unknown；真正无法确认影响时才进入 needs_reconciliation。只读查询和制品准备按计划能力、期限和限额执行，秘密材料访问仍遵循授权。重连先补报账本和实际状态，按第 8.2.1 节恢复可信时间并核对原步骤，再确认新的授权/代次后继续；不重新执行已完成步骤。

普通计划不开放离线自主推进后续变更。v4.5 另提供第 8.5 节的人类本机应急入口，它形成独立恢复意图、权限和记录，不沿用旧普通计划离线执行。应急未配置或未完成兼容验收时显示不可用；部署前检查 Hub/通道健康，并在计划中说明半部署状态可接受的等待窗口及人工恢复入口，超过窗口只告警和升级，不自动取得应急权限。

### 8.4 普通部署执行顺序

1. Remote Agent 接收完整计划，检查身份、策略、目标能力、执行代次、实际基线与本地账本。
2. 预拉取或下载全部制品并校验身份、架构与可用磁盘。
3. 检查配置、secret 版本、端口、卷、备份和数据库前提。
4. 确认 Hub 已登记期望修订与原 Operation；每个新变更步骤取得有效启动许可，按计划执行迁移和服务更新。
5. 每步保存结果与服务实际版本，验证就绪和关键业务探测。
6. Remote Agent 在获批健康窗口内达到成功标准后持久回报；Hub 核验事实并结束 Deployment，各端分别释放已确认解除的占用和绑定执行权。

健康参数包括启动超时、间隔、连续成功阈值和观察窗口。窗口内失败属于本次部署失败；窗口后出现异常创建 Incident，不覆写历史 succeeded。迟到证据采用追加更正记录。

Compose 依赖启动、重建和健康行为由受控执行器明确处理。定向更新时防止 Compose 隐式更新计划之外的服务；所用 flags、服务范围及版本需在 P0/P1 验证，不把一次 compose 命令视为天然的事务。

远端部署具名步骤仍由 Remote Agent 记录，不能以 DBOS step 的序号取代 step_id。每次普通新副作用、重试或补偿按本节取得当前步骤许可并核对环境及资源；本机应急按第 8.5 节逐步核验专门授权。已完成历史步骤可以复用事实证据，但先前缓存的“允许部署”不能证明当前仍有权限。健康观测携带观测时间和窗口，重放旧观测不能冒充当前就绪。

### 8.5 本机应急恢复与显式交还

本节规定恢复动作，授权来源、操作者身份及离线撤权窗口唯一归 D05 第 2.2 节。应急由已获准的本机管理员主动发起，使用 Remote Agent 本机受限入口；不接受 Agent 请求，也不由心跳超时自动触发。

1. 校验应急配置、管理员身份、范围及期限，在本地事务登记 maintenance_id、受影响绑定/共享资源、操作者、原 Operation 和维护门禁，阻止该范围新普通步骤。门禁在任何新进程启动前检查，旧许可已接受但未启动也不能绕过。
2. 按 D02 核对原进程、迁移账本、服务向量、配置与物理占用。门禁不自动停止旧步骤；未确认结束或到达允许接管的安全边界时保持核对，不执行冲突恢复。
3. 从本地已有、身份已验证的制品及当前状态生成固定 RecoveryPlan，列出范围、输入、前后置条件、影响、期限与失败处理。管理员确认 plan_digest 后，以新的关联 Operation 登记本机批准及步骤意图；不能复用旧批准扩大恢复范围。
4. Remote Agent 在相同资源锁和账本下逐步核验本机授权、门禁、计划、时限及实际状态，执行并验证结果。新恢复失败或结果未知时保留门禁和占用，不能反复重试。
5. 重连后先补报维护、原部署及恢复事实。Hub 暂停相关普通计划，核对制品、每服务版本、配置和数据库；通过领域命令记录原计划的真实结果，并登记经确认的新环境修订或明确混合状态。不得伪造 Hub 曾签发本机许可，也不把原失败改成成功。
6. 当前获授权 Hub 与本机管理员对相同 maintenance_id、恢复结果摘要和交还范围完成确认；先在 Hub 持久记录待交还决定，再由执行器在本地事务校验无未知冲突并更新受信任控制身份/资源代次、解除门禁，最后回报。回执丢失查询原交还记录，不重复解除或递增。Hub 在确认解除前不恢复该范围准入；旧计划必须重新核对或重制。

初始固定动作仅包括指定服务的受控重启，或恢复到已有且身份可信、与当前数据库及配置兼容的制品。保持当前配置/secret 版本，禁止应急入口任意运行宿主 shell、下载未知制品、改变授权、轮换凭据、回退数据库或执行任意迁移。缺少兼容证据、可用材料或本机授权时明确拒绝；更复杂数据恢复遵循独立批准的恢复流程，不冒充此模式已支持。

维护门禁覆盖绑定及所有冲突共享资源，其他无冲突环境可继续。Remote Agent/主机重启、授权到期、Hub 变更 incarnation 或恢复旧备份都不自动解除门禁；授权到期阻止新恢复步骤，当前动作按已声明安全边界收束。账本丢失按 D02/D05 以新执行器身份核对，不能宣称已恢复普通执行权。

## 9. 迁移、失败与补偿

### 9.1 首批交付项目迁移模式与结果查询契约

首批交付项目固定为 PostgreSQL 单库、线性 Alembic 修订链，只允许事务能力已声明、目标版本与迁移账本可核对的迁移。多头修订链、跨数据库迁移和特殊非事务步骤均不受支持，必须在计划编译前显式拒绝，不得降级为警告后继续。迁移计划说明适用数据库版本、事务能力、备份、兼容窗口和验证方式。旧应用与新 schema 的兼容性决定迁移在停机或服务更新前后执行，不统一规定所有迁移都先执行。

每个迁移步骤至少固定下列输入和安全边界：

|项目|契约内容|
|---|---|
|目标与制品|数据库实例 ID、迁移制品摘要、起始 revision、目标 revision|
|并发与事务|执行锁身份及冲突规则、明确声明的事务能力；事务能力与目标数据库实际记录必须一致|
|控制边界|步骤超时、取消请求的安全停止边界，以及运行中和结果未知时的处理方式|
|结果证据|数据库迁移账本查询、实际 revision、迁移后置检查及执行器物理步骤记录|
|业务兼容|旧应用与新 schema 的兼容条件、允许的补偿范围和所需人工恢复说明|

结果查询至少使用以下状态：

|状态|判定要求|
|---|---|
|`not_started`|完整且可信的执行账本和数据库证据共同表明迁移未开始；查无记录本身不足以成立|
|`running`|账本、执行锁及数据库可观察状态支持步骤仍在执行|
|`succeeded`|数据库 revision 达到目标，且迁移后置检查通过；执行器顶层回报及退出码只能作为辅助证据|
|`failed_known`|失败及已经发生的影响均能由账本、数据库状态和检查结果确定|
|`unknown`|无法确认实际影响，包括记录缺失且账本完整性无法证明|

回执丢失时，沿用原 `Operation` 查询执行器账本、数据库迁移账本和后置状态；不得仅凭回执缺失创建新 attempt 并盲目重放。只有确认未开始且重新核验授权、计划和执行边界后，才可依原 `operation_id + step_id` 判断是否允许新的实际尝试。取消只表示提出停止请求，不证明迁移失败，也不授予自动回退或补偿权限；是否已停止及已发生影响仍须查询并记录。

### 9.2 三类迁移边界与计划变更

平台与交付项目分别维护迁移支持契约，不因使用相同数据库或 Alembic 而合并其支持范围：

|迁移边界|版本与执行范围|备份/恢复与结果证据|
|---|---|---|
|Hub 业务 Alembic|由 Hub 业务版本和已支持 schema revision 矩阵管理|按 Hub 业务数据库的备份恢复流程处理，以业务 schema revision、完整性检查及领域探测证明结果|
|DBOS 系统 schema / SDK 升级|由 DBOS SDK、系统 schema 和工作流 application version 的兼容组合管理，使用 DBOS 支持的升级流程|按 DBOS 系统 schema 的备份恢复与恢复门禁处理，以系统 schema 版本、DBOS 支持的升级结果和工作流恢复核对作为证据|
|交付项目声明的迁移模式|只按该项目 Manifest / ProjectDescriptor 声明且平台明确支持的迁移模式执行|按目标业务数据库声明的备份恢复方法，以项目迁移账本、实际 revision、后置检查及兼容性证据判定结果|

上述三类分别在 P0 冻结受支持版本、备份恢复要求、终态证据及账本完整性判据；首批交付项目还须冻结迁移执行锁、事务能力集合、步骤超时与取消边界、旧应用兼容条件及后置检查项。Hub 使用 Alembic 不代表任意生成项目的迁移都受支持。DeploymentPlan 内容或其固定输入（项目配置、迁移制品摘要、计划冻结的起始数据库状态）发生变化时，必须重新解析并生成计划、重新审批后才能执行。Task 取消不隐含 Deployment 停机；需要停止部署时须对原 `Operation` 明确发出取消请求，并按步骤安全边界等待停止或进入结果核对。

P1 提供首批迁移模式和许可协议的最小证据，包括身份、第 8.2.1 节选定时间域/纪元、认证样本及误差计算、`issued_at`/`expires_at` 边界、首次接受到实际启动的单调时间间隔、失信与重启后拒绝旧许可，以及数据库账本查询、revision 与后置检查；P4 扩展回执丢失、取消竞争、执行锁冲突、部分失败和人工恢复等故障证据。

### 9.3 部署失败与补偿

|情形|处置|
|---|---|
|首次副作用前预检失败|不更新服务，记录原因，释放已确认无执行的预留|
|部分服务更新失败|停止后续更新，保存每服务实际身份及 partially_applied 结果|
|步骤超时但影响未知|进入 needs_reconciliation，查询实际状态，保持冲突资源阻塞|
|补偿已批准且当前仍适用|按具名步骤执行，保留原失败，登记补偿结果与新期望修订|
|迁移不可逆或兼容性不满足|停止自动回退，按维护窗口、向前修复或人工恢复处理|

镜像可回退不代表数据库可回退。备份文件存在不代表可恢复；在部署前要求备份时应核对对应数据库、时间与恢复证据。迁移成功但回执丢失时依据数据库迁移账本核对，不能仅因本地步骤未完成就重跑。

用户单独发起的回滚是新的 Deployment 和审批，原计划内的失败补偿是原 Operation 的获批子步骤。两者都必须检查当前配置、secret 撤销状态和数据库兼容性。

DBOS 取消 Hub 主流程后，查询和停止确认由独立受控的 control 工作流继续推进；Remote Agent 执行获准的安全停止或计划内补偿，补偿步骤仍须获得当前许可。不得依赖被取消流程必然执行清理，也不能通过通用 rewind/fork 重新发送迁移或回滚命令。部署结果未知时保留 active_deployment 和物理预留，按 D02 核对后才允许释放。

## 10. standalone 与离线重启

从同一 Manifest 导出固定制品、参数化 Compose 模板、配置 schema、迁移与恢复说明；可直接运行的导出结果还须绑定明确 EnvironmentConfigRevision，并使用与受管计划相同的最终解析及策略检查。模板缺少必需输入时不能标为可运行包。归档包包含镜像及加载校验步骤；Registry 包明确独立可访问地址和权限。实际 secret 通过单独受控通道交付，不写入可分享归档；本机应急身份材料不随业务包分发。

业务容器明确 restart 策略，目标 Docker 服务配置开机启动，必要配置与受限凭据材料安全保留在目标。业务启动路径不需要先联系 Hub 或调用 CloudHelm SDK。DBOS 仅存在于 Hub 控制面，交付项目和 Remote Agent 无需连接 DBOS 系统数据库，也不依赖 Conductor。

重启策略仅保证进程重新启动，不保证数据库就绪或业务可用；应用应具备受控重试和就绪检查。数据库迁移使用受管一次性步骤或明确幂等机制，不能在每次容器重启时无条件重跑未知迁移。

P1 验证已知项目的完整计划、基本失联、步骤许可和独立交付，P2 接入 Agent 制品，P4 扩大迁移、部分失败、撤权竞争和恢复覆盖。独立交付验收包括 Hub 离线、目标及 Remote Agent 重启、独立重新安装和保留业务卷的单项目卸载，验收要求见 D06。
