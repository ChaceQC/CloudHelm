## 1. 权威仓库与项目接入

Project 必须指定唯一权威 Git 来源、目标分支和访问策略，来源可为受管 bare repository 或外部 Git 远端。镜像与开发副本不能成为第二套隐式权威。

light 新建项目默认由受信任 Git 服务创建受管 bare repository，支持平台内审查、项目级合并和源码导出，不要求安装 Gitea。bare repository 受项目授权与备份策略保护，不直接暴露匿名文件访问。

已有项目接入时登记外部权威远端、目标分支、认证引用及访问能力。凭据仅交给 Git 服务。无推送权限时明确显示只读接入，不能把本地分支更新显示为已经合入外部仓库。

权威来源迁移需冻结写入、同步并校验 refs、更新来源版本、恢复写入；失败保持原权威，不自动双向镜像。webhook 只作通知，周期 fetch 补偿漏报。

接入检查包括锁文件、Dockerfile、Compose、构建命令、目标架构、配置 schema、迁移与健康接口，并识别 Git LFS、submodule、依赖 Git 元数据的版本生成等需求。无法支持的项目返回具体限制，不能把文件占位内容当作完整源码。

## 2. 工作文件与 Git 元数据

WorkItem 从精确 base_commit 创建独立 worktree，Task 有集成分支，项目有目标分支。Workspace 保存 repo、commit、owner、工作文件位置、执行模式、配额、状态和保留策略。

默认由 Runner 构造不含共享 .git 指针及目录的工作文件视图，沙箱只操作该视图。受信任 Git 服务提供限定的 status、diff、commit 和候选提交工具，验证归属、路径与参数。

Git 服务禁用仓库 hooks、外部 diff、textconv 和过滤器等不受信任执行配置，使用受控环境与参数调用，不将仓库提供的命令拼接成宿主 shell。路径授权在解析符号链接后核对边界，并防止检查后路径被替换。

提交与构建输入采集前，停止或冻结该工作区全部写入者，包括测试服务、watcher 和后台子进程；无法冻结则创建不可变文件快照。文件采集与提交期间不能恢复写入。

需要完整 Git 的项目明确选择隔离 clone，Git 在沙箱权限下运行，不共享可写元数据，不注入长期推送凭据。LFS/submodule 等获取由受控接入流程完成；禁用过滤器的默认模式不能静默承诺兼容所有仓库。

缓存以只读共享或由受控服务写入为主。不得让不可信沙箱共同写同一个依赖目录；缓存来源、键及失效边界应可追踪，避免跨项目污染。

## 3. 沙箱与构建执行器

开发沙箱使用 Docker，限制 CPU、内存、PID、用户、挂载、执行时间和网络出口。执行器检查宿主实际支持的资源限制；磁盘配额能力不足时明确限制支持范围，不能把逻辑计数当作硬隔离。

沙箱无控制面数据库、宿主 Docker socket 和远端部署凭据。Runner 的宿主控制接口仅允许已注册操作，不接受任意挂载、特权参数或宿主 shell。

按需镜像构建优先验证受限 rootless BuildKit 方案，宿主 Runner 管理生命周期，构建输入经受控接口提交。具体内核、cgroup、存储驱动及网络兼容性在 P1/P2 核验后固定；不支持时停止构建或使用已配置的独立受限 Runner，不偷偷向沙箱开放宿主 socket。

构建容器、浏览器、扫描器和预览按需启动。基础镜像和工具链固定可追溯身份，扫描器数据库等可变化输入记录版本与时间。Docker 隔离不被视为任意恶意多租户的完整宿主安全保证。

私有依赖访问按用途提供短期凭据或受限代理，禁止把部署凭据复用到构建。仓库代码可能读取构建过程中可访问的凭据，因此必须先限制权限和出口，不能依赖日志脱敏独自防止泄露。

## 4. 资源预留与组合任务

模型调用、工作文件、执行进程、预览分别计量。初始建议上限为 3 个模型调用、2 个活跃开发 Task、1 个重执行槽和 1 个按需预览；最终准入以实际 CPU、内存、磁盘和进程需求为准。

ResourceReservation 至少保存 owner、资源组、请求量、硬上限、执行器、租约、状态和释放证据。reserved、active、releasing、orphaned、released 分开；租约失效将其送入核对，不能直接变成 released。

重执行包括依赖安装、编译、镜像构建、浏览器测试及全栈联调。轻量模式同时只准入一组重任务；不同任务公平排队，预算耗尽或超出机器能力时明确退出或等待用户决策。

集成测试采用组合资源组：被测服务、数据库、浏览器和测试命令一起计算总需求，组内子步骤消费父级预留，不再次申请唯一重任务槽。避免“服务占槽等待浏览器，浏览器等待服务释放”的死锁。

用户预览与测试环境分别标识。用户预览可按可见策略暂停或重建，运行测试的依赖环境不能被当作可随意回收的普通预览。测试资源超过总容量时排队或要求更大 Runner，不通过拆分预留隐藏并发峰值。

控制查询、取消、心跳和回报使用有界独立容量，不能排在长构建之后。CPU 和内存配额必须覆盖进程树；磁盘与网络 I/O 同样可能拖慢数据库，需要测量并在可用情况下限流。

## 5. light 容量预算

|项目|初始目标|验证要求|
|---|---|---|
|常驻平台|约 1～1.5GB|统计 API、worker、PostgreSQL、Runner、代理及其他实际进程|
|OS、文件缓存及突发|至少约 0.75GB|结合宿主可用内存和压力判断|
|开发执行|使用剩余受控容量|包含整个组合任务与构建执行器的峰值|
|Swap|只缓冲短时峰值|不计入正常可承诺容量|
|磁盘|按项目实测|包括源码、缓存、镜像层、归档、临时解包、日志和数据库|

4GB 指整台 Ops Hub，不含 Desktop 与交付机器。先支持代表性小型 Python/Node Web 项目，大型 Java、复杂前端和长浏览器套件需单独验证。OOM、磁盘不足和系统压力必须形成可理解的失败分类，不能无限提高上限重试。

## 6. 构建输入与验证证据

BuildRun 绑定不可变构建输入描述，至少包括源码 commit/快照、ProjectDescriptor 修订、构建步骤、工具链镜像、基础镜像解析结果、锁文件、目标平台和影响行为的构建参数。敏感参数只保存受控引用，不进入公开摘要输入。

同一 commit 采用不同参数、架构或外部描述文件时属于不同构建输入。复用产物须证明输入等价，不仅比较源码 SHA。不可固定的外部依赖应记录解析结果及限制，不能承诺未实现的可复现构建。

|证据|绑定对象|用途|
|---|---|---|
|源码测试与代码审查|精确 commit、验收版本、测试工具及环境|证明源代码层面的检查范围|
|构建与来源记录|输入摘要、执行提供方、工具链、构建结果|关联源码与制品来源|
|制品扫描与运行验证|镜像/制品身份、架构、运行契约、测试配置|证明实际交付对象通过指定检查|

构建完成后对最终镜像执行必要的启动、就绪及关键业务检查，再形成可供 Release 使用的证据。宿主受信任采集器计算制品摘要并记录构建来源，不直接信任仓库脚本自报的“通过”或制品身份。

外部 CI adapter 保存提供方 run 引用，重复触发和丢失回执按 D02 核对。CI 没有目标机器部署权限，不能自行越过 Release 和 DeploymentPlan 流程。

## 7. 集成与项目合并队列

任务内 IntegrationAttempt 固定候选提交集合，冲突反馈为明确返工。项目队列每次读取权威目标分支，生成精确合入候选，取得所需验证与审查，再以预期旧 SHA 条件更新。

分支变化时重新集成，并按证据适用范围决定重跑；不能沿用针对其他 SHA 的结论冒充验证通过。PR 合并如果重写 commit，必须验证其最终实际版本。外部提交会触发基线影响分析，但不自动 rebase 所有长期工作项。

共享文件可在调度层串行处理；实际文件访问仍由沙箱和路径授权保证。WorkItem 局部测试通过不等于项目集成通过。

## 8. 费用预留与未知 usage

每次模型请求前在并发事务中预留费用，按输入估算、最大输出和已知提供方计费项计算保守上界。未知缓存收益按普通输入计算，不能先假定命中以降低预留。

请求完成后按真实 usage 和对应价格版本结算；缺失字段保持 unknown。超时、连接中断或取消可能已经发生费用，不能立即释放全部预留并重试。

未知费用保留待核对预留，尝试获取提供方记录；无法核对时按已批准的保守计费规则占用预算并标记估算。超出可计算的最大费用或提供方语义不明时，设置更低并发、明确风险预算并限制重试，不声称严格预算保证。

缓存创建、读取、输出和压缩请求分别计入，避免同一 token 双计费。报告同时给出实际与估算费用、未知记录和统计覆盖率。Task 暂停后不得为缓存保温继续请求。

## 9. 保留、清理与交付

工作区清理前保留必要 commit、patch、报告和恢复引用。制品、镜像层、下载归档和缓存分别设配额；原始日志与大型工具输出不能无限写入数据库。

垃圾回收先计算当前运行、回滚候选、进行中操作、未完成任务和用户保留标记的引用集合，采用标记与延迟删除，在最终删除前重新确认引用。存在新引用或结果未知时跳过，不与部署下载争删文件。

磁盘预检包括归档、解包、docker load 和镜像层的并存峰值。制品落盘采用临时内容、完成校验和原子发布；未校验文件不进入可用索引。

P1/P2 核验仓库、构建边界及基本资源协议，P7 在真实 4 核 4GB 整机执行容量评估。验收要求见 D06。
