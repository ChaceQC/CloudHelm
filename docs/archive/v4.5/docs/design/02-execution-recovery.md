## 1. 责任与共用范围

持久工作流选用 DBOS Python。领域服务决定允许执行什么以及结果对业务意味着什么；平台编写 workflow/step，DBOS 承担队列、检查点、持久等待、定时、配置范围内的重试和重放；Gateway 校验当前授权、参数和审批；Executor 执行受限操作并保存事实。

|组件|接入方式|职责边界|
|---|---|---|
|hub-api|FastAPI + DBOSClient|鉴权、业务命令、事务入队及查询；不调用 DBOS.launch，不执行工作流|
|hub-worker|单个 DBOS 应用进程|加载平台工作流/步骤，消费队列并调用领域服务；不直接运行生成代码|
|PostgreSQL|同一数据库的业务 schema 与 dbos 系统 schema|保存业务权威状态和 DBOS 执行记录；同实例不同数据库不等于同一事务|
|Runner / Remote Agent|平台受控执行协议|维护真实进程、物理资源、本地账本及操作代次；不获得 Hub 数据库凭据|
|Conductor|默认不部署|未来多 worker 故障转移和管理的可选组件；采用前重新核验资源与安全|

业务 workflow 定义归 collaboration、agent-runtime、integration、delivery、operations 等所属领域，公共 workflow 层只管理 DBOS 接入、WorkflowBinding、版本注册及恢复门禁。hub-worker 是统一注册/执行入口，不把全部业务过程集中进公共 workflow 模块。

工作流、队列与步骤记录使用 DBOS 支持的接口管理。取消自研 WorkflowJob 领取、调度续租、通用超时扫描和检查点重放；平台仍编写业务编排和结果核对逻辑，不直接修改 DBOS 内部表驱动调度。增加远程 Runner 只是增加物理执行容量，不自动增加 DBOS worker 副本。

开发 Runner 与 Remote Agent 共用操作身份、步骤记录、查询、取消和代次规则，但使用独立能力集。Operation 用于外部副作用或需独立恢复的长任务；普通只读查询使用有界查询步骤，业务数据库变更使用幂等领域命令。不得借共用协议允许开发身份调用部署工具，也不要求所有工具都支持自动补偿。

API 在短事务内登记业务请求、事件及必要的 Outbox，按本节下述规则同时入队，提交后返回业务标识及异步状态位置。不在 HTTP 请求事务内等待长命令。内部工具可进程内调用，不要求全部包装成 MCP 服务。

### 1.1 事务入队与可靠交接

1. 由 D01 第 1.1 节应用命令处理器创建统一 UnitOfWork，在业务 schema 以调用者、资源和幂等键登记命令，比较规范化 request_digest；同键不同输入拒绝。
2. 所有参与领域服务使用该 UnitOfWork 的同一个 SQLAlchemy Connection/Session 短事务，写入业务状态、EventLog、必要 Outbox 和 WorkflowBinding；服务不得独立提交或在别的连接提前写入。
3. 调用 DBOSClient.enqueue_in_transaction，使用固定 workflow_name、application_name、workflow_id 和 queue_name。由调用者统一提交或回滚；回滚后业务记录与入队记录均不可见。
4. 事务提交后才能查询等待结果；不得在事务内等待 worker。异步 SQLAlchemy 入口使用经 SDK 核验的 run_sync 桥接方式，普通 enqueue_async 不自动加入已有业务事务。

此原子性只覆盖同一 PostgreSQL 数据库事务。业务表与 DBOS 表若未来拆为两个数据库，必须改用事务 Outbox 加稳定 Workflow ID 的交接，并修订本基线。Desktop 同步及其他外部投递仍需要 Outbox；同库消息、批准或结果处理可以在业务事务中直接入队下一次有界推进，跨事务/外部交接仍用 Outbox，不能因原子入队而全部删除。

DBOS 重复 Workflow ID 返回既有执行的行为不能替代请求摘要校验。WorkflowBinding 在事务中保存业务对象、流程类型、执行修订、application_name、workflow_id、request_digest 和代码版本关联，不维护 lease_until 或可独立推进的镜像调度状态。

### 1.2 启动与最小部署

DBOS 作为 Python 依赖进入 hub-worker，FastAPI 与 worker 可以同机独立进程部署，PostgreSQL 复用 Hub 数据库实例。工作流及步骤定义在 DBOS.launch 前加载；启动前核对 schema、应用版本及运行模式，launch 后注册受支持的队列并报告就绪。API 的 DBOSClient 生命周期由应用统一管理，不为每次请求创建连接池。

普通重启由 systemd 或容器服务管理器恢复单个 worker，并确认旧实例已经退出；不以自研第二套租约系统抢占 DBOS 流程。DBOS 自动恢复的适用前提是检查点完整、代码版本兼容且符合当前运行门禁。恢复旧数据库备份时禁止直接执行此普通启动路径，严格遵循 D05。

### 1.3 业务对象与执行身份映射

|对象|工作流映射|身份连续性|
|---|---|---|
|Task|长期目标，不强制对应单个常驻工作流|Task 身份贯穿多个业务过程|
|AgentSession|长期会话，历史和等待归业务状态|多个 Run 共享 Session，PydanticAI run_id 独立记录|
|AgentRun|一次有界工作流，模型请求可使用受限子工作流|崩溃恢复原 Run；等待结果续接创建新 Run|
|Operation|独立外部执行意图，可被提交回执及多个受控等待/恢复流程引用|重投、查询和接管沿用 operation_id；新的本机恢复意图创建关联 Operation，不覆盖原部署|
|Deployment|Hub 的提交、查询、授权和核对流程引用同一部署计划与 Operation|远端本地执行器唯一推进计划步骤，不由 Hub 工作流逐步驱动|
|WorkflowBinding|业务对象、过程类型、推进修订到具体 DBOS 工作流的映射|同业务对象可有多个历史绑定，不复制调度状态|

长期人工/依赖等待以 D01 的条件记录和可靠续接实现。部署待批准时只保存业务记录；批准事务创建部署提交工作流。远端执行期间，Hub 可用有期限的监督流程查询，超过单次观察窗口后保存待观察条件并通过 DBOS 定时/事件启动后续查询，沿用原 Operation，不能因监督流程结束而结束部署或释放物理资源。

DBOS 的短期接收、等待子流程和定时能力仍可用，须单独预算等待并发。由业务条件决定下一次是否可运行，由 DBOS 负责可靠执行和定时，不引入应用级通用任务领取器。

## 2. 操作、尝试与步骤

|对象|关键字段|含义|
|---|---|---|
|Operation|operation_id、idempotency_key、kind、request_digest、scope、target、authorization_ref、deadline、状态|一次不可变业务执行意图|
|ExecutionAttempt|attempt_id、operation_id、hub_incarnation、resource_generation、executor_id、开始/结束、结果|某执行器的一次执行或接管尝试|
|StepExecution|operation_id、step_id、input_digest、适用资源、状态、前置/后置证据、尝试引用|执行器账本产生的可核对具名步骤，Hub 保存回报投影|
|ProcessBinding|attempt_id、step_id、容器/进程组身份、启动标记、资源预留、最后查询|本地真实进程与持久记录的对应关系|

幂等键按调用者及业务资源确定作用域。同键同请求返回原 Operation；同键不同摘要拒绝。重投或接管沿用 operation_id；真正改变业务意图需新 Operation 并重新验证授权。

DBOS 身份与物理执行身份分开：workflow_id 标识一次平台流程，DBOS step 检查点标识该流程内的执行位置；operation_id / step_id 标识远端业务操作及具名步骤，attempt_id 标识真实执行尝试。DBOS step 的内部序号不能充当远端 step_id。普通重放沿用原 Operation 与尝试引用，只有核对后确需新的实际执行尝试才创建 ExecutionAttempt 和相应资源代次。Run 续接、工作流更换和框架新 tool-call ID 均不自动产生新的同义业务操作。

StepExecution 的唯一键为 operation_id + step_id；重试不生成一个无关联的新步骤绕过去重。不同执行尝试追加历史，不覆盖“已经成功”的证据。

## 3. 状态与结果

Operation 使用 queued、running、cancel_requested、needs_reconciliation、succeeded、failed、cancelled。部分服务更新属于 Deployment 的业务结果，底层 Operation 同时提供步骤向量及最终失败原因。

|步骤状态|语义|恢复行为|
|---|---|---|
|planned|尚无副作用意图落盘|校验后可执行|
|started|执行意图已持久化，副作用可能开始|先查询，不能当作未执行|
|succeeded|后置条件和结果已持久保存|复用结果，不重跑|
|failed|已确认失败及其已知影响|按该工具声明判断是否可重试|
|unknown|无法确认实际影响|核对或人工处理|
|cancelled|已确认未开始或已停止，并保存已发生影响|不表示撤销已有变更|
|skipped|因前置失败等明确原因未执行|记录原因，不伪造成功|

每种工具必须声明结果查询方式、重试类别、取消方式、超时、输出上限及补偿能力。D01 的 accepted 提交回执不增加 Operation 成功终态，也不保证物理资源已分配；只有最终执行证据可以供下游使用。部署计划步骤另声明启动许可和失联安全边界，本机应急计划遵守 D04/D05 的独立授权与维护门禁。查询不到记录只有在可信且完整的执行账本中才可解释为未执行；执行器记录丢失不满足这个条件。

## 4. 本地持久执行记录

Runner/Remote Agent 使用本地持久账本保存收到的操作、计划摘要、已接受的步骤启动许可、执行代次、步骤和结果；首版可使用 SQLite 事务与适当的同步持久性设置。本机维护门禁、应急授权使用及交还进度也须持久保存，重启不清除隔离。账本不与业务容器临时文件系统共生命周期，不保存模型上下文或实际密钥。

开始有副作用的步骤前先持久登记 intent，再启动命令并保存可查询的进程身份；执行后验证后置条件并持久记录结果，最后回报 Hub。记录 intent 与启动进程之间仍存在崩溃窗口，因此必须使用稳定的容器/进程组标识和实际状态查询，不能依靠这两次写入宣称 exactly-once。

数据库迁移先查询业务数据库的迁移账本与执行锁。事务性迁移尽量在同一数据库事务提交业务变更与迁移版本；非事务性迁移提供可核对的分步标记和人工恢复说明。Remote Agent 顶层成功标记不能替代数据库自身证据。

账本磁盘不足时拒绝启动新变更；不能先执行，再期望稍后补上记录。短期离线期间保留待上报结果，补报按操作和结果标识去重。

## 5. 租约、代次与接管

需区分三个概念：DBOS 管理工作流的领取与恢复归属；资源执行代次拒绝旧控制者的新命令；物理执行占用表示旧进程是否仍在修改资源。平台不复制 DBOS 内部调度租约。DBOS application_version、ConversationEpoch、hub_incarnation 与资源 generation 分别管理，不能相互替代。

执行命令携带已注册的 hub_incarnation 和目标资源的单调 generation。执行器仅接受当前获准的 incarnation，并持久保存每个资源已接受的 generation。相同代次仍须校验 operation_id 和请求摘要，不能被其他操作复用。

增加 generation 不能自动停止旧进程。执行器对同一冲突资源持有本地执行锁，新命令即使代次更高，也须先核对旧进程；仍在执行的迁移不能仅通过拒绝旧回执就变为可重入。

接管顺序：

1. 将业务 Operation 与资源登记为待核对，通过领域执行门禁停止该冲突资源的新启动；不手工伪造 DBOS 调度状态。
2. 查询执行器账本、进程组/容器及实际资源状态。
3. 已完成则补记结果；仍执行则继续观察，或在允许的安全点停止。
4. 确认停止后记录已发生影响及步骤边界，再判断剩余步骤是否允许继续。
5. 重新验证授权、期限和资源条件，为新的实际尝试分配代次；旧尝试结果只作为历史证据。

未确认旧占用解除前，ResourceReservation 为 orphaned/reconciling，不能被重新分配。Executor 无法联系时允许影响范围外的工作继续，对冲突资源保持阻塞。

本地锁解决受管执行之间的串行化，不能阻止外部管理员直接操作 Docker 或数据库；这类变化由前后置条件检查及漂移识别处理。本机应急接管必须先登记 D05 的维护门禁，再按上述顺序核对原操作；提高代次不能解除门禁或终止旧进程，Hub 重启、恢复备份和更换 incarnation 也不能绕过本机门禁。

## 6. 领取、投递与并发

DBOS 是唯一持久调度实现，API/领域服务通过 SDK 入队，worker 使用 SDK 消费；不另建应用级 SKIP LOCKED 任务轮询与重试器。DBOS 内部实现如何领取不构成平台依赖契约。

|队列|工作内容|初始限制与等待规则|
|---|---|---|
|orchestration|有界 Agent 推进、工程过程和部署提交/观察|有界并发；长期人工/依赖等待不留在本队列，短期内部等待仍计入预算|
|model-calls|一次模型调用及其结果登记|初始真实请求并发上限 3；框架/SDK 重试也经过准入，不包含外部工具或人工等待|
|heavy-execution|安装、构建、测试等组合执行|初始并发上限 1；同时通过 ResourceReservation 准入|
|control|取消、查询、核对、步骤许可及有界维护|保留独立容量；长定时等待使用单独维护容量，不能饿死许可和取消|
|maintenance|等待条件超时检查、补偿唤醒和历史维护|独立有界容量；优先由 DBOS 定时触发短批次，不为每个业务等待常驻一个流程|

父流程等待子任务时，不能与子任务竞争唯一重执行槽；组合任务由一个父级物理预留覆盖全部子进程。初期使用单 worker 并显式配置队列并发；增加 worker 前核验每 worker、全局及分区并发语义，不能将每进程上限误当集群总上限。队列限制只约束 DBOS 任务，不能证明已经启动的远端进程停止。

Outbox 分发允许重复，接收方先完成幂等登记再处理。正式消息和 WaitCondition 的业务判定及结束 Run 后续接归 D01；同库条件变化与后续入队使用同一事务。DBOS 定时/持久消息用于有界补偿检查和需要的短期协调，定时登记也必须可靠交接；不能为每条人工等待常驻一个 orchestration 工作流。工作流通知或完成回执不代替远端副作用证据。

PydanticAI 与 DBOS 的接入必须保留逐真实请求准入。P0 验证受限模型子任务或同等队列接口与官方集成的兼容；只给整个 AgentRun 限流不能证明模型请求并发和费用已受控。

同一环境的变更通过 D04 的环境绑定执行权串行；跨环境共享的主机资源单独管理。多个物理资源按固定资源键顺序申请，申请不到时释放未使用的预留并返回等待，避免循环持锁。单 worker 使用异步 I/O 管理模型和执行协议，阻塞库放入有界线程池或隔离执行，不能阻塞控制请求和 DBOS 运行循环。

紧急修复优先级与预算由 D03 第 4.1 节管理。P0/P1 核验选定 DBOS 版本的优先级及队列能力，优先级只影响获准任务的领取顺序；物理 ResourceReservation 仍为最终准入。不得用普通和紧急两个各限 1 的队列制造两个并发重执行组。能力不足时先明确支持范围或调整受支持接入方案，不另建通用领取、续租和重试引擎；不得宣称能够抢占仍在执行的物理任务。

## 7. 超时、暂停和取消

deadline 区分允许开始的期限及操作最大执行时长，具体字段在协议 schema 中分别表示。签发端和执行端检查时钟偏差；期限不可信时拒绝新变更并报告时间问题，不能自行延长授权。

模型超时不自动取消已经启动的工具。用户暂停停止新工作，在安全点让出执行；用户取消登记 cancel_requested，由执行器返回“未开始”“已停止且存在影响”“仍在安全停止中”或“状态未知”。只有可确认的前两类才结束相应尝试。

运行测试等可终止的进程可按已配置的宽限期停止整个进程组；迁移和数据恢复按工具语义处理，不能为了释放资源强杀后宣称无影响。补偿作为获批的具名步骤记录，不擦除原失败。

Task paused、Operation cancel_requested 和 DBOS 流程取消是不同状态。先在业务事务记录暂停/取消及控制任务，再由控制队列驱动执行器安全停止或核对；取消主工作流不能取消独立的清理/核对流程。DBOS 的取消通常在后续 step 边界生效，可抢占异步 step 的能力须核验，但两者都不保证外部进程停止。

恢复 Task 时先经领域服务复核依赖、授权、预算及现存占用：未完成 Run 使用受控 DBOS 恢复入口，已结束 Run 的业务等待满足后创建新的推进身份。原始 resume 可能绕过队列调度，不能作为面向用户的直接接口；工作流入口与每个副作用步骤仍执行物理准入检查，重新消耗模型/重执行容量时使用对应受限子任务。DBOS workflow_timeout 不替代命令开始期限和执行器最大时长。

## 8. 保留窗口与清理

已完成操作去重记录的保留期至少覆盖命令可接受期限、最大重投时间及允许时钟偏差。命令过期后也必须拒绝，不能因记录已清理而重新执行。

未完成、unknown、未确认停止及仍被业务/恢复引用的记录不按普通 TTL 删除。取消墓碑保留到所有相关命令不可再被接受；历史精简保留足以拒绝重放的身份和摘要。

目标端重新安装或执行账本丢失时产生新的 executor 实例身份，不能沿用旧身份并声称“查无记录就是没执行”。重新接入先核对运行资源，再由授权恢复流程决定可继续的操作。

DBOS 检查点、工作流输入输出、消息及代码版本引用纳入独立保留策略。长等待、未完成子流程、unknown 操作和恢复引用存在时禁止先清除所需检查点；已结束历史通过 SDK 支持的清理能力处理，不直接删除内部表。平台幂等墓碑须覆盖请求可接受窗口，不能因引擎历史清理而允许同一外部副作用再次发生。大对象保存制品引用，清理时计入 DBOS 活跃输入输出的引用集合。

## 9. 工具恢复分类

|工具类别|允许策略|禁止行为|
|---|---|---|
|纯查询|有界重试并标记观测时间|将过期数据当作当前状态|
|确定性文件/容器创建|按稳定身份及摘要查询，核对后复用|同名不同输入静默覆盖|
|构建|查询既有 BuildRun/进程；确认结束后按预算新建尝试|回执丢失即重复启动|
|外部 CI|按关联 ID 查询；不可识别时人工核对|无法查询时盲目触发第二次|
|部署/配置|按计划基线和步骤核对|使用过期计划继续修改新版本|
|数据库迁移/恢复|数据库账本、锁、后置检查或人工核对|仅靠 Operation 未成功就重复执行|

## 10. 协议实现与验证

执行 schema 独立包含 schema_version、operation_id、attempt_id、step_id、scope、target、授权引用、incarnation、generation、输入摘要和期限。认证保护消息完整性，字段校验不替代传输认证。

P0 冻结 PydanticAI/DBOS 接缝、WorkflowBinding、稳定身份、首条执行与计划 schema；P1 验证原子入队、基本重启、取消、独立部署和未知结果门禁，P2/P3 验证 Run 续接与真实协作，P4 扩大接管、迁移、升级和旧备份恢复覆盖。执行验收同时记录 DBOS 历史、业务数据库状态、实际进程和资源变化，验收要求见 D06。

## 11. 工作流重放与实时执行门禁

workflow 只保留确定性编排及 DBOS 持久原语；模型、数据库、时间/随机数、Git 和网络访问放入 step。DBOS 已持久保存的 step 结果会被复用，未完成步骤可能再次执行。对领域写入使用稳定 command_id 去重；对外部操作执行“按 Operation 查询、核对、再决定是否启动”，禁止把整个部署脚本或 Agent 循环作为可无限重试的黑盒。

每个产生新副作用的 Hub step 在实际尝试内重新读取当前权限、Task 暂停/取消、恢复门禁、预算、资源与计划基线；Executor 接受命令时再次检查能力、代次及本机维护门禁。普通远端计划的新变更步骤按 D04 在线取得短期许可；仅 D05 明确授权的本机应急流程可使用另一授权来源，并逐步核对本地权限、计划、时限和物理状态。不能把“曾经批准”或“资源曾经可用”作为缓存结果长期复用。读取历史完成事实可以复用证据；新的变更必须通过其执行模式的当前门禁。

重试策略按查询、业务命令、模型请求和物理执行分类设置，限制次数、退避及期限；DBOS 技术重试不等于业务允许重做。模型调用失败处理遵循 D01/D03 的请求与费用记录，未知远端影响进入 needs_reconciliation。清理和核对使用独立受控工作流，不依赖已取消父流程的 finally 一定完成。

## 12. 工作流升级与恢复边界

固定 application_name、workflow_name、输入/结果 schema 和代码 application_version。DBOS SDK 版本、系统 schema 版本、工作流代码版本、文档版本及远端执行协议版本分别维护；不能用 v4.5.0 代替 SDK 版本。

初期优先通过经过重放验证的 DBOS patch 兼容旧流程；PydanticAI 版本、工具集合及消息格式变更一并进入接缝兼容矩阵。改变步骤顺序或删除步骤时不能直接覆盖运行中的旧逻辑。无法兼容时，在维护窗口停止接收新任务，完成或经授权处理现有流程后切换单 worker 版本；不通过两个未经协调的 worker 并行运行规避升级。需要新旧代码长期并存时，采用 DBOS 支持的应用版本路由，并先完成多 worker 恢复与容量验收。缺少兼容代码时显示 waiting_upgrade，不盲目重放。

普通 worker 崩溃由服务管理器重启，再由 DBOS 恢复。原宿主或 PostgreSQL 丢失不能靠库自动解决；多 worker 自动故障转移需要 Conductor 或明确且验证过的协调方案。Conductor 不在 light 必需部署内，其许可、版本、凭据、数据访问及资源要求在采用时评审。

恢复、fork、rewind 和强制重试均从平台授权入口发起。不得通过 rewind 丢弃检查点来绕过成功步骤、审批、费用或审计；必须核对原 Operation 和物理占用，形成明确的恢复决定及新业务意图（如有）。旧备份恢复按 D05 在 DBOS.launch 前建立恢复门禁。

### 12.1 v4.3 到 v4.4 的语义迁移

本节保留 v4.3 到 v4.4 的历史迁移约束，升级到 v4.5 还须执行第 12.3 节。文档不声称存在或已经迁移旧运行系统；若有旧数据，先盘点 waiting_tool Run、常驻审批/消息工作流、逐步下发部署和旧 ProjectDescriptor，制定维护窗口及迁移记录。

旧 Run 不能直接改为新的有界 Run：先核对其历史和关联 Operation，在安全边界结束或保留旧版本完成，再建立业务等待及续接映射。执行中的部署保持单一执行权，旧 Hub 逐步驱动流程与新的远端计划执行器不得同时控制同一 Operation。旧 Descriptor 按 D04 的支持子集显式转换、审查并产生新修订；旧证据的 InputSet 无法还原时标记 needs_review，不伪造完整来源。

### 12.2 SDK 接缝与检查点数据

PydanticAI 的官方 DBOS 接入仅复用同一 DBOS 引擎，不建立第二份独立持久图。框架直接工具、MCP、流式回调的 I/O、自动重试与检查点边界在 P0 逐项核验：当前授权必须在新副作用内检查，费用必须在实际模型请求前准入，展示流不能驱动业务状态。

DBOS 输入输出只保留有界、脱敏结果和工程引用；完整上下文及大型输出保存在受控制品存储。若 SDK 默认序列化会复制完整历史或敏感材料，须使用受支持的序列化/适配扩展并验证恢复，不能仅在说明中宣称已脱敏。PydanticAI 的运行配置、工具标识和模型映射随版本固定；实际凭据只在步骤内部解析。

### 12.3 v4.4 到 v4.5 的迁移约束

升级先盘点应用命令事务、等待最终结果的旧工具批次、环境已绑定的 Release、在途部署及执行器能力。已有数据采用维护窗口和版本化迁移，不能因修改设计版本直接转换运行语义。

1. 旧 tool-call 仍要求最终结果时按原协议完成或在安全边界结束；新工具包使用提交/等待语义并切换必要的 Epoch，原 Operation 去重身份保留。
2. 旧 Release 若已固定环境参数，保留不可变历史并标记环境适用范围；无法证明环境无关时禁止直接晋升。重新构建或验证后创建新 Release，不删除旧字段伪装兼容。
3. 工作区人工接管、正式验收资产和环境配置修订补齐来源；无法还原时 needs_review，不能生成虚假验收证据。
4. Remote Agent 须先支持持久维护门禁、应急授权校验与交还协议，再允许注册本机应急配置；旧执行器明确不支持，不把完整计划的历史批准当作本机授权。
5. 升级时先停止新准入并核对在途操作；按 D05 第 10.2 节执行备份、迁移、验证和恢复准入。旧 DBOS 检查点只由兼容代码处理，缺失时保持 waiting_upgrade。

只有协议能力、迁移结果及恢复流程验收完成才能启用对应能力；无旧实现时交付迁移约束，不声称迁移已执行。
