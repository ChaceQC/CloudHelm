## 2. 版本规则

1. 总体设计使用 `vM.N`，配套专题使用 `vM.N.P`；前两位必须相同。当前总体设计为 `v4.5`，各专题的修订组合见下表。
2. 同一总体基线内，专题澄清、补充与修订递增第三位；可以独立递增，但同时更新下方清单和依赖兼容说明。
3. 改变三端边界、状态所有权、安全不变量或交付语义时，显式评审总体版本，不以第三位隐藏不兼容变更。
4. 总体版本变化后，各专题完成核对才迁移到新前两位，初始修订号为 0；旧文档归档，不自动批量改号假定兼容。
5. 版本写入页首，专题文件名稳定。文档版本与软件、PydanticAI/DBOS SDK、数据库、工作流应用及执行协议版本分别管理。

|文档|当前版本|对齐总体|
|---|---|---|
|本索引、D01、D03～D06|v4.5.1|v4.5|
|D02|v4.5.0|v4.5|

所有文件以 UTF-8 保存。读取配置及排障不得显形输出密钥；文档仅使用字段名、用途和资源标识，不包含实际凭据。

## 3. 文档维护

修改设计规则时，同步更新负责文档、受影响引用、验收要求和版本清单。实现进度及实际验收结果在交付记录中维护，设计正文说明系统结构、行为和约束。

本版沿用 v4.4 的 P0～P6 划分并增加交付与验收要求，旧记录必须逐项核对，不能自动认定新要求通过。各领域业务工作流与规则一起维护，公共 workflow 层仅承载引擎接入、身份映射和恢复门禁。

保留模块化单体、三端隔离、PydanticAI、DBOS 唯一持久执行、不可变制品、计划审批、同库事务入队、物理副作用核对及业务独立运行。正常变更继续在线取许可；本机应急新增独立且预先配置的人类授权来源，不能以普通修订号隐藏这一安全契约变化。Agent 不拥有应急授权，Remote Agent 不自主决定离线推进。

v4.5 对工具结果语义、Release 环境绑定和应急授权的改变须按 D02 第 12.3 节显式迁移。既有成功记录不改写，旧执行器缺少维护门禁或应急协议时不开放新能力；先冻结兼容版本与具体授权机制，再实施。SDK 接口、序列化、请求准入及优先级接缝需实际验证，本次未重新核验上游接口。

### 4.1 继承的容量基线

Ops Hub 维持 4 核 8GB；同机 light 与独立 Runner 两档使用同一 Hub 基线，独立执行节点另外配置。常驻平台 2GB、系统/缓存 1GB、突发余量 1GB、开发执行共享上限 4GB，开发执行 CPU 总配额初始不超过 3 vCPU。

模型真实请求上限 3、活跃开发 Task 上限 2、重执行上限 1、按需预览上限 1；数量上限不承诺同时满额运行。紧急任务改变获准排队顺序，不增加物理并发，也不借应急预算释放未知费用。D03/D06 记录实际容量与支持范围，设计参数不表示验收通过。

### 4.2 v4.5.1 可选沙箱人类测试

针对 AI 生成代码补充可选的实际操作测试，默认关闭，由用户按任务/候选选择。开启后在 Hub 开发沙箱或获准独立 Runner 临时运行固定版本，提供入口和测试说明，记录人类结论与反馈；未开启、明确跳过、未反馈和通过分别表示。问题反馈进入返工，新版本重新测试，临时环境按期限及资源策略清理。

本次沿用 v4.5 总体边界和正常部署审批，未将人工测试改成所有任务的强制步骤；现有流程默认未启用。D02 v4.5.0 的 Operation、业务等待及回收规则继续适用，其他受影响专题升至 v4.5.1。新增会话/状态在实现时单独协商 API/schema 兼容，旧客户端不得将未知状态显示为通过；文档修订不表示临时环境已部署或人类已验收。
