## 2. 版本规则

1. 总体设计使用 `vM.N`，配套专题使用 `vM.N.P`；前两位必须相同。当前总体设计为 `v4.4`，各专题的修订组合见下表。
2. 同一总体基线内，专题澄清、补充与修订递增第三位；可以独立递增，但同时更新下方清单和依赖兼容说明。
3. 改变三端边界、状态所有权、安全不变量或交付语义时，显式评审总体版本，不以第三位隐藏不兼容变更。
4. 总体版本变化后，各专题完成核对才迁移到新前两位，初始修订号为 0；旧文档归档，不自动批量改号假定兼容。
5. 版本写入页首，专题文件名稳定。文档版本与软件、PydanticAI/DBOS SDK、数据库、工作流应用及执行协议版本分别管理。

|文档|当前版本|对齐总体|
|---|---|---|
|本索引、D03、D06|v4.4.1|v4.4|
|D01、D02、D04、D05|v4.4.0|v4.4|

所有文件以 UTF-8 保存。读取配置及排障不得显形输出密钥；文档仅使用字段名、用途和资源标识，不包含实际凭据。

## 3. 文档维护

修改设计规则时，同步更新负责文档、受影响引用、验收要求和版本清单。实现进度及实际验收结果在交付记录中维护，设计正文说明系统结构、行为和约束。

本版使用 P0～P6 的新阶段划分，旧版阶段完成状态不自动映射。各领域业务工作流与规则一起维护，公共 workflow 层仅承载引擎接入、身份映射和恢复门禁。

## 4. v4.4 六项架构变更

|变更|本版决定|实现入口|
|---|---|---|
|Agent Runtime|PydanticAI 负责模型/工具协议，CloudHelm 负责上下文、工程协作、Gateway 和费用；角色共享运行时|D01 第 8 节|
|工作流边界|Task/Session 长期保存，Run 有界；等待结束当前 Run，条件满足后可靠续接；DBOS 唯一持久执行底座|D01 第 4～5 节、D02 第 1.3 节|
|远端执行权|Hub 生成/批准/提交完整计划，Remote Agent 唯一推进有限步骤；新变更默认在线取得步骤许可|D04 第 8 节|
|版本与证据|EngineeringRef、InputSet、EvidenceRecord、DependencyLink 统一结构，历史事实与当前适用性分离|D01 第 9 节|
|项目契约|Compose 受支持子集承载运行字段，薄扩展补充工程与交付规则，环境记录固定参数/secret 版本|D04 第 1 节|
|实施与容量|P0 接缝、P1 执行闭环、P2 单 Agent、P3 多 Agent、P4 恢复、P5 运维扩展、P6 产品评估；4 核 8GB Hub 基线，两档部署分别验收|D03 第 5 节、D06|

保留模块化单体、三端隔离、当前授权、不可变 Release、计划审批、同库事务入队、物理副作用核对及业务独立运行。PydanticAI 官方接口在本轮设计讨论中核对，具体 SDK 版本、序列化、请求准入与队列接缝仍需 P0 实际验证。

v4.4 对 AgentRun、工作流映射、远端执行权和 ProjectDescriptor 的改变需要显式迁移决策；如存在旧实现，遵循 D02/D04 的兼容与迁移要求，不以文档升级代替运行迁移。

### 4.1 v4.4.1 容量修订

Ops Hub 的标准硬件与验收基线调整为 4 核 8GB；同机 light 与独立 Runner 两档使用同一 Hub 基线，独立执行节点另外配置。D03 补充同机内存规划、CPU 总配额、预览和组合任务共享预算，D06 同步 P1/P2/P6 的测量与验收。

总体设计仍为 v4.4，本次为资源配置和验收参数修订，不改变三端边界、执行身份或授权语义。D01、D02、D04、D05 的 v4.4.0 与本次修订兼容，资源参数以 D03 v4.4.1 为准；模型请求上限 3、重执行上限 1 保持一致。内存预算及支持范围仍需实测，不将规格升级写成容量已通过。
