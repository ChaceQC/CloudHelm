## 1. 发布对象与项目契约

ReleaseCandidate 固定项目最终集成提交、验证证据及构建输入引用。BuildRun 通过后，领域服务校验来源、摘要、运行验证和策略，创建不可变 Release。失败保留候选与构建记录，不用新产物覆盖原 Release。

发布工作流及部署提交、授权、查询和核对工作流由 delivery 定义并由 DBOS 执行，delivery 保留业务结果所有权。Remote Agent 是完整部署计划的唯一物理步骤推进者，Hub 只接收账本事实并判定业务结果，不另建逐步下发循环。WorkflowBinding 关联固定业务对象和推进修订；恢复使用原 BuildRun/Operation 查询既有结果。引擎的 SUCCESS 不独自构成 Release 或 Deployment 成功证据。

### 1.1 字段唯一来源

|来源|权威内容|引用方式|
|---|---|---|
|Compose 受支持子集|service key、镜像/构建声明、启动命令、网络、卷、端口、健康、重启及资源|版本化源文件及解析输入，运行字段只在此处定义|
|ProjectDescriptor 薄扩展|构建目标选择、验收入口、迁移顺序/兼容条件、配置 schema、证据和发布政策|通过稳定 service key 和工程引用关联，不重复声明 Compose 运行字段|
|环境记录|实际环境参数、受控资源绑定、不可变 secret 版本引用|按环境版本解析，不从操作者临时 shell 隐式取值|
|Release Manifest|经解析、策略校验和验证的不可变结果|派生快照和来源引用，不能独立修改后反向充当第二套源|

Compose 与薄扩展各自选定唯一权威位置，可在仓库或平台版本化存储；来源变更显式迁移。配置 schema 标记敏感字段但不含值。迁移的应用命令在固定制品内执行，薄扩展说明何时执行及安全条件，不开放任意宿主脚本。

### 1.2 支持子集与编译过程

首条链路支持单目标、多服务、项目内网络、受管命名卷、环境配置引用、服务健康与固定镜像。源码 build 可供 Hub 受限构建使用，最终目标配置必须替换为已验证制品；目标禁止 build，归档模式禁止自动 pull。

特权容器、Docker socket、设备直通、任意宿主 bind mount、host 网络和未经批准的外部共享资源默认拒绝。include/extends、复杂 profiles、外部文件与插值能力在 P0/P1 形成逐项兼容表；未支持的能力拒绝并指出位置，不能静默忽略。获准例外也须在同一解析与策略入口验证。

1. 固定 Compose/薄扩展源版本、文件集合、环境参数版本和 CLI/解析器版本。
2. 在受限解析环境使用 Compose 标准解析能力处理声明，显式提供环境输入；禁止从 Hub 进程环境或越界文件继承配置。
3. 校验支持子集、唯一字段来源、service key、路径和资源政策，输出不支持字段及语义差异。
4. 生成规范化运行规格，计算不包含实际秘密值的摘要；secret 只保存版本化引用，真实值不进入持久解析输出、日志或审批正文。
5. 构建、验证并解析最终镜像身份，形成 Release Manifest；安装阶段只消费获准的派生结果及环境绑定，不重新运行源码声明。

Compose 标准化不等于安全校验。P0/P1 必须核验解析过程是否读取文件或展开秘密；需要的敏感解析仅在受控临时内存/运行材料中进行，保存和展示前还原为引用。现有 Compose 导入输出差异与兼容报告，由用户确认无法无损映射的项目配置，不让模型每次发布重新猜测。

### 1.3 工程引用与 Release 准入

Compose、薄扩展、构建 InputSet、镜像和验证报告统一使用 D01 工程引用。delivery 创建 Release 前检查证据当前适用性及规则版本；分析未完成或来源缺失时保持待复核。迁移旧 Descriptor 必须显式拆分字段并产生新修订，不能用批量改版本号假定语义等价。

## 2. 完整 Release Manifest

|内容|固定引用|
|---|---|
|source|权威仓库、精确 commit、构建输入摘要、BuildRun、工具链与执行提供方|
|services|稳定 service key、OS/架构、各平台不可变制品身份|
|runtime|启动参数、配置 schema、端口、卷、资源、依赖、健康和重启策略|
|migrations|迁移制品、顺序、适用数据库版本、兼容条件及恢复限制|
|verification|源码证据、制品扫描、最终镜像运行验证和审查引用|
|descriptor|Compose 源/规范化规格、ProjectDescriptor 薄扩展修订、解析器版本及规范化摘要|

只变更一个服务也产生完整新 Release，未变服务沿用已核验的不可变制品。数据库等第三方依赖固定镜像身份并声明数据卷要求；固定镜像不意味着允许自动升级或回退数据目录格式。

Release 可以部署到多个环境，每个环境绑定独立推进。首条验收采用单目标；未来一个环境包含多个目标时按目标分别保存计划与结果，不宣称跨目标原子切换。

## 3. Registry 与归档交付

|模式|传输与启动|身份验证|
|---|---|---|
|Registry|目标按获准 digest 拉取|记录 index/platform digest，核对目标架构与容器实际镜像|
|归档|受限 HTTPS 下载，完整校验后 load，使用 Release/服务专属本地标签启动|先校验 archive SHA-256，再校验 image ID/config digest、OS 和架构|

归档摘要、image config digest 和 Registry manifest digest 含义不同，字段不得混用；docker load 后没有 RepoDigests 不应误判为可跳过身份核对。

归档模式禁止 Compose 自动 pull/build，执行前将专属标签核对至获准 image ID，启动后再核对容器实际 image ID。受管变更在目标执行锁内进行；管理员手工改写标签作为漂移处理。

下载授权绑定目标与 Release，支持断点续传、临时文件、限速、超时和过期清理。续传清单仍绑定同一内容摘要；完整校验前不得 load。预检计算归档、镜像加载及临时解包的并存空间。

## 4. 环境绑定、命名空间与资源占用

Environment 表达项目内逻辑环境；EnvironmentBinding 关联 project_id、environment_id、target_id、installation_id，是单目标部署与执行锁的基本范围。同一项目的 test 与 prod 即使使用同一机器也必须有不同绑定。

Compose project、目录、网络、卷和服务标签由稳定安装标识生成，保存到绑定记录；用户可见名称不直接作为全局资源键。重命名项目不改变资源归属。重新安装与接管已有资源需显式绑定，不能仅凭名字相同就接管。

端口、显式共享网络和外部卷建立目标主机级资源声明。Remote Agent 在本地主机资源锁内核对持久占用记录及实际系统状态，再登记使用者。卸载只释放自身资源；共享卷必须显式允许共享，不能默认共享。

外部管理员可能绕过平台修改资源，因此预检成功不能保证后续端口绑定必然成功；运行失败仍按部分更新记录，不自动清除其他项目资源来“修复”。

## 5. DeploymentPlan 与起始基线

计划内容规范化后生成 plan_digest，批准后不可原地更改。至少包含：

|分组|必要信息|
|---|---|
|目标|Release/Manifest 摘要、EnvironmentBinding、目标平台、获准服务制品|
|起始状态|expected_environment_revision、起始 Release 或明确的首次安装标记、必要的实际服务向量、配置版本及数据库前置条件|
|运行输入|Compose 规范化规格与薄扩展版本、配置版本、不可变 secret 引用版本、网络及卷资源声明|
|执行|有限类型的具名步骤、顺序、固定输入摘要、前后置条件、停机范围、迁移、健康窗口、开始期限/最大时长及资源需求|
|失败处理|允许的补偿、准确目标版本、数据库兼容条件、何时进入人工核对|
|授权|所需策略、批准对象、有效期限、逐步骤启动许可要求、安全停止点和失联行为|

起始状态只包含影响执行安全的字段；心跳时间、瞬时 CPU 和日志数量不进入审批摘要。允许变化的字段必须显式列出，不能使用“无重大变化”作为无法判定的规则。

首次安装需证明绑定内不存在未登记的运行资源；缺少历史 Release 不代表目标一定为空。实际观察过期或结果未知时，先刷新和核对，不直接审批执行。

## 6. 审批与执行前条件更新

个人项目默认自动开发、验证、审查和构建，所有者可批准自己提出的部署。团队或重要环境可以要求独立审查及禁止自批；Agent 永远不代表人类批准，项目设置不能弱化环境强制策略。

构建前批准仅在项目策略要求时启用，绑定仓库、提交、构建输入及证据。部署批准绑定 plan_digest、目标、配置和 secret 版本、审批身份及策略版本。执行前重新检查当前策略与凭据状态；内容变化重新生成计划和批准。

审批待决只保存 DeploymentPlan、Approval 和业务等待条件，不占常驻 DBOS 编排工作流。批准事务按稳定身份更新业务状态、创建 WorkflowBinding 并入队部署提交流程。通知只携带批准记录引用；提交时重新读取 plan_digest、身份、当前策略和期限，不能只凭一条消息执行。

计划获批后，业务记录、WorkflowBinding 与 DBOS 入队按 D02 同事务提交。取得绑定执行权后，Hub 通过 expected_environment_revision 条件更新登记 active_deployment；Remote Agent 接收完整计划和原 Operation，取得本地锁并核对实际状态、操作代次和前置条件。队列分区只能辅助串行化，不能替代绑定执行权与目标本地锁。Hub 事务与远端变更不是分布式事务，崩溃窗口按 D02 查询和恢复。

若 A→B 和 A→C 均已获批，B 完成后，C 不能继续使用基于 A 的迁移和补偿。基线不匹配产生明确的 replan_required 原因；生成替代 DeploymentPlan 并重新审批，旧计划和批准保留历史。

## 7. 期望状态的提交时机

EnvironmentRevision 为递增的期望状态修订，保存 Release、配置及引用的批准证据。计划和审批阶段不改变当前期望；预检通过、准备开始首次副作用前，以条件更新创建新的期望修订并登记执行操作。该领域命令按 Deployment/Operation 的稳定命令身份去重，避免事务已提交而 DBOS step 检查点丢失时重复递增修订。

如果此时控制面崩溃，期望可能已经推进而目标未改动，恢复查询 Operation 后继续验证或记录失败，不以旧观测立即判断业务已失败。active_deployment 在实际执行未知时不能直接释放。

已批准的失败补偿恢复旧版本时，登记新的期望修订，引用原计划的补偿批准及执行证据；不把修订号倒退，不把原更新改为成功。失败且无法补偿时保留目标期望、实际混合状态及失败原因，默认不自动反复趋近目标。

人工决定接受部分状态或外部变更时，需形成新计划或可追溯的受管配置/版本记录。不能将混合服务状态直接贴上某个未经验证 Release 的标签。

## 8. 完整计划执行、许可与健康检查

### 8.1 Hub 与 Remote Agent 的分工

Hub 负责编制和批准不可变计划、提交固定计划及 Operation、签发当前步骤启动许可、接收事实、核对和计算 Deployment 业务结果。Remote Agent 负责唯一的步骤推进、本地锁、账本、实际进程及后置检查。完整计划重投按 operation_id + plan_digest 去重；本地已有计划时查询原执行，不另起执行循环。

首版 PlanStep 限于制品准备、运行输入检查、迁移、服务更新、健康验证和已批准补偿等类型，使用稳定 step_id、类型版本、input_digest、前后置条件、时限、取消方式和失败分支。执行器报告支持的类型/版本；遇到未知类型拒绝整计划，不按未知字段猜测执行。步骤包含固定制品和参数引用，不接受任意宿主 shell、模型临时插入步骤或无限自定义循环。

计划规定前序失败时停止或进入已批准补偿；受控执行器按记录推进有限步骤，不承担平台通用队列、跨任务调度或 DBOS 重放。物理步骤事实由 Remote Agent 账本产生，Hub 的 StepExecution 为回报投影，不能反向伪造执行器成功。数据库变更仍以数据库自身账本为必要证据。

### 8.2 步骤启动许可

每个新变更步骤默认在线请求一次短期启动许可。请求携带 Operation/计划/步骤/输入摘要、executor 实例、资源代次、前序结果引用及当前实际状态。Hub 经当前策略、暂停/取消、恢复门禁、计划有效期、secret 状态、资源及前置条件检查后返回受认证完整性保护的许可。

许可绑定 grant_id、operation_id、plan_digest、step_id、input_digest、executor、hub_incarnation、generation、环境执行身份和有效期限；其唯一授权是当前具名步骤。Remote Agent 在本地锁内再次检查身份、代次、期限和实际前置条件，持久登记许可接受与步骤 intent 后才能启动。重投相同许可查询原步骤，不获得第二次执行权；许可过期后尚未开始的动作须重新取得当前许可。

初始前置条件使用计划起始环境版本；本次部署登记新 EnvironmentRevision 后，后续步骤校验 active_deployment、该执行修订、计划规定的中间状态及前序后置证据。不能每一步都要求仍处于首次安装前状态，也不能跳过外部漂移检查。Hub 对回报落后于当前请求的情况先核对，不只凭远端一条“上步完成”就签发许可。

已接受许可到进程启动存在受限窗口，撤权与远端接受不构成原子操作。许可期限和允许时钟偏差限制这一窗口；撤权后拒绝新许可并发出取消，执行器在获知撤权后拒绝尚未开始的动作。系统不能承诺离线即时撤销已接受动作。开始期限与最大执行时长分开，许可到期不意味着应强杀正在执行的迁移。

### 8.3 失联与重新连接

|位置|默认行为|
|---|---|
|计划未接受或变更步骤未取得有效许可|等待连接和重新校验，不开始变更|
|步骤许可已接受、动作已开始|仅按该步骤规则完成或收束到安全点，保留结果|
|即将开始后续变更/重试/补偿步骤|在线取得新的步骤许可；失联不凭历史批准继续|
|业务已经运行|保持运行，管理通道离线不改变容器运行目标|
|步骤实际结果未知|needs_reconciliation，保留冲突锁和占用，查询后再决定|

已知在等待授权的部署保留当前业务阶段并设置 waiting_authorization 原因，不伪装成失败或 unknown；真正无法确认影响时才进入 needs_reconciliation。只读查询和制品准备按计划能力、期限和限额执行，秘密材料访问仍遵循授权。重连先补报账本和实际状态，确认新的授权/代次后继续；不重新执行已完成步骤。

首版不开放离线连续执行后续变更的模式。未来若引入须显式定义可接受的撤权延迟和授权范围，并升级安全契约。

### 8.4 执行顺序

1. Remote Agent 接收完整计划，检查身份、策略、目标能力、执行代次、实际基线与本地账本。
2. 预拉取或下载全部制品并校验身份、架构与可用磁盘。
3. 检查配置、secret 版本、端口、卷、备份和数据库前提。
4. 确认 Hub 已登记期望修订与原 Operation；每个新变更步骤取得有效启动许可，按计划执行迁移和服务更新。
5. 每步保存结果与服务实际版本，验证就绪和关键业务探测。
6. Remote Agent 在获批健康窗口内达到成功标准后持久回报；Hub 核验事实并结束 Deployment，各端分别释放已确认解除的占用和绑定执行权。

健康参数包括启动超时、间隔、连续成功阈值和观察窗口。窗口内失败属于本次部署失败；窗口后出现异常创建 Incident，不覆写历史 succeeded。迟到证据采用追加更正记录。

Compose 依赖启动、重建和健康行为由受控执行器明确处理。定向更新时防止 Compose 隐式更新计划之外的服务；所用 flags、服务范围及版本需在 P0/P1 验证，不把一次 compose 命令视为天然的事务。

远端部署具名步骤仍由 Remote Agent 记录，不能以 DBOS step 的序号取代 step_id。每次真正开始新副作用、重试或补偿时按本节取得当前步骤许可并核对环境及资源；已完成历史步骤可以复用事实证据，但先前缓存的“允许部署”不能证明当前仍有权限。健康观测携带观测时间和窗口，重放旧观测不能冒充当前就绪。

## 9. 迁移、失败与补偿

迁移计划说明适用数据库版本、事务能力、备份、兼容窗口和验证方式。旧应用与新 schema 的兼容性决定迁移在停机或服务更新前后执行，不统一规定所有迁移都先执行。

|情形|处置|
|---|---|
|首次副作用前预检失败|不更新服务，记录原因，释放已确认无执行的预留|
|部分服务更新失败|停止后续更新，保存每服务实际身份及 partially_applied 结果|
|步骤超时但影响未知|进入 needs_reconciliation，查询实际状态，保持冲突资源阻塞|
|补偿已批准且当前仍适用|按具名步骤执行，保留原失败，登记补偿结果与新期望修订|
|迁移不可逆或兼容性不满足|停止自动回退，按维护窗口、向前修复或人工恢复处理|

镜像可回退不代表数据库可回退。备份文件存在不代表可恢复；在部署前要求备份时应核对对应数据库、时间与恢复证据。迁移成功但回执丢失时依据数据库迁移账本核对，不能仅因本地步骤未完成就重跑。

用户单独发起的回滚是新的 Deployment 和审批，原计划内的失败补偿是原 Operation 的获批子步骤。两者都必须检查当前配置、secret 撤销状态和数据库兼容性。

DBOS 取消 Hub 主流程后，查询和停止确认由独立受控的 control 工作流继续推进；Remote Agent 执行获准的安全停止或计划内补偿，补偿步骤仍须获得当前许可。不得依赖被取消流程必然执行清理，也不能通过通用 rewind/fork 重新发送迁移或回滚命令。部署结果未知时保留 active_deployment 和物理预留，按 D02 核对后才允许释放。

## 10. standalone 与离线重启

从同一 Manifest 导出固定制品的 Compose、配置样例、迁移与恢复说明；派生 Compose 与受管执行使用相同规范化运行规格和制品身份。归档包包含镜像及加载校验步骤；Registry 包明确可独立访问的外部地址和权限安排。实际 secret 通过单独受控通道交付，不写入可分享归档。

业务容器明确 restart 策略，目标 Docker 服务配置开机启动，必要配置与受限凭据材料安全保留在目标。业务启动路径不需要先联系 Hub 或调用 CloudHelm SDK。DBOS 仅存在于 Hub 控制面，交付项目和 Remote Agent 无需连接 DBOS 系统数据库，也不依赖 Conductor。

重启策略仅保证进程重新启动，不保证数据库就绪或业务可用；应用应具备受控重试和就绪检查。数据库迁移使用受管一次性步骤或明确幂等机制，不能在每次容器重启时无条件重跑未知迁移。

P1 验证已知项目的完整计划、基本失联、步骤许可和独立交付，P2 接入 Agent 制品，P4 扩大迁移、部分失败、撤权竞争和恢复覆盖。独立交付验收包括 Hub 离线、目标及 Remote Agent 重启、独立重新安装和保留业务卷的单项目卸载，验收要求见 D06。
