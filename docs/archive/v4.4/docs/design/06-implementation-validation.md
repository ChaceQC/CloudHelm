# 06 实施计划与验收

> 文档版本：v4.4.1
> 对齐总体设计：v4.4
> 修订日期：2026-10-07
> 文档性质：实施计划与验收要求。

[返回文档索引](README.md)。本文件说明实施阶段、验收要求、组件复用和效果评估方法。

## 1. 实施原则

保留完整多 Agent 开发、远程交付与持续运维目标。先验证组件接缝和最小执行闭环，尽早接入真实 Agent 与两个开发会话，再扩大可靠性、运维和产品能力。阶段名称为 v4.4 的 P0～P6，与 v4.3 旧编号不兼容，不能仅替换进度标签。

选定 PydanticAI 协议运行时、DBOS 唯一持久执行底座、模块化单体、完整远端执行计划、Compose 支持子集与薄扩展。初期 FastAPI/DBOSClient、单 DBOS worker 与 PostgreSQL 同库不同 schema；Runner 通过相同执行协议支持同机 light 和独立节点，默认无 Conductor。

基础 Desktop 随阶段交付。当前授权、幂等、秘密保护、执行隔离、未知结果门禁和基本取消随 P1 建立；P4 扩大故障覆盖和恢复自动化，不把安全前提延期补做。P0 固定核心不变量和首条链路接口，其余 API/schema 随对应领域冻结。

每阶段交付实际实现、版本化契约、使用说明和验收记录。只验证该阶段的关键风险和实际改动，已通过场景不为普通文档改动重复运行。设计更新不表示实现或验收已经完成。

## 2. P0 架构接缝

交付三组可运行的接缝验证及其决策记录，锁定 PydanticAI、DBOS、SQLAlchemy/驱动、PostgreSQL、Compose 的具体版本和兼容矩阵。

|接缝|交付与验证|必须明确的边界|
|---|---|---|
|Runtime 与 Gateway|模型请求、外部工具请求、历史保存、工具结果续接、当前门禁和费用记录|PydanticAI run_id 与 CloudHelm Run 分开；每次真实请求可准入；长期等待能结束 Run|
|DBOS 与业务状态|同库事务入队、稳定身份/摘要、模型容量、有界工作流、条件满足后续接|原 Run 重放与新 Run 续接区分；无丢失交接和第二套调度状态机|
|Hub 与 Remote Agent|完整计划接收、有限步骤、步骤许可、本地账本、基本失联与重复投递|本地唯一推进；当前动作安全收束；新变更在线取许可|

同时冻结 Runtime 输入/TurnResult、Task/Session/Run/Workflow/Operation 映射、EngineeringRef/InputSet/EvidenceRecord/DependencyLink 核心语义、PlanStep/启动许可 schema、Compose 支持子集及首条链路错误/权限语义。

核验 PydanticAI 官方 DBOS 接入对实际请求拦截、SDK 自动重试、流式回调、历史续接及序列化的影响。完整历史和实际秘密不能因默认 SDK 行为进入不受控检查点；记录可直接复用、需要薄适配和不支持的能力。不得以文档中的示例 API 代替真实接缝结论。

退出条件：三组接缝可运行，关键不变量具备直接证据，首条链路契约可实施；接口缺口有明确解决决定。P0 不要求提前冻结全平台所有 API，也不建设完整产品底座。

## 3. P1 最小执行闭环

使用已知的小型前后端数据库项目，交付基础身份、目标配对、受控 Git 与工作区、受限构建、Operation/Attempt/本地步骤账本、资源准入、Compose 解析校验、薄扩展、不可变 Release、计划审批和独立目标部署。基础 Desktop 可以提交、批准、查询和取消。

业务与 DBOS 同事务入队、稳定请求摘要、当前授权、秘密隔离、原子制品落盘和基本事件恢复随链路交付。默认支持有限步骤及可验证的迁移方式；未知结果保持阻塞，尚无自动恢复能力时明确进入人工核对，不尝试猜测重做。

退出条件：

- 已知项目通过构建和制品验证，在另一台机器按完整计划运行；Hub 离线后业务和目标重启仍可运行。
- 重复提交只关联原计划/Operation，已完成步骤不重复执行；失联时后续变更等待许可。
- 基本取消、安全停止、无权限、秘密不出界、沙箱与 Git 边界以及资源准入成立。
- 原子入队、基础 worker 重启和未知结果门禁有证据；旧备份恢复入口默认禁止自动执行。
- 完成一次实际同机 4 核 8GB 已知项目交付测量，记录真实拓扑及 D03 的内存/CPU 预算执行情况；建立独立 Runner 的注册、能力匹配和分离统计，不能混记为同机通过。

Registry、外部 CI 和完整运维 adapter 可在 P5 补齐；不能通过发送源码到目标临时构建替代制品交付。

## 4. P2 Agent 完整链路

接入真实单 Agent 代码生产、工作项与验收修订、ContextPackage/ModelRequestRecord、有界 Run、外部工具续接、费用准入、独立验证审查和项目合并队列。Agent 生成的代码使用同一 P1 构建交付链。

交付统一工程引用、InputSet、证据适用性和必要影响索引。Run 在工具或人工等待时结束，Session 保留历史；收到结果后形成新 Run，当前 Run 崩溃则恢复原身份。独立验证角色使用受限权限检查实际代码和最终制品。

退出条件：从真实需求到修改、验证、审查、构建、批准部署形成完整链路；输入与结果可追溯，过期证据不被采用。模型真实请求和内部重试均受预算约束，usage 未知保留待核对，重放不重复计费。测量 Agent 驱动的构建/联调、队列和控制响应。

此阶段只确认单 Agent 工程链路，不以独立审查角色代替 P3 的两个开发会话协作验收。

## 5. P3 多 Agent 协作

交付至少两个开发 Agent 的独立工作区、角色策略、任务图、正式契约、直接消息、收件箱确认、可恢复等待、冲突处理与返工。两个开发会话围绕同一真实前后端需求协作，最终进入同一项目合并和交付链。

退出条件：契约确认后可并行实现，联调由精确产物解锁；循环等待、无进展和预算耗尽具有明确升级方式；协调者可以依据持久业务记录接管。覆盖回复早于登记等待、重复结果、结束 Run 与续接间崩溃、暂停期间收信、框架新 run_id 和运行中契约变化。

同时记录首轮单/多 Agent 的质量、耗时、费用、冲突和无效通信，尽早检查协作假设。P6 扩大重复实验和统计，不能到最终阶段才首次验证协作是否有效。

## 6. P4 可靠性与恢复完善

扩展真实执行窗口的崩溃、接管、部分部署、撤权竞争、迁移与补偿、Hub 旧备份、执行器账本丢失和工作流升级。交付用户可操作的核对与恢复入口，以及恢复审计和兼容矩阵。

退出条件：旧进程未确认停止前不释放冲突资源；计划中间状态不误用初始基线，外部漂移仍能被识别；许可过期、接受后撤权和步骤中断遵守 D04 的明确边界。恢复包含业务与 DBOS schema、会话/等待、工程引用和可恢复代码的一致性备份；新控制身份和逐资源核对完成前不自动出队。

普通 worker 重启覆盖在 P1，P4 验证兼容升级、缺失旧代码、旧备份和跨端恢复。若存在旧实现，按 D02/D04 显式迁移 v4.3 语义；无旧实现时只交付迁移约束，不编造迁移成功记录。

## 7. P5 持续运维与扩展

交付有界日志/指标、告警、ObservedState/DriftRecord、Incident、固定诊断、获批 runbook 和代码修复 Task 关联。补齐支持清单中的 Registry、外部 CI 和观测 adapter，并分别验证权限、幂等、输入/结果身份及容量。

退出条件：管理通道与业务健康分开；漂移处置及修复经过当前授权与同一交付流程；适配器声明可用/受限/不支持范围。独立 Runner 的能力协商、工作区归属和多节点资源准入达到已声明范围，不以扩展 Runner 等同于多 DBOS worker。

## 8. P6 产品与最终评估

完成 Desktop 项目、需求、团队、diff、证据、预览、审批、部署和 Incident 体验，以及 Windows/Linux 安装、升级、断线同步和权限变化处理。整合 P0～P5 实现和证据完成完整产品验收。

形成同机 light 与独立 Runner 两档容量报告、单/多 Agent 对照、缓存对照、成功交付成本、失败/人工介入记录及答辩材料。同机档位在真实 4 核 8GB 整机测量；独立档位以 4 核 8GB Hub 为基线，报告全部执行节点配置与总资源。

退出条件：无项目开发工具链的桌面可使用完整闭环，预览隔离与批准对象清晰，续接/授权等待/结果未知有准确提示；实验可追溯且报告覆盖率。允许得出受限通过、不支持或多 Agent 未优于单 Agent 的结论，完整目标依据实际验收确认。

|能力|验收要求|

## 10. 两档部署容量测量方法

同机 light 使用整机受限为 4 vCPU、8GB RAM 的 Linux Ops Hub，外部模型 API 和另一台交付机器。独立 Runner 档位使用相同的 Hub 硬件基线，并记录各开发执行节点和交付目标配置，分别统计并给出总资源；不能只报告 Hub 的 8GB 而省略远端构建开销。记录 OS、架构、SSD/其他磁盘、Swap、项目 commit、工具链和全部常驻组件，不能只限制高配宿主中的一个容器。

记录空载、DBOS 入队/有界推进/检查点恢复、持久 Session 等待与定时容量、依赖安装、前端构建、后端测试、一次浏览器检查、预览竞争及归档交付的内存/CPU/磁盘峰值与耗时。分别记录 API 与 DBOSClient 池、worker 的 DBOS/模型池、PostgreSQL 活跃连接与写入、队列等待量、检查点增长和控制队列延迟；防止多个小池合计超过数据库上限。

核对 D03 的 2GB 常驻平台、1GB 操作系统/缓存、1GB 突发余量和最多 4GB 开发执行共享预算；这些是初始规划，报告同时列出实际占用和不足项。验证全部开发进程的 CPU 总配额、构建/测试内部并发、预览与测试资源合计、资源不足准入，以及重任务期间许可、取消和心跳响应。两个活跃 Task、三个模型请求和一个预览只作数量上限，不把配置值直接当作同时满负载通过的证据。

测量 API 延迟、数据库连接、任务排队、步骤许可及取消响应；阈值在执行前按支持范围固定，不在结果出来后为通过而修改。沿用 P1/P2 早期记录，最终报告比较变更后的资源趋势。DBOS 不需要独立服务的事实不能代替 SDK 和数据库增量的测量。

持续观察不少于 24 小时，混合代表性任务与空闲，检查泄漏、残留容器、资源预留、Session/WaitCondition 和 DBOS 定时/历史增长、指标行数、日志增长和清理引用。支持结论分为通过、受限通过、不支持；超限时修订容量或支持范围后重新验证相关场景。单 worker 恢复只证明该拓扑，多 worker/Conductor 的容量和故障转移单独报告。

## 11. 多 Agent 与缓存实验口径

预先固定任务集、原始需求、独立验收集、模型版本、工具权限、运行环境、预算与人工介入规则。同一任务重复执行，记录顺序、随机因素、失败和波动，不使用一次演示推导普遍优势。

单/多 Agent 对比记录通过率、总耗时、实际费用、token、人工次数与耗时、冲突、返工、独立验证发现的问题及无效通信。失败任务成本不能排除；交付成本至少同时报告全部实验费用除以成功任务数以及各任务明细，零成功时该指标记不可计算。

可设置无直接通信、无独立审查等消融对照，研究收益来源。简单任务成本上升时如实报告，不人为增加团队以满足演示外观。

缓存对照比较每轮重拼与稳定前缀/增量追加，固定语义输入与验收，分别记录冷启动、连续请求和压缩切换。交错或随机安排实验顺序，记录调用间隔及提供方缓存条件；无法保证物理冷缓存时注明限制。

提供方能力与 usage 取自真实记录，缺失统计只能报告输入稳定性及效果未知。费用包含缓存创建/读取、输出、失败请求和压缩；主要指标为质量、每次成功交付的全部成本、时间与人工介入，命中率作为诊断信息。

## 12. 复用矩阵与核验

|领域|拟复用能力|平台承担的部分|采用前核验|
|---|---|---|---|
|Desktop|Tauri、React、TypeScript|管理 UI、权限状态、同步与预览边界|Windows/Linux 打包、IPC、WebView 隔离|
|API/数据|FastAPI、Pydantic、SQLAlchemy、PostgreSQL、Alembic|领域命令、同库事务、版本、业务事件与授权|同事务入队、数据库角色、业务/DBOS schema 迁移与连接预算|
|工作流|DBOS Python、DBOSClient、队列/检查点/定时|各领域有界 workflow、公共接入/WorkflowBinding、可靠续接与实时门禁|原子交接、Run 身份、模型容量、取消、版本和保留|
|Agent|PydanticAI 消息、工具协议、结构化输出、外部工具和官方 DBOS 接入|有界推进、上下文、工程协作、Gateway、请求/费用记录|真实请求准入、重试、续接、流式回调、序列化、许可证及 usage|
|源码|系统 Git；可选 Gitea/GitHub|仓库归属、受控工具、合并队列|权限、过滤器、LFS/submodule、条件更新|
|执行与构建|Docker、受限 BuildKit、现成项目工具链|输入固定、资源、记录与证据|内核/cgroup/存储兼容、峰值与权限|
|交付|Compose 标准解析及受支持子集、归档；可选 Registry/CI|薄扩展、固定完整计划、步骤许可、本地执行及证据核对|解析无敏感泄漏、输入唯一来源、更新范围、失联和许可竞争|
|预览与观测|Caddy 或现有代理；可选专业后端|预览授权、有界采集、Incident|TLS/DNS、Cookie、配额与断线行为|

OpenHands、SWE-agent、Aider 可作为开发循环的参考，Coolify、Dokploy 可作为部署交互的参考。本版同时选定 PydanticAI 协议运行时和 DBOS 持久执行底座；文档选型不表示集成已实现。Agent Runtime 不建立另一套可绕过 DBOS/Operation 的副作用重试链。组件采用前核验接口、许可证、运行依赖与资源开销，接入范围由平台领域契约限定。

DBOS 接管通用持久调度，平台保留需求/契约、审批、资源、Git 集成、Release/Deployment 和真实操作核对。不得一边引入 SDK，一边继续实施旧的通用 WorkflowJob 队列和调度租约。官方依据由 D02 维护。

## 13. 需要在实现阶段冻结的选择

|选择|当前约束|冻结阶段与证据|
|---|---|---|
|Runtime 接缝与版本|PydanticAI，统一角色与 Gateway，框架/业务身份分开|P0 接口及真实请求/外部工具/续接/序列化验证；P2 完整链路|
|DBOS 与数据库|同库不同 schema、稳定身份与事务入队|P0 版本及契约，P1 驱动/角色/迁移/基本恢复|
|工作流与长期状态|Task/Session 长期，有界 Run，业务等待后可靠续接|P0 映射，P2/P3 真实等待和并发，P4 升级|
|远端计划与许可|有限步骤、完整计划、本地唯一推进、在线步骤许可|P0 协议，P1 已知项目与基本失联，P4 竞争及恢复|
|工程引用和适用性|统一引用及显式依赖，各领域持有权威对象|P0 核心结构，P2/P3 输入变化、证据与消费者门禁|
|Compose 支持子集|运行字段唯一来源，薄扩展，解析输入受控|P0/P1 兼容表、差异报告和安全解析|
|受限构建与两档容量|按需 rootless BuildKit，同机/独立 Runner 相同协议|P0/P1 能力与内核，P1/P2 早期测量，P6 持续报告|
|预览 DNS/TLS|不同主机名，证书可信，IP-only 不默默降级|P1/P2 安装预检，P6 浏览器与安装验收|
|模型及缓存能力|真实提供方与 usage，不假定兼容接口完全一致|P0 接缝，P2 能力表，P3 初测，P6 对照|
|告警与保留、适配器|有界采集，来源和能力明确|P5 实现与配额，P6 汇总|
|多 worker 与 Conductor|非两档部署的必需组件；须另有故障转移方案|扩展前核验版本、许可、安全、恢复和容量|

未决项不能削弱安全、版本、授权和恢复不变量；需要改变不变量时按索引中的版本规则同步评审。

## 15. 建议代码组织

实现代码按以下目录组织。运行入口与逻辑模块分开，逻辑模块可以共享进程部署。

```text
cloudhelm/
  apps/desktop/                 # 管理客户端
  services/hub-api/             # FastAPI + DBOSClient，不启动执行运行时
  services/hub-worker/          # PydanticAI/单 DBOS 运行时，统一注册各领域工作流
  services/dev-runner/          # 受信任开发执行器
  services/remote-agent/        # 完整计划的有限步骤执行、许可校验与本地账本
  modules/identity/             # 身份、策略与审批
  modules/projects/            # 项目、仓库及需求版本
  modules/collaboration/       # 工作项、依赖、决策、消息及业务等待/续接工作流
  modules/agent-runtime/       # PydanticAI 适配、Session/有界 Run、请求、上下文及推进工作流
  modules/workflow/            # 公共 DBOS 接入、WorkflowBinding、版本注册与恢复门禁
  modules/execution/           # Operation、Attempt、步骤及资源
  modules/workspaces/          # 工作区与沙箱生命周期
  modules/integration/         # 合并队列、验证、审查及所属工作流
  modules/tool-gateway/        # 工具鉴权及路由
  modules/delivery/            # Compose/薄扩展、Release、计划、许可及交付工作流
  modules/operations/          # 观测、漂移、Incident 及运维工作流
  modules/artifacts/           # 内容存储、索引与清理
  integrations/                # DBOSClient 封装、Git、CI、模型、MCP 和观测适配
  packages/contracts/         # API/事件/执行 schema，共享工程引用和 Runtime 契约
  database/migrations/         # 业务 schema；DBOS 系统迁移单独受控执行
  infra/ops-hub/
  infra/remote-target/
  examples/standalone-project/
  docs/design/
  docs/acceptance/
  tests/
```

跨模块依赖通过明确接口和领域命令组织，避免循环导入与任意写表。实际存放方式可以根据语言和构建系统调整，但不得借移动目录改变 D01 的状态所有权。DBOS 运行时、SDK 管理接口及系统数据库仅位于受信任 Hub，Runner 与 Remote Agent 只实现平台执行协议，Remote Agent 本地推进固定计划。跨领域共享 EngineeringRef/InputSet 结构，各领域维护自身证据与适用性；公共 workflow 层不反向依赖全部业务模块。

## 16. DBOS 专项验收清单

以下为实施阶段必须形成的证据，本次文档修订不表示已经执行或通过。按所属阶段覆盖必要场景，不为每次普通改动重复运行整套故障实验。

|阶段|场景|退出证据|
|---|---|---|
|P0/P2|PydanticAI 请求、校验修复、重试、外部工具和续接|真实请求逐次准入；工具经过 Gateway；保存历史可续接；SDK 默认序列化无秘密泄漏|
|P0/P1|业务写入/事务入队失败或回执丢失|业务与 DBOS 同提交/回滚；同键异摘要拒绝，同键同请求返回原身份|
|P1/P2|领域提交后检查点丢失、worker 重启|业务版本不重复推进；恢复原 Run/Operation；已知外部结果可复用|
|P2/P3|回复先到、结果重复、Run 结束与新 Run 入队间崩溃|等待登记无丢失；continuation_revision 去重；一个 Session 最多一个有效 Run|
|P2/P3|工具批次未全部完成、消息到达与暂停/续接竞争|遵守固定续接策略；unknown 不伪造失败；暂停不触发新推理，控制事件可处理|
|P2/P3|契约变化与异步影响分析未完成、不同构建输入|消费者有效性门禁阻止旧证据被采用；历史结果保留|
|P0/P1|Compose 不支持字段、插值/外部文件、敏感输入|明确诊断且拒绝越界；运行字段唯一；标准化输出无实际秘密|
|P1/P4|完整计划重复提交、断网发生在许可前/接受后/步骤中|仅一个本地执行循环；许可绑定并去重；当前步骤按约定收束，后续变更等待|
|P1/P4|计划批准后撤权、许可过期、执行器时钟偏差|拒绝无效启动；记录可接受的许可窗口；不宣称即时撤销已接受动作|
|P1/P4|迁移完成但回执丢失、部分更新、补偿时失联|依据数据库/本地账本；中间状态正确；补偿重新取许可；不盲重放|
|P1/P4|主流程取消、旧进程仍运行、恢复绕过队列|独立核对继续；物理占用保留；新启动仍受当前门禁|
|P1/P6|模型/重任务饱和、定时等待多、数据库连接紧张|许可、取消与查询可响应；模型/物理/维护容量分开；无父子槽死锁|
|P2/P4|模型已计费但响应/检查点未知|保留原请求和未知费用；新增真实请求重新准入，不重复结算|
|P4|PydanticAI/工具历史变化、兼容补丁、缺失旧代码|旧流程可恢复或明确 waiting_upgrade；不无条件套用新步骤序列|
|P4|恢复旧备份，远端比备份新，Run 已结束而 Session 仍在等待|启动门禁生效；核对真实操作和等待；新控制信任建立前不恢复执行|
|P4/P6|清理期间等待条件、InputSet、证据或恢复仍引用内容|所需历史和制品仍存在，去重窗口保持有效|
|P5/P6|独立 Runner 能力不足、断线、工作区迁移|按真实节点准入；占用/来源明确；Hub 与全部节点资源分别报告|
|扩展前|多 DBOS worker、新旧应用版本、Conductor 故障|故障转移、版本路由和物理核对明确；独立 Runner 验收不能替代|
