## 1. 项目定位与文档分工

**云舵 CloudHelm——多 Agent 协作开发与远程交付运维平台。**建议论文题目为《基于多 Agent 协作的远程软件开发与运维平台设计与实现》。

用户通过 Desktop 提交目标、观察协作、审查产物并批准部署。独立 Linux Ops Hub 承载 Agent 推理调度、源码、隔离开发、验证与构建。另一台远程机器通过 Remote Agent 接收受控部署，并独立运行交付后的业务。

本文规定产品范围、架构边界、核心决策和交付主线。对象字段、状态转换、恢复步骤、资源参数、部署协议、安全配置及专项验收放入独立详细设计，避免总体设计承担全部实现细节。

## 2. 产品范围与使用过程

完整平台提供项目与仓库管理、需求澄清、团队协作、独立开发环境、代码集成、验证审查、构建发布、独立远程交付、持续运维、权限审批和审计。Desktop 退出后，Ops Hub 继续已经授权的工作，需要新的人类决策时等待。

典型使用过程如下：

1. 用户创建项目或接入已有仓库，配置技术约束、预算和验收要求。
2. 协调 Agent 形成工作项与契约，相关 Agent 按真实依赖交流、实现和返工。
3. 开发结果进入项目级合并队列，独立验证与审查绑定最终集成版本。
4. 平台构建并验证不可变制品，形成完整项目 Release。
5. 用户审查目标环境、起始状态、配置、数据库影响及失败策略，批准具体部署计划。
6. Remote Agent 执行部署并报告每个服务的实际版本与健康状态。
7. 告警形成 Incident；需要变更环境时执行获批操作，需要改代码时创建关联修复 Task。

首条完整验收路径固定 Linux Ops Hub、另一台 Linux 交付机器、包含前后端与数据库的示例项目及 Docker Compose 部署。多项目、多团队、多目标和不同技术栈依相同契约扩展。

Kubernetes、多云资源创建、跨区域高可用、任意远程终端和开放式自动生产处置属于后续扩展。阶段实施不缩减多 Agent 协作、独立交付及持续运维的完整目标。

## 3. 三端边界与物理部署

|位置|职责|不可跨越的边界|
|---|---|---|
|Desktop|目标输入、团队视图、diff、预览、审批、部署与运维展示|不执行 Git、依赖安装、项目测试、构建或 Agent 模型循环|
|Ops Hub 控制面|API、领域规则、授权、持久调度、模型适配、证据索引|不以控制面身份运行生成的代码或仓库脚本|
|Ops Hub 开发执行区|工作文件、沙箱、测试、按需构建与预览|不能访问控制面数据库、共享 Git 元数据、长期远端凭据或宿主 Docker socket|
|远程交付机器|正式业务容器、业务数据、Remote Agent 及本地执行记录|不承担临时开发调试，不依赖 Hub 在线才能继续运行|

初期采用 FastAPI + DBOSClient、单个加载 DBOS 运行时的异步 worker、受信任 Runner、PostgreSQL、系统 Git、制品目录和轻量反向代理。业务工作流归所属领域，公共 workflow 层只管理 DBOS 接入、WorkflowBinding 与恢复门禁，由 worker 统一注册执行；无需独立工作流服务器，默认不部署 DBOS Conductor。逻辑模块不分别拆为常驻微服务；Runner 的宿主权限与控制面身份分离。

Hub 业务表与 DBOS 系统表采用同一 PostgreSQL 数据库、不同 schema。API 只提交和查询，不因增加 API 进程而启动额外工作流执行器。初期一个 DBOS worker 由 systemd 或容器服务管理器重启；增加独立 Runner 不等于增加 DBOS worker。多 worker 自动故障转移在引入 Conductor 或经过验证的协调方案后单独验收。

Desktop 经 HTTPS REST 提交命令，经 SSE 接收业务事件；必要时通过受控 WebSocket 连接沙箱会话。Remote Agent 主动建立认证通道接收命令、回传结果及心跳。SSH 仅用于受限初次引导，不构成第二条日常部署通道。

## 4. 领域划分与状态所有权

按身份授权、项目协作、工程执行、发布交付、持续运维组织领域。跨领域操作通过显式命令及结果交接，不直接修改其他模块的业务表。

|层次|主要对象|设计责任|
|---|---|---|
|业务目标与结果|Task、Release、Deployment、Incident|由对应领域服务校验状态转换与完成条件|
|业务内部过程|WorkItem、ContractRevision、Review、WaitCondition|记录依赖、版本、证据、等待及局部进展|
|执行与尝试|AgentRun、ModelRequestRecord、Operation、ExecutionAttempt、StepExecution|区分有界推理、真实模型请求和外部执行；远端步骤事实归执行器账本|
|基础设施记录|DBOS 工作流/队列/检查点、WorkflowBinding、ResourceReservation、InboxDelivery、事件游标|DBOS 管理流程执行，平台管理业务关联、物理资源、收信与同步；不替代业务结果|

Task、Release、Deployment 和 Incident 生命周期独立。开发完成不代表已经部署，历史部署成功不代表服务当前健康。每个权威状态只有一个负责模块，界面阶段尽量从权威状态与证据投影，不维护另一套可独立修改的结论。

领域服务决定业务动作是否允许；DBOS 持久推进平台编写的工作流，处理队列、等待、定时和重放；Gateway 执行当前授权和参数检查；Runner 与 Remote Agent 报告实际执行事实。WorkflowBinding 仅关联业务对象与 DBOS 执行身份，不复制一套调度状态机。DBOS 成功、取消或重试状态不能直接替代 Task、Deployment 或物理进程的业务结论。

## 5. 多 Agent 协作与版本化输入

团队围绕工作项、契约、代码和验证结果协作。协调、开发、验证、审查、发布与运维是能力角色，按任务需要启用。简单任务可以缩小团队；正式多 Agent 验收仍需至少两个开发 Agent 使用独立工作区并进行真实协作。

实现、联调和验收等具有不同前置条件的工作优先拆为明确工作项。依赖以契约版本、候选产物及环境条件表达；消息用于提问、交付和变更提议，不能直接越过调度、审批或完成条件。

PydanticAI 负责模型消息、工具协议与结构化结果，CloudHelm 负责上下文、角色策略、工程协作、当前授权及费用。所有角色共享同一 Runtime；外部副作用经 Gateway 转交 Operation，模型无权直接运行宿主命令。每次真实模型请求，包括框架重试，均经过请求登记与预算准入。

Task 和 AgentSession 可长期存在；同一 Session 同时最多一个有效 AgentRun。Run 是一次有界推进，遇到外部工具、人工输入或依赖等待时提交历史与等待条件并结束，后续条件满足后可靠入队新的 Run。当前 Run 崩溃时恢复原身份。用户暂停后消息只积累；协调者从持久任务图、正式决策和执行记录恢复。

ContextPackage 保存 Run 启动基线；每次模型请求单独记录实际输入、历史边界、增量和有效版本。工程引用统一对象类型、身份、版本及适用摘要，InputSet 固定实际输入，EvidenceRecord 声明验证范围，DependencyLink 记录消费关系及规则版本。输入变化沿显式依赖判定影响，历史完成事实与当前证据适用性分别保存。

模型输入缓存优化采用稳定前缀、追加式会话、版本化工具包和显式压缩检查点。同会话复用优先，跨 Agent 收益依据提供方实际统计；权限、正确性、总费用与质量优先于缓存命中率。

## 6. 统一可靠执行

构建、测试、部署和固定运维操作复用执行基础协议，但分别实现权限与业务语义。Operation 用于外部副作用或需独立恢复的长任务；普通只读查询通过受限接口和有界步骤完成，领域状态变更通过幂等命令完成，不为每次查询创建完整物理执行账本。

系统采用事务业务更新、EventLog、Outbox 和 DBOS 持久执行。业务写入与工作流入队通过同一 SQLAlchemy 事务调用 `DBOSClient.enqueue_in_transaction`，使用稳定 Workflow ID 和请求摘要；两个独立数据库不能获得该原子性。Desktop 事件及外部交接仍保留 Outbox；同库消息/批准与下一次推进可以事务入队，跨事务交接通过稳定事件身份去重。允许重复投递，不宣称跨数据库、文件、容器及业务数据库具有天然的端到端 exactly-once。

工作流执行确定性的有界推进或有明确终点的工程过程，模型、数据库、Git 和执行器调用通过步骤完成。长期人工/依赖等待保存在业务条件中，由事件事务和 DBOS 定时补偿触发后续推进；不常驻占用编排队列名额。已持久化的步骤结果可以复用，未完成步骤可能重试；真实操作沿用 Operation 身份先查询后决定执行。每次新副作用与重试都重新检查当前授权、暂停、恢复门禁及资源条件，不能用历史检查点中的许可绕过撤权。

租约失效不代表实际进程已停止；结果未知不代表失败；取消不代表回滚。接管必须查询实际执行，未确认停止前不能释放物理资源或启动冲突操作。数据库迁移等不可确定重放的步骤必须使用对应执行证据，无法确认时进入核对。

## 7. 源码、构建与证据链

每个 Project 有唯一权威 Git 来源。light 新建项目默认使用受管 bare repository，已有项目接入外部权威远端；更换来源需显式迁移。

开发工作区独立，受信任 Git 服务管理元数据和推送权限。沙箱默认仅获得工作文件视图；需要完整 Git 的项目采用隔离 clone。采集提交或快照前冻结所有写入者。

项目级合并队列基于当前权威分支生成候选，验证最终合入提交并进行条件更新。外部提交导致基线变化时重新集成，不覆盖外部工作。

证据关联覆盖有效需求、工作项、源码、构建输入、最终制品和部署计划，使用 D01 的工程引用和输入集合。源码审查、构建输入验证与制品验证分别记录；相同 commit 不意味着不同构建可以复用全部证据。引用、关系和适用性使用 PostgreSQL 表与索引实现。

## 8. Release、审批与部署

Compose 的受支持子集是服务运行声明的权威；ProjectDescriptor 仅补充构建目标、验收、迁移、配置 schema 和发布政策，通过 service key 引用运行服务。环境记录管理实际参数和 secret 版本。解析、校验和冻结后的 Release 表示完整项目版本，固定各服务制品、第三方依赖、运行契约、配置 schema、迁移和来源证据。默认归档交付，Registry 为可选后端；两种方式分别校验相应摘要和实际镜像身份。

默认个人流程自动开发、验证、审查及构建，由所有者批准具体部署。构建前审批按策略启用；重要环境可以要求独立人类审批。Agent 不具备人类批准能力。

DeploymentPlan 同时绑定目标 Release 和起始环境版本，包括配置及 secret 版本、必要的数据库前提、更新顺序、健康窗口和补偿条件。取得环境执行锁后再次检查起始状态；过期计划不能仅因曾经获批就继续执行。Hub 负责生成、批准和提交完整不可变计划，Remote Agent 按有限步骤类型在本地推进并保存权威执行账本，Hub 不另行维护逐步下发的执行循环。

每个新变更步骤默认在线取得绑定计划、步骤、输入、代次及期限的启动许可。失联时未开始的变更等待，当前已获准步骤仅按约定完成或收束到安全点；补偿同样重新确认授权。许可是有明确失效边界的短期授权，不能承诺即时撤回离线执行器已接受的动作。

远程资源按项目、环境、目标与安装实例划分命名空间，主机级资源另行检查冲突。首版采用允许短暂停机的原地更新，不承诺跨服务原子切换。迁移不可逆、部分更新和结果未知均保留真实记录。

standalone 与 managed 使用同组制品，交付包包含独立启动所需内容或明确可用的外部制品访问安排。业务运行、机器重启恢复和重新安装不隐式依赖已经移除的 Hub 私有服务。

## 9. 安全、同步与持续运维

人类、Desktop 会话、Agent、Runner 和 Remote Agent 使用不同身份。服务端按项目、环境、资源和当前策略授权，密钥通过受控机制注入，禁止进入模型上下文、聊天、客户端缓存及公开制品。

预览与管理端使用不同主机名，每个预览实例独立 origin；仅靠同主机不同端口不构成 Cookie 隔离。预览不能获得管理会话或 Tauri 原生能力。

Desktop 使用一致性快照、持久事件游标和聚合版本恢复。界面优先呈现目标、职责、依赖、产物、费用及待决事项，执行细节可追溯。权限撤销使相关订阅和缓存失效。

Remote Agent 提供有界日志、指标、服务检查和固定 runbook。期望状态、实际观测、漂移与历史部署分别记录。默认报告漂移，由授权操作处理；管理通道离线不直接等同于业务故障。

恢复覆盖 Hub 旧备份、目标重启、Agent 本地记录及凭据恢复。普通 worker 重启可以从 DBOS 检查点恢复；从旧备份恢复 Hub 时，先禁止 DBOS 自动启动、出队和重放，核对远端事实并建立新的有效控制代次，再恢复获准流程。业务数据备份由项目负责并纳入部署策略。

## 10. 技术路线与容量目标

Desktop 采用 Tauri、React、TypeScript；控制面采用 FastAPI、Pydantic、SQLAlchemy、PostgreSQL 和 Alembic，Agent 协议运行时采用 PydanticAI，持久调度采用 DBOS Python。Alembic 管理业务 schema，DBOS 系统 schema 使用 SDK 支持的迁移流程。开发与交付复用系统 Git、Docker、Compose 和现成工具链；外部工具经 Gateway 和 MCP adapter 接入。DBOS 不替代 Agent Runtime、业务授权或沙箱，具体复用边界及核验要求见详细设计 06。

正式定义同机 light 和独立 Runner 两种部署档位，使用相同执行协议。Ops Hub 标准硬件基线为 4 核 8GB Linux 主机，不含 Desktop 和远程交付机器；同机 light 在该主机上运行控制面、PostgreSQL 与开发 Runner，调用外部模型 API，重执行串行、预览按需、有界观测。独立 Runner 档位的 Hub 同样以 4 核 8GB 为基线，开发节点按项目需求单独配置并分别核算容量。默认不要求 Gitea、独立 CI、Registry、Redis/Celery 或完整观测栈。

同机内存初始规划为常驻平台预留 2GB、操作系统及文件缓存预留 1GB、突发余量保留 1GB、开发执行共享预算上限 4GB；开发执行包含构建执行器、项目服务、测试数据库、浏览器、预览和全部子进程。具体分配及实际准入由 D03 管理。4 核 8GB 是设计与验收基线，尚非容量实测结论；增加内存不自动提高重任务并发。

模型、工具、工作区和预览分别配额。DBOS 编排、模型调用、重执行和控制操作使用分离的队列及容量；等待批准或回复不占模型和重执行槽。联调环境与浏览器按组合任务预留总资源，物理 ResourceReservation 不随队列槽释放而自动释放。DBOS 的连接池、检查点、历史和恢复开销计入整机预算，P1/P2 即开展代表性容量验证，P6 汇总两档容量结论；不能将组件启动成功当作支持结论。

## 11. 实施主线与验收

|阶段|目标|核心退出条件|
|---|---|---|
|P0 架构接缝|Runtime 接口、DBOS 映射、工程引用和远端计划协议|关键接缝可运行，组件版本与首条链路契约锁定|
|P1 最小执行闭环|基础身份、Runner、受控 Git/构建、Release、审批及独立目标部署|已知前后端数据库项目真实交付，基本取消、重复请求与失联可解释|
|P2 Agent 完整链路|单 Agent 修改、独立验证审查、构建和批准部署|生成代码进入同一链路，费用、上下文与证据可追溯|
|P3 多 Agent 协作|两个开发会话、独立工作区、契约、通信、冲突和返工|真实协作可收敛，续接和输入变化不造成重复执行或误验收|
|P4 可靠性与恢复完善|崩溃窗口、部分部署、撤权、旧备份与升级|执行事实可核对，旧状态不会盲目重放，迁移和补偿范围明确|
|P5 持续运维与扩展|Incident、诊断、受控处置、修复 Task 和适配器|开发交付运维闭环及已支持适配器能力可验证|
|P6 产品与最终评估|完整 Desktop、发行、两档容量及单/多 Agent 效果|完整产品、资源、成本、失败和人工介入记录齐备|

基础 Desktop 随阶段提供。阶段交付物、验收要求和实现选型在详细设计 06 维护；各阶段依据实现成果及验收证据确认完成。基础授权、幂等、隔离、秘密保护和未知结果门禁随 P1 交付；P4 扩大故障与恢复覆盖。P0 冻结核心不变量及首条链路接口，后续 API 随领域逐步冻结，不要求提前定完全部接口。

## 12. 预期成果与主要风险

软件成果包括 Windows/Linux Desktop、独立 Ops Hub、开发 Runner、Remote Agent、多 Agent 协作与远程部署运维闭环，以及可独立运行的示例项目。

研究重点为围绕版本化产物的协作、依赖与动态调度、独立验证驱动的返工、从需求到运行制品的证据关联，以及具有授权、幂等和恢复语义的人机协同执行。

重点风险包括多 Agent 共享错误假设、PydanticAI/DBOS 接缝与工作流升级兼容、低配资源争抢、未知结果重试、不可逆迁移、凭据暴露和设计实现脱节。通过明确状态所有者、成熟组件复用、受限执行、专项故障验证及可追溯文档管理控制风险。实验允许得出受限通过、不支持或多 Agent 未带来收益的结论。
