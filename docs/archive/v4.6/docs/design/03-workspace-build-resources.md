## 1. 权威仓库与项目接入

Project 必须指定唯一权威 Git 来源、目标分支和访问策略，来源可为受管 bare repository 或外部 Git 远端。镜像与开发副本不能成为第二套隐式权威。

light 新建项目默认由受信任 Git 服务创建受管 bare repository，支持平台内审查、项目级合并和源码导出，不要求安装 Gitea。bare repository 受项目授权与备份策略保护，不直接暴露匿名文件访问。

已有项目接入时登记外部权威远端、目标分支、认证引用及访问能力。凭据仅交给 Git 服务。无推送权限时明确显示只读接入，不能把本地分支更新显示为已经合入外部仓库。

权威来源迁移需冻结写入、同步并校验 refs、更新来源版本、恢复写入；失败保持原权威，不自动双向镜像。webhook 只作通知，周期 fetch 补偿漏报。

接入检查包括锁文件、Dockerfile、Compose 支持子集、CloudHelm 薄扩展、构建命令、目标架构、配置 schema、迁移与健康接口；按 D04 校验唯一字段来源和不支持能力，并识别 Git LFS、submodule、依赖 Git 元数据的版本生成等需求。无法支持的项目返回具体限制，不能把文件占位内容当作完整源码。

## 2. 工作文件与 Git 元数据

WorkItem 从精确 base_commit 创建独立 worktree，Task 有集成分支，项目有目标分支。Workspace 保存 repo、commit、owner、workspace_revision、写入权及代次、工作文件位置、执行模式、配额、状态和保留策略。紧急修复按 D05 从实际运行基线创建，不默认取当前主分支。

默认由 Runner 构造不含共享 .git 指针及目录的工作文件视图，沙箱只操作该视图。受信任 Git 服务提供限定的 status、diff、commit 和候选提交工具，验证归属、路径与参数。

Git 服务禁用仓库 hooks、外部 diff、textconv 和过滤器等不受信任执行配置，使用受控环境与参数调用，不将仓库提供的命令拼接成宿主 shell。路径授权在解析符号链接后核对边界，并防止检查后路径被替换。

提交与构建输入采集使用短时冻结全部写入者或经过验证的一致性快照。冻结范围包括测试服务、watcher 和后台子进程；普通复制不能在写入期间冒充一致性快照。固定并校验源码候选后即可恢复开发，验证/构建在独立候选位置执行，不持续占用开发工作区写锁。既不能冻结也不能取得一致快照时拒绝采集并报告原因。

需要完整 Git 的项目明确选择隔离 clone，Git 在沙箱权限下运行，不共享可写元数据，不注入长期推送凭据。LFS/submodule 等获取由受控接入流程完成；禁用过滤器的默认模式不能静默承诺兼容所有仓库。

缓存以只读共享或由受控服务写入为主。不得让不可信沙箱共同写同一个依赖目录；缓存来源、键及失效边界应可追踪，避免跨项目污染。

### 2.1 开发、候选与制品环境生命周期

|用途|固定或可变输入|输出与回收|
|---|---|---|
|日常开发|可变 Workspace，固定工具链；增量安装、开发服务和按需预览|快速反馈，不直接充当最终候选证据；空闲可休眠|
|候选验证|精确 commit/快照、AcceptanceSuiteRevision、测试配置与数据集版本|独立环境生成正式证据，完成后按保留策略回收|
|制品验证|最终镜像身份、运行契约、测试环境输入|生成制品证据；与目标环境检查分别记录|

工作区环境记录工具链引用、依赖缓存键、初始化与启动入口、测试数据版本、实际运行源码修订、资源组、预览路由和最近活动时间。环境状态区分 preparing、ready、suspended、failed、disposed；ready 需要当前进程与就绪证据，不仅是目录存在。项目开发/测试命令归薄扩展，受限 Runner 执行；不重复定义 Compose 服务运行字段。

依赖缓存至少按项目/信任范围、工具链、OS/架构、锁文件与影响安装的参数区分；锁文件变化使不匹配缓存失效。下载缓存、构建缓存与工作区内可变依赖分别管理，不能将可写 node_modules 等目录作为跨项目公共缓存。验证环境按固定输入恢复，不能继承未记录的开发机状态。

测试数据使用版本化初始化、迁移及重置入口，可重复生成；测试库/卷与用户预览分别命名并隔离。正式验证不得无说明地复用已经被人工修改的数据。默认使用合成数据；导入业务数据须有授权与脱敏记录，不复制生产秘密。初始化失败保留原因，不将未准备的数据集标为 ready。

预览显示用途、实际运行修订、更新时间和数据集；热更新尚未确认时显示 pending/stale，不把编辑器当前文件版本直接显示为运行版本。休眠先撤销路由或标记不可用，再确认进程停止、回收可释放资源；恢复重新准入并检查数据、配置和就绪。恢复无须盲目重新安装相同依赖，但失败或失效缓存不可跳过检查。三个用途共同计入第 4～5 节预算，预览恢复不抢占正在验证所需的组合资源。

### 2.2 人工接管与交还写入权

接管通过应用命令和 expected_workspace_revision 发起，保存操作者、范围、基线及原因。写入权区分 agent_owned、handoff_pending、human_owned、return_pending；这些是 Workspace 控制信息，不替代 Task/Operation 状态。

1. handoff_pending 阻止新的相关 Agent 写操作，执行器在同一写入门禁下停止或冻结现存写入者；模型可以结束当前请求，但旧结果无权写入。
2. 确认全部相关写入者停止后固定接管基线和新的写入代次，才登记 human_owned。写入者未知时保持待核对，不因页面超时直接交权。
3. 用户经服务端受控编辑或 patch 接口修改，校验身份、路径、base revision 和写入代次；Desktop 不运行本地 Git/工具链。并发版本不符拒绝覆盖，提供差异和显式合并入口。
4. 交还时禁止新的人工写入，固定修改快照、差异和新 workspace_revision，恢复 Agent 写入代次。按 D01 重新判断工作项、验收和证据，向 Session 注入修改引用；必要时切换 Epoch 后才继续。

接管只冻结相关工作区的冲突写入，影响范围外工作可继续。交接使用稳定 handoff_id 和 D02 的执行/核对记录，业务事务提交不等于执行器门禁已切换；任一端崩溃后查询原交接进度，确认新代次后才开放对应写入，不因重投发放第二份写入权。关闭页面、离线或期限到期不自动交还；外部 Git 提交仍按权威基线变化处理。工作区清理须先确认交接和写入已结束。

### 2.3 可选沙箱临时部署与人类测试

AI 生成代码通过自动检查后，提供可选的人类实际操作测试。项目可保存默认选项，初始为关闭；用户可按 Task 或 ReleaseCandidate 显式开启。未开启显示“未执行人工测试”，不创建强制等待，也不生成“人工通过”证据。该环节使用固定候选/制品在开发执行区临时部署，不替代自动验证、正式验收资产或正式目标的部署审批。

推荐位置为候选构建和必要自动检查通过后、形成可发布 Release 前。运行在 Ops Hub 的开发沙箱或获准独立 Runner，由受限执行器启动前端、后端和必要测试数据库，使用固定镜像身份、测试配置及独立数据集。复用 D04 已验证的运行契约和参数绑定规则；执行走开发 Operation，不将临时环境登记为生产 EnvironmentBinding，也不向正式交付机器部署临时调试服务。

HumanTestSession 的测试记录由 integration 管理，workspaces 管理临时环境，execution 保存启动/停止事实。记录至少包含 session_id、Task/候选引用、被测制品集合与 InputSet、需求/验收修订、测试配置/数据集、环境实例、负责测试的用户、访问入口、期限、反馈和处理记录。生命周期分为 preparing、awaiting_human、testing、completed、expired、cancelled；完成结论单独保存 passed、changes_requested 或 skipped。准备失败和资源等待有明确原因，不能把未就绪环境标为已交付测试。

流程如下：

1. 用户开启后固定被测版本，申请完整资源组并临时部署；只有服务就绪、访问授权有效时才创建人工待办。
2. 向指定人类提供带版本标识的入口、变更摘要、建议测试步骤、预期行为、已知限制和到期时间。需要测试账号时通过受保护入口领取最小权限的临时测试身份，不在聊天、通知或报告中显形显示密码/密钥。交付通知规则见 D05。
3. 人类实际操作并提交“通过”“需要修改”或“跳过”，反馈可包含步骤、预期/实际结果及经授权的附件。Agent 可以整理反馈、建议用例和修复，但不得代填人类结论；打开链接、通知送达或自动浏览器成功均不算人工通过。
4. “需要修改”形成关联返工：原 Task 未完成时按工作项流程处理，已经完成时创建关联修复 Task。修复产生新候选/镜像及新测试轮次，原测试事实保留；不在测试中的实例上偷偷热更新代码。需求新增另走需求修订，不能把反馈直接当作已批准需求。
5. 当前轮次通过或由有权用户明确跳过后，才解除该候选已选择的人工等待；跳过记录操作者、原因和时间，不生成通过证据。未反馈、超时、失联、准备失败或取消都不能自动解除为通过；用户可选择重建继续测试或明确跳过。发布侧判断归 D04。

人工结论生成独立 EvidenceRecord，绑定实际被测制品、配置、测试数据基线、验收范围和测试者/时间；测试数据重置操作也保留记录。不同源码、制品、构建变体、行为相关配置或验收范围变化时重新判断适用性，旧结论不得自动用于新版本。可变开发预览上的体验反馈可作为问题线索，但不能直接替代固定版本的人工测试证据。

等待人类时不保留活跃 AgentRun、模型请求或常驻编排等待。环境仍运行时继续占用真实 ResourceReservation；准备/构建消耗重执行容量，人类等待不占该队列槽，但环境占用可能阻止其他重任务准入。临时环境与普通预览共享当前按需预览上限及 4GiB 开发执行预算，不额外承诺一个免费实例；超过能力时排队或使用已配置的合适 Runner。

设置有效期、空闲回收和可见的资源让出规则。暂停、到期或为紧急任务回收前提示测试者并保留已提交反馈；访问中断后需要明确恢复/重建，不能以旧路由表示环境可用。结束、跳过或取消后撤销路由/票据及测试身份，确认进程停止后释放资源，按策略清理临时卷与测试数据。保留问题附件和证据引用，不持久保留无用运行环境；待提交的浏览器数据不保证能在回收后恢复。

### 2.3.1 人测期限、续期与资源让出

以下是容量验证前的初始策略值，P1/P2 根据实际记录再确认支持范围。资源排队时 HumanTestSession 保持 preparing，不展示可用测试入口；资源排队时间不计入本轮有效期。服务和授权均就绪时记录 ready_at，并据此计算测试期限。

|参数|初始值|行为|
|---|---|---|
|空闲提醒|连续 30 分钟没有人类有效活动|发出回收提醒；自动健康探测和后台心跳不算人类活动|
|提醒宽限|提醒后 5 分钟|允许完成当前操作或提交反馈；宽限结束后进入安全停止流程|
|初始硬期限|ready_at 后 4 小时|到期前提示；到期后请求安全停止，不因持续探测或活动自动延长|
|手动续期|最多一次，增加 2 小时|到期前由当前有权测试者申请，重新检查当前授权、共享容量和紧急等待|
|续期总上限|ready_at 后 6 小时|续期结果明确显示原硬期限、获准后的硬期限及本轮总时限上限|
|普通预览与人测|共享 1 个预览槽|界面显示占用者、排队原因和可能的让出时间|

人类有效活动指该测试者在有效授权下进行的实际操作或反馈提交；探测、服务自检和无人操作的页面心跳不能刷新空闲时间。续期未获准时保留原硬期限，不延长会话。暂停、停止请求、票据撤销或租约到期本身均不证明进程已停止；停止未确认时仍按第 4 节占账，并阻塞冲突资源。

资源让出按以下顺序处理：

1. 已结束、已跳过、已取消或已到硬期限的环境，进入停止确认和回收。
2. 空闲且等待人类开始的环境。
3. 空闲中的测试环境。
4. 正在操作的测试环境；先通知并给出宽限，再按该执行器声明的安全停止方式处理。

只有第 4.1 节规定的已授权紧急优先级可以请求普通环境让出；界面同时说明请求者、原因、通知宽限和停止确认状态。未知或不可安全停止的执行继续核对，不因紧急请求或期限到期而直接释放。

回收时撤销入口票据、专用会话、临时测试身份和已有连接；确认进程组停止后才释放资源。已提交的反馈和结论保留；已完成且绑定当前候选的人测 passed 证据不因环境回收自动失效，适用性仍按制品、配置、数据基线和范围判断。未完成的人测不得标成 passed。

同一候选重建时创建新的环境实例和访问授权，并记录数据重置或配置变化，候选和本轮身份保持可核对。新候选必须建立新的测试轮次；旧页面只能向原轮次提交，服务端核对候选与轮次后拒绝将旧结论写入新候选。页面需明确提示回收时未提交的操作、文本和附件可能丢失；若实现草稿保存，草稿绑定候选与轮次，重建或候选变化后不得自动转为正式反馈或结论。

## 3. 沙箱与构建执行器

开发沙箱使用 Docker，限制 CPU、内存、PID、用户、挂载、执行时间和网络出口。执行器检查宿主实际支持的资源限制；磁盘配额能力不足时明确限制支持范围，不能把逻辑计数当作硬隔离。

沙箱无控制面数据库、宿主 Docker socket 和远端部署凭据。Runner 的宿主控制接口仅允许已注册操作，不接受任意挂载、特权参数或宿主 shell。

按需镜像构建优先验证受限 rootless BuildKit 方案，宿主 Runner 管理生命周期，构建输入经受控接口提交。具体内核、cgroup、存储驱动及网络兼容性在 P0/P1 核验后固定；不支持时停止构建或使用已配置的独立受限 Runner，不偷偷向沙箱开放宿主 socket。

构建容器、浏览器、扫描器和预览按需启动。基础镜像和工具链固定可追溯身份，扫描器数据库等可变化输入记录版本与时间。Docker 隔离不被视为任意恶意多租户的完整宿主安全保证。

私有依赖访问按用途提供短期凭据或受限代理，禁止把部署凭据复用到构建。仓库代码可能读取构建过程中可访问的凭据，因此必须先限制权限和出口，不能依赖日志脱敏独自防止泄露。

## 4. 资源预留与组合任务

模型调用、工作文件、执行进程、预览分别计量。4 核、8GiB 规划的同机基线初始建议上限为 3 个模型调用、2 个活跃开发 Task、1 个重执行槽和 1 个按需预览；这些是数量上限，不保证可以同时满额运行。每个 Task 可以有多个协作 Agent，但其工具和后台进程共享同机执行预算；最终准入以实际 CPU、内存、磁盘和进程需求为准。内存增加不自动提高重执行并发。

工作队列采用 D02 的 DBOS orchestration、model-calls、heavy-execution、control，定时维护使用独立 maintenance 队列。人工/依赖/所需工具结果等待保存在业务层，结束当前有界 AgentRun；提交长任务本身只等待可靠回执，条件满足后可靠入队下一 Run。审批待决不保留常驻工作流。短流程内部等待及 DBOS 定时任务仍可能占队列容量，维护等待独立限额，不能挤占 control 的取消、查询和步骤许可。

worker 队列槽、真实模型请求、数据库连接、线程池和物理资源分别预算。PydanticAI 内部工具并发不直接获得执行资源，批量工具由 Gateway 分类准入；结束 Run 不释放仍在执行的 Operation 占用。

ResourceReservation 至少保存 owner、资源组、host_resource_pool_id、executor_instance_id、带单位的请求量、硬上限、租约、状态和释放证据。reserved、active、releasing、orphaned、released 分开；前四种状态在尚未确认释放时继续占用账本，租约失效将其送入核对，不能直接变成 released。DBOS 重放、任务失败或取消即使释放了队列槽，也不能释放尚未确认停止的进程占用；新重任务在启动前仍必须经过物理预留检查。

重执行包括依赖安装、编译、镜像构建、浏览器测试及全栈联调。轻量模式同时只准入一组重任务；普通任务公平排队，获准紧急任务按第 4.1 节处理。预算耗尽或超出机器能力时明确退出或等待用户决策。

集成测试采用组合资源组：被测服务、数据库、浏览器和测试命令一起计算总需求，组内子步骤消费父级预留，不再次申请唯一重任务槽。避免“服务占槽等待浏览器，浏览器等待服务释放”的死锁。

用户预览与测试环境分别标识，并共同计入第 5 节的开发执行共享预算。构建或测试准入时计入已运行预览及后台服务；资源不足可按可见策略暂停普通预览，确认进程停止后再回收额度。运行测试的依赖环境必须纳入组合资源组，不能随意回收。单个组合任务超过总容量时要求更大 Runner 或调整项目执行方案，不能仅靠排队解决永远无法容纳的任务，也不通过拆分预留隐藏并发峰值。

控制查询、取消、心跳和回报使用有界独立容量，不能排在长构建之后。DBOS control 队列与接收回报的 API 保留连接池、异步循环和有界线程池容量，不能只按队列名称分离却共用已耗尽的阻塞资源。CPU 和内存配额必须覆盖进程树；磁盘与网络 I/O 同样可能拖慢数据库，需要测量并在可用情况下限流。

### 4.1 紧急修复的优先级与预算

紧急级别由具有相应权限的人或预先批准的 Incident 政策赋予，记录 Incident、范围、原因、期限和授权身份；Agent 自报紧急不获得优先级。调度采用 emergency/normal 两类业务优先级，普通任务使用等待时间保护，设置紧急占用时间/连续任务上限及升级提示，防止长期饥饿。具体参数在容量验收前固定，不能为一次故障无限扩大。

优先级经 D02 核验过的 DBOS 能力实施，不增加物理重执行槽或第二套调度引擎。只对已满足依赖、授权和预算的任务优先准入；无空闲资源时显示阻塞者、是否可中断及已知剩余时限，不假定能立即抢占。普通构建若已声明可安全取消，可按当前授权停止整个进程组并在确认结束后让出资源，重新排队沿用业务引用并记录取消成本。迁移、不可安全中断或结果未知的占用保持核对，不为紧急任务强制释放。

EmergencyBudget 作为现有预算账本中的独立额度类别，绑定 Incident、金额/调用/时间上限、授权人和有效期。普通预算耗尽时只有明确获准的应急额度才可继续，不能自动透支。逐真实模型请求仍预留费用，未知 usage 继续保留；不得通过换预算池重复执行或释放未知预留。已耗费用和失败成本计入修复统计，结束时按结算规则释放剩余额度。

4 核、8GiB 规划的同机资源池仍只有一组重执行，模型全局上限仍为 3。独立 Runner 仅可在能力和权限匹配、实际有余量时承接紧急任务，不自动搬移正在写入的工作区。演练需覆盖普通长构建占用、预算耗尽及不可中断任务，记录修复等待时间和控制响应。

### 4.2 共享宿主资源池与计量

资源池按实际共享资源的宿主划分，host_resource_pool_id 标识该池，executor_instance_id 对应 D02 ExecutionAttempt.executor_id，标识其中一个 Runner 实例；池身份与 D02 执行器身份分别记录，不能互相替代。同一宿主的多个 Runner 实例共享同一份开发预算、物理余量、冲突账本和重执行槽；增加 Runner 进程不会为每个实例复制一份内存额度或重执行槽。独立节点分别登记自己的资源池、经核验容量和能力，只有这些独立物理资源才能另计。

资源请求使用规范化的整数单位，按维度分别准入：

|维度|请求单位|约束|
|---|---|---|
|内存|MiB|覆盖服务、浏览器、构建器及全部子进程；限制能力须由宿主/容器实测确认|
|CPU|毫核，例如 1000m = 1 vCPU|计入该宿主池全部开发进程树，不以 Runner 实例分别重置总额|
|临时磁盘|字节|包括下载、解包、镜像加载、构建缓存和同时存在的中间文件峰值|
|进程|PID 数量|覆盖后台和全部子进程|
|并发|按类别的整数槽数|同机重执行槽合计上限为 1；普通预览与人测共用 1 个预览槽|
|互斥资源|稳定冲突键|例如工作区写入权、环境实例或宿主端口；所有入口使用同一规范化键判冲突|

既有容量文字中的 8GB 和 4GB 是规划简称，分别按 8GiB = 8192MiB、4GiB = 4096MiB 理解，不表示十进制 GB 的计量契约。内存请求、限制、预算和账本使用 MiB 整数。每一资源维度的有效准入上限取配置预算与宿主可分配实测容量（扣除系统/平台必要保留及池外占用）中的较小值；已映射到预留的进程用量由预留账本计一次，监测值用于发现超限，不再与该预留相加。无法映射到预留的占用要保守扣减可分配实测容量并限制新准入。

资源池的已占账量是该池全部未释放预留请求之和，包括 reserved、active、releasing、orphaned；再加上尚未归属且尚未计入实测容量扣减的保守占用。只有每个维度的“已占账量 + 新请求”均不超过有效准入上限、所有稳定冲突键无冲突，且所需能力已核验，才可接受。实际使用持续超过预留或硬限制无法执行时立即限制后续准入并记录超限；不通过抬高预算或重复记账掩盖实际压力。释放只依据已证明未启动或进程组停止的证据；租约到期、执行器失联及回执丢失继续占账。

同机 8GiB/4GiB 数值仅描述容量规划，不代表实测承诺。执行准入仍按上述资源池账本和宿主可分配实测量逐维计算；如果平台常驻或系统占用提高，应降低开发执行可用额度。独立 Runner 的容量和资源限制单独测量，不能用 Hub 的余量代替。

### 4.3 Hub 原子准入与执行器确认

一次资源申请先由 Hub 对共享资源池完成原子记账，再由执行器在本地持久确认。Hub 数据库事务与执行器本地账本事务各自原子提交；两者之间只能依靠稳定身份、幂等回执和差异核对衔接，不能描述为跨机器原子事务。

1. Hub 在短数据库事务中锁定资源池账本行或比较并更新条件版本，按调用方/业务范围校验幂等键与规范化 request_digest；摘要覆盖资源组、目标资源池、各维度请求量、硬限制及稳定冲突键。事务检查当前授权、操作期限、取消状态、资源容量和冲突键，并一次预留整组资源。相同身份与摘要返回原 reservation_id；同一幂等身份摘要不同则拒绝。
2. 同一 UnitOfWork 保存 ResourceReservation、领域事件、必要 Outbox 和 WorkflowBinding；若使用 D02 已核验的同库 DBOS 事务入队能力，也在该数据库事务中写入必要入队记录。提交后才允许 Outbox/worker 与执行器通信。网络调用、等待 Runner、创建容器和启动进程均不得放在 Hub 事务内。
3. 执行器按 host_resource_pool_id 的共享本地账本/锁串行化同宿主多个 Runner 的竞争，使用 reservation_id、operation_id、request_digest、hub_incarnation、resource_generation 和 executor_id（即本文件的 executor_instance_id）建立幂等记录，检查本地冲突与能力，并在本地事务持久写入接受或拒绝事实后返回回执。hub_incarnation 是单独的控制信任标识，resource_generation 按 D02 作为目标资源的单调代次；重投沿用原记录，不同摘要、过时代次或未获准的 incarnation 不能覆盖原接受事实。
4. 获得本地接受确认后，启动门禁再次读取当前授权和期限，检查取消/维护状态、真实可用资源及冲突键。通过后写入启动标记和 ProcessBinding，把容器与完整进程组绑定到 reservation_id、operation_id 和 resource_generation，再启动并回报实际事实。若取消、授权撤销、请求过期或资源条件变化而拒绝启动，执行器必须在与启动相同的本地锁内持久关闭该分配为 closed_unstarted，并保证所有重复消息都不能再启动；无法完成关闭时保持 unknown 并继续占账。
5. Hub 等待回执超时或执行器拒绝时先查询原 reservation_id、operation_id、hub_incarnation、resource_generation 和 executor_id。不得直接创建第二份预留或改用新幂等身份绕过不确定结果。只有执行器证明没有进程启动，且已在同一本地启动锁/账本中持久关闭该分配、所有重复消息都不能再启动，Hub 才能结束原预留。该条件同时适用于从未接受的请求和已接受但被启动门禁拒绝的请求；单纯观测不到进程不构成释放证据，启动未来仍可能发生时结果保持 unknown 并继续占账。

组合任务在服务、数据库、浏览器和测试命令启动前一次性申请完整资源组，任一部分不能准入时整组不启动。子步骤消费父级 ResourceReservation 的份额，不为同一已计入资源再次申请预算或重执行槽。资源变化必须通过 adjust_reservation 明确增减，在 Hub 与执行器两端增量检查容量、能力和冲突；现存占用未知或停止未确认时不能缩小对应额度。需求永久超过执行器能力时明确返回“当前执行器无法容纳”，要求调整方案或选择容量匹配的 Runner，不无限排队，也不通过拆分预留隐藏峰值。

### 4.4 Hub 与执行器差异核对及证据

|差异|处理规则|
|---|---|
|执行器已接受，Hub 回执丢失|查询原 reservation_id、operation_id 和代次；从本地持久接受记录恢复回执，不新建预留|
|Hub 有预留，执行器从未接受且未启动|执行器在同一本地启动锁/账本中持久关闭原分配、拒绝所有晚到重复消息后，Hub 按原分配保存未启动证据并释放|
|执行器已接受，但启动门禁因取消、撤权或期限拒绝|执行器持相同本地启动锁持久记为 closed_unstarted，并封闭所有重复消息的启动路径后，Hub 才可释放；只观察不到进程仍保持 unknown 占用|
|Hub 认为执行结束或已释放，执行器仍有进程|转入 releasing/orphaned 核对，继续占用预算和互斥键，确认进程组停止后才能释放|
|发现未登记或无法归属的占用|按保守规则扣减该资源池可分配容量，限制相关新准入并调查归属|

P1 基本证据应覆盖并发申请不超分配、重复投递返回同一接受结果、不同 request_digest 被拒绝、接受回执丢失后查询原账本、以及停止未知时预留和冲突键仍被保留。P4 扩大到 Hub/Runner 重启、执行器账本损坏或不完整、代次变化、Runner 接管及重新核验容量与进程的情形。证据记录请求摘要、资源池与执行器身份、代次、状态转换、实测偏差和释放依据。ResourceReservation 继续作为资源账本与启动门禁；DBOS 仍是唯一持久执行底座。

## 5. 部署档位与容量预算

两种档位均为正式支持方向，Ops Hub 标准硬件基线统一为 4 核 8GiB 规划值；能力和支持结论分别维护，独立开发节点按项目需求另外配置。单 DBOS worker 的初始控制面拓扑不因增加 Runner 改变。

|档位|部署方式|准入和统计|
|---|---|---|
|同机 light|控制面、PostgreSQL、开发 Runner 在同一台 4 核、8GiB 规划 Linux 主机|按整机基线验收；重执行串行，统计全部常驻与组合任务峰值|
|独立 Runner|4 核、8GiB 规划 Hub 与开发执行分离，可配置一台或多台独立 Runner|执行节点按需求单独配置；按已核验能力和剩余容量准入，Hub 与全部节点分别报告资源|

Runner 注册 executor_instance_id，并关联 host_resource_pool_id；前者标识 Runner 实例，后者标识实际共享宿主及其唯一资源账本。Runner 另行登记 OS/架构、容器/构建能力、CPU/内存/PID/磁盘限制支持、允许工具链和协议版本；声明需接入验证并结合实时占用，不能仅信任静态自报。同一宿主池中的多个 Runner 共用一组重执行槽和池预算；首次每个共享宿主池的重执行合计按一组准入。独立节点按自己的池容量及能力准入，增加并发须单独测量。调度依据 Operation 需求匹配，无法支持时明确等待或失败，不把任务静默送到未经授权节点。

工作区与数据位置固定到所属执行器；迁移通过不可变源码/制品引用及新的 Workspace 显式进行，不因控制面认为节点空闲就复制仍有写入者的目录。两个档位沿用相同身份、执行账本、资源协议和证据要求。

### 5.1 4 核 8GiB 同机 light 初始预算

|项目|初始规划|验证要求|
|---|---|---|
|常驻平台|预留 2GiB（2048MiB）|包含 API/DBOSClient、PydanticAI/DBOS worker、PostgreSQL、Docker/Runner、代理及 SDK 缓存和连接池；这是预算，不是实测占用|
|操作系统及文件缓存|预留 1GiB（1024MiB）|记录宿主基础占用与缓存压力，不与容器已计量缓存重复相加|
|未分配突发余量|保留 1GiB（1024MiB）|应对控制请求、检查点、回报和资源峰值；不作为正常执行额度提前分配|
|开发执行共享预算|初始上限 4GiB（4096MiB）|所有开发 Task 的构建执行器、项目服务、测试数据库、浏览器、预览、watcher 和子进程合计，不是每个任务各有 4GiB|
|Swap|只缓冲短时峰值|不计入正常可承诺容量|
|磁盘|建议 SSD，容量按项目实测|包括源码、缓存、镜像层、归档、临时解包、日志和数据库，验收记录空间峰值及 I/O 争用|

8GiB = 8192MiB 指整台 Ops Hub，不含 Desktop 与交付机器。上述四项内存规划合计 8GiB；这些数字是资源规划预算，不是实测占用。开发执行准入按第 4.2 节逐维取配置预算与扣除必要保留后的宿主可分配实测容量较小值；平台实际占用超出保留时降低执行额度，不挤占必要余量。待 P1/P2 测量后修订具体配额。

同机全部开发执行的 CPU 总配额初始不超过 3000m（3 vCPU），为操作系统和控制面留出约 1000m（1 vCPU）的规划余量；具体 CPU 调度保障及控制延迟在 P1/P2 验证。构建器、测试运行器和浏览器的内部并发须显式限制，配额覆盖全部子进程。PostgreSQL 的连接、查询内存与 SDK 连接池按常驻平台总预算配置，不能按单个连接池独立放大。

DBOS 无独立编排服务器，不表示没有增量开销；检查点写入、历史、定时流程、连接池和恢复峰值均计入预算。上表为 4 核 8GiB 的设计规划，不是 SDK 实测值或任意项目都可运行的承诺。

先支持代表性小型 Python/Node Web 项目，大型 Java、复杂前端和长浏览器套件需单独验证。P1 在真实 4 核 8GiB 整机测空载、有界推进、持久等待记录、worker 重启和已知项目完整交付；P2 测 Agent 驱动的全栈组合任务、预览竞争及控制响应。若超出同机容量，修订同机支持范围；采用独立 Runner 时作为另一档位报告，不能记作完整功能同机 8GiB 通过。OOM、磁盘不足和系统压力必须形成可理解的失败分类，不能无限提高上限重试。

## 6. 构建输入与验证证据

BuildRun 绑定 D01 的不可变 InputSet，至少包括源码 commit/快照、Compose 源及参数化运行契约引用、ProjectDescriptor 薄扩展修订、构建步骤、工具链镜像、基础镜像解析结果、锁文件、目标平台和影响构建的参数。构建配置与部署环境配置分开；编译进产物的环境差异属于新的构建变体，测试运行配置由对应 EvidenceRecord 单独绑定。敏感参数只保存受控引用，不进入公开摘要输入。

同一 commit 采用不同参数、架构或外部描述文件时属于不同构建输入。复用产物须证明输入等价，不仅比较源码 SHA。不可固定的外部依赖应记录解析结果及限制，不能承诺未实现的可复现构建。

|证据|绑定对象|用途|
|---|---|---|
|源码测试与代码审查|精确 commit、验收版本、测试工具及环境|证明源代码层面的检查范围|
|构建与来源记录|输入摘要、执行提供方、工具链、构建结果|关联源码与制品来源|
|制品扫描与运行验证|镜像/制品身份、架构、运行契约、测试配置|证明实际交付对象通过指定检查|

上述报告使用 D01 的 EngineeringRef/InputSet/EvidenceRecord 统一身份和适用范围，各生产领域保存原始事实，交付领域在形成 Release 时重新检查适用性版本。输入变化按显式依赖传播，不能仅凭报告曾经通过就复用到新构建。

构建完成后对最终镜像执行必要的启动、就绪及关键业务检查，再形成可供 Release 使用的证据。宿主受信任采集器计算制品摘要并记录构建来源，不直接信任仓库脚本自报的“通过”或制品身份。

外部 CI adapter 保存提供方 run 引用，重复触发和丢失回执按 D02 核对。CI 没有目标机器部署权限，不能自行越过 Release 和 DeploymentPlan 流程。

### 6.1 正式验收资产与结果完整性

AcceptanceSuiteRevision 由 integration 管理，固定脚本/工具的不可变来源、执行入口、关键断言或必需用例、允许跳过规则、适用需求/契约、测试数据和确认记录；通过 EngineeringRef 进入 InputSet。仓库内可保存源文件，但被用于正式验收的修订由平台固定并只读提供，候选代码不能替换验证入口或降低通过阈值。

开发 Agent 可以增补普通测试；修改正式验收入口、关键断言或跳过规则须产生新修订，按项目政策由有权身份确认后生效。开发任务无权自行降低当前固定要求，Agent 的“测试已调整”不构成批准。验证环境从独立受控来源加载固定验收资产，仓库配置不得静默改写选例或排除规则；不兼容时报告待修订，不能自动迁就候选代码。

报告记录预期与实际执行用例集合/数量、通过/失败/跳过及理由、缺失检查、数据集、源码/制品身份、验收修订、环境输入和输出来源。受信任采集器核对执行入口及报告完整性，必需检查缺失、被跳过或未运行时不能仅凭退出码 0 通过。大型报告进制品存储，数据库保存有界摘要和引用。

正式验收修订变化按 D01 重判消费者证据，历史报告保持原结果。人工代码接管不会自动修改验收版本。独立验收证明固定检查的范围，不宣称能够证明所有业务行为正确。

## 7. 集成与项目合并队列

任务内 IntegrationAttempt 固定候选提交集合，冲突反馈为明确返工。项目队列每次读取权威目标分支，生成精确合入候选，取得所需验证与审查，再以预期旧 SHA 条件更新。

分支变化时重新集成，并按证据适用范围决定重跑；不能沿用针对其他 SHA 的结论冒充验证通过。PR 合并如果重写 commit，必须验证其最终实际版本。外部提交会触发基线影响分析，但不自动 rebase 所有长期工作项。

共享文件可在调度层串行处理；实际文件访问仍由沙箱和路径授权保证。WorkItem 局部测试通过不等于项目集成通过。

集成与构建的流程推进使用各自领域定义的 DBOS 工作流，MergeQueueEntry、IntegrationAttempt、BuildRun 和验证报告仍由各自领域保存。按 project_id 进行的队列分区可辅助串行化，但最终合入必须保留目标分支 SHA 条件更新；DBOS 重放复用既有候选引用，不自动重新采集不同代码并沿用旧输入摘要。

## 8. 费用预留与未知 usage

每次真实模型请求前在并发事务中预留费用，包括 PydanticAI 校验修复、模型/传输重试和压缩请求，按输入估算、最大输出和已知提供方计费项计算保守上界。未知缓存收益按普通输入计算，不能先假定命中以降低预留。

请求完成后按真实 usage 和对应价格版本结算；缺失字段保持 unknown。超时、连接中断或取消可能已经发生费用，不能立即释放全部预留并重试。

费用预留和结算以真实 ModelRequestRecord 身份幂等处理。DBOS 已完成 step 的重放不重复预留或结算；若请求已发生而检查点未保存，先查询已登记结果和提供方记录，再按未知费用规则决定后续动作。SDK 自动重试不得隐式绕过每次真实模型调用的费用准入。

未知费用保留待核对预留，尝试获取提供方记录；无法核对时按已批准的保守计费规则占用预算并标记估算。超出可计算的最大费用或提供方语义不明时，设置更低并发、明确风险预算并限制重试，不声称严格预算保证。

缓存创建、读取、输出和压缩请求分别计入，避免同一 token 双计费。报告同时给出实际与估算费用、未知记录和统计覆盖率。Task 暂停后不得为缓存保温继续请求。

## 9. 保留、清理与交付

工作区清理前保留必要 commit、patch、报告和恢复引用。制品、镜像层、下载归档和缓存分别设配额；原始日志与大型工具输出不能无限写入数据库。

DBOS workflow/step 的输入输出只保存有界结果、版本、摘要和制品引用，不重复存整份仓库、镜像、完整模型上下文或逐 token 日志。活跃 DBOS 流程、持久 Session/WaitCondition、InputSet/DependencyLink 和未解除的恢复引用进入垃圾回收标记集合；检查点历史的保留与清理由 D02 规定。

垃圾回收先计算当前运行、回滚候选、进行中操作、未完成任务和用户保留标记的引用集合，采用标记与延迟删除，在最终删除前重新确认引用。存在新引用或结果未知时跳过，不与部署下载争删文件。

磁盘预检包括归档、解包、docker load 和镜像层的并存峰值。制品落盘采用临时内容、完成校验和原子发布；未校验文件不进入可用索引。

P0/P1 核验 Runtime/DBOS 接缝、仓库、构建及基本资源协议；P1/P2 形成早期整机和 Agent 链路容量记录，P3 记录协作开销，P6 汇总同机 light 与独立 Runner 的持续容量和支持范围。验收要求见 D06。
