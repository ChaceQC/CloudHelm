# 06 实施计划与验收

> 文档版本：v4.3.0
> 对齐总体设计：v4.3
> 修订日期：2026-10-07
> 文档性质：实施计划与验收要求。

[返回文档索引](README.md)。本文件说明实施阶段、验收要求、组件复用和效果评估方法。

## 1. 实施原则

按照完整平台目标，优先贯通确定性构建与远程交付，再接入 Agent 代码生产、多 Agent 协作和完整运维体验。每个阶段交付运行实现、配套契约和验收证据。

基础 Desktop 随阶段提供，P6 完成体验与发行。身份、权限、执行恢复和资源边界从底座阶段建立，不推迟到发布前补做。

持久调度固定采用 DBOS Python；不再实施自研 WorkflowJob 领取、调度租约和通用重放器。首条部署为 FastAPI + DBOSClient、单 DBOS worker、同库不同 schema 的 PostgreSQL 及受信任 Runner，默认无需独立工作流服务器或 Conductor。DBOS 的原子入队、恢复和队列能力在早期验证，不能等全部业务开发完成后再确认底座假设。

每个阶段记录实现版本、输入项目、使用环境、验证结果及支持范围。验证范围依据阶段交付和实际变更确定。

跨阶段能力逐步验收，例如 P1 验证仓库创建与读写，P3 验证多任务与外部提交的集成。各阶段记录已覆盖的范围，完整能力在相关阶段全部交付后确认。

## 2. P0 核心契约

交付领域状态所有权表、对象引用与版本关系、主要命令/事件/执行 schema、错误语义、权限矩阵、Manifest/DeploymentPlan 和示例项目支持边界。明确 API 前缀、幂等作用域、协议兼容及配置迁移方式。

冻结 DBOS Python 具体 SDK 版本、SQLAlchemy/驱动与 PostgreSQL 兼容矩阵，验证 D02 引用的事务入队、持久消息、取消/恢复、队列配置和应用版本接口。定义 WorkflowBinding、稳定 Workflow/Command/Operation 身份、请求摘要、同库 schema 和数据库角色、四类队列、工作流重放规则及旧备份启动门禁。DBOS 选型已确定，具体 SDK 版本核验不等于重新建设通用调度引擎。

退出条件：每个状态有唯一写入责任，D01～D05 的交接可以落到命令和证据；关键未知项登记负责人及冻结阶段。不能只把所有字段都列为可选以规避契约决策。

## 3. P1 持久与执行底座

交付身份登录与目标接入基础、FastAPI DBOSClient、单 worker 启停、DBOS 队列/检查点、事务入队与 WorkflowBinding、业务事件/Outbox、Operation/Attempt/StepExecution、Runner 本地账本、资源预留、bare repository 和受限沙箱。提供基本状态、暂停/取消与核对 UI。

交付基于同一 PostgreSQL 事务的业务写入与 enqueue_in_transaction、稳定 ID/摘要校验、业务命令重试去重、持久通知分发和受控的工作流恢复入口。普通重启由服务管理器拉起，旧备份 recovery 模式禁止 DBOS.launch。API 扩进程不启动 DBOS 执行器。

退出条件为业务状态与入队同提交/同回滚，重复投递不会形成第二次业务意图，已完成检查点可复用，未完成外部步骤按实际状态核对。取消、恢复、接管与资源释放均依据真实进程；等待流程不饿死控制/模型/重执行队列，Git 与沙箱权限隔离有效，事务事件和同步游标可恢复。完成空载、等待、入队与 worker 重启的早期资源记录，并验证一次兼容代码升级。

## 4. P2 确定性交付

使用已知、可扩展的前后端数据库示例项目，不依赖 Agent 生成代码完成本阶段。交付 ProjectDescriptor、受限构建、输入和镜像验证、完整 Release、归档传输、DeploymentPlan、审批、Remote Agent 原地更新及基础健康回报。

退出条件为业务在独立机器运行，各环境资源独立，部署遵循获批计划及有效基线，迁移结果可核对，Hub 离线时目标重启可以恢复业务。验证 DBOS 检查点缺失与远端回执丢失、已批准计划过期、主流程取消但核对继续等场景。

在实际 4 核 4GB Hub 上测量一次完整构建/联调组合任务、数据库写入与控制响应；记录同机 Runner 或独立 Runner 的真实拓扑。超限时修改资源或支持范围，不等到 P7 才发现基本链路无法容纳。

Registry 或外部 CI 后端可以后续补齐实现，但其不变量在此阶段固定；不得通过跳过制品验证或向目标临时发送源码构建代替归档交付。

## 5. P3 Agent 代码生产

交付工作项与验收修订、单 Agent Runtime、受控代码工具、ContextPackage/ModelRequestRecord、独立验证与审查、项目合并队列和需求变更影响分析。使用同一 P2 交付链验证生成的代码。

退出条件为模型输入和工程结果可追溯，项目合并遵循分支版本条件，最终镜像与验证输入对应，模型费用按预留和结算规则管理。DBOS 重放不重新计费，真实模型请求中断保留未知 usage；步骤重试不能绕过预算或重复创建 AgentRun，长等待不占模型调用名额。

单 Agent 阶段用于验证代码生产接入，不代表多 Agent 目标完成。验证/审查可使用独立受限角色，不能用开发者自述代替事实证据。

## 6. P4 多 Agent 协作

交付成员/会话调度、直接消息、收件箱处理确认、可恢复等待、分类依赖、正式决策、契约修订和返工。至少两个开发 Agent 使用不同工作区围绕真实前后端依赖协作。

退出条件为契约确认后可并行实现、联调按真实产物解锁、等待和返工具有明确结束条件，协调会话可以从持久状态恢复，暂停、收信和预算规则按设计生效。验证回复早于等待登记、重复通知、DBOS 接收后业务处理前崩溃、暂停期间收信和运行中契约失效，不能把引擎消息送达当作工程条件已满足。

稳定前缀和版本化输入随 Runtime 实现；缓存命中率和收益在 P7 通过实际提供方数据评估，不影响正确性门槛。

## 7. P5 持续运维与恢复

交付有界指标和日志、告警规则、ObservedState/DriftRecord、Incident、固定诊断与获批 runbook、业务修复 Task 关联、备份清单及 Hub 旧备份恢复流程。

退出条件为管理通道与业务健康分别展示，重连操作重新检查有效性，控制面恢复遵循身份确认与状态核对流程。实际恢复包含业务与 DBOS schema 的一致性备份，核对所需代码版本和制品；在建立新 incarnation、逐资源确认恢复许可前不能自动出队或执行旧步骤。证明业务独立运行不依赖 DBOS 或 Conductor。

## 8. P6 Desktop 与扩展体验

完成项目、团队、需求、代码与证据、预览、审批、目标和运维视图，以及 Windows/Linux 打包、安装升级、权限变化与断线同步。补齐计划支持的 Registry、外部 CI 和观测 adapter，并提供能力矩阵。

退出条件为无开发工具链的桌面可安装使用，预览与管理权限隔离，审批对象清晰，执行状态可以查询与核对，已支持的 adapter 具有完整能力说明。

## 9. P7 容量与效果评估

完成真实 4 核 4GB Ops Hub 报告、单/多 Agent 对照、缓存对照、交付成本统计和答辩材料。完整产品验收依据 P0～P6 的交付要求及最终版本进行。

退出条件为提供可追踪的输入版本、资源峰值、通过率、耗时、费用、人工介入、失败与恢复证据。允许得出受限通过、不支持或多 Agent 未优于单 Agent 的结论。

## 10. 产品验收要求

|能力|验收要求|
|---|---|
|项目与开发|支持仓库创建和接入、独立工作区、受限工具执行、项目级集成及版本化审查|
|Agent 协作|多个开发会话围绕契约和产物协作，依赖、消息、等待、返工及上下文可追溯|
|可靠执行|DBOS 原子入队、检查点、重放、等待和升级符合契约；平台操作核对、取消和物理资源与真实执行一致|
|发布与交付|构建输入、验证和最终制品对应；审批绑定环境及版本；受管与独立部署使用同组制品|
|安全与客户端|身份和权限由服务端校验，预览隔离有效，秘密材料受控，客户端同步保持状态一致|
|持续运维|提供有界观测、漂移识别、Incident 和受控处置，支持业务独立运行、重启及备份恢复|
|容量与成本|执行遵循资源与费用预算，支持范围由真实整机测量和质量、时间、成本评估确定|

验收记录包含实现版本、运行环境、操作引用、预期与实际结果及支持范围，敏感字段只保存标识。远程交付、资源隔离和恢复能力在真实目标环境验收。

## 11. 4 核 4GB 测量方法

使用整机受限为 4 vCPU、4GB RAM 的 Linux Ops Hub，外部模型 API 和另一台交付机器。记录 OS、架构、磁盘、Swap、项目 commit、工具链和全部常驻组件，不能只限制高配宿主中的一个容器。

记录空载、DBOS 入队/等待/检查点恢复、依赖安装、前端构建、后端测试、一次浏览器检查、预览竞争及归档交付的内存/CPU/磁盘峰值与耗时。分别记录 API 与 DBOSClient 池、worker 的 DBOS/模型池、PostgreSQL 活跃连接与写入、队列等待量、检查点增长和控制队列延迟；防止多个小池合计超过数据库上限。

测量 API 延迟、数据库连接、任务排队及取消响应；阈值在执行前按支持范围固定，不在结果出来后为通过而修改。沿用 P1/P2 早期记录，最终报告比较变更后的资源趋势。DBOS 不需要独立服务的事实不能代替 SDK 和数据库增量的测量。

持续观察不少于 24 小时，混合代表性任务与空闲，检查泄漏、残留容器、资源预留、DBOS 长等待/历史增长、指标行数、日志增长和清理引用。支持结论分为通过、受限通过、不支持；超限时修订容量或支持范围后重新验证相关场景。单 worker 恢复只证明该拓扑，多 worker/Conductor 的容量和故障转移单独报告。

## 12. 多 Agent 与缓存实验口径

预先固定任务集、原始需求、独立验收集、模型版本、工具权限、运行环境、预算与人工介入规则。同一任务重复执行，记录顺序、随机因素、失败和波动，不使用一次演示推导普遍优势。

单/多 Agent 对比记录通过率、总耗时、实际费用、token、人工次数与耗时、冲突、返工、独立验证发现的问题及无效通信。失败任务成本不能排除；交付成本至少同时报告全部实验费用除以成功任务数以及各任务明细，零成功时该指标记不可计算。

可设置无直接通信、无独立审查等消融对照，研究收益来源。简单任务成本上升时如实报告，不人为增加团队以满足演示外观。

缓存对照比较每轮重拼与稳定前缀/增量追加，固定语义输入与验收，分别记录冷启动、连续请求和压缩切换。交错或随机安排实验顺序，记录调用间隔及提供方缓存条件；无法保证物理冷缓存时注明限制。

提供方能力与 usage 取自真实记录，缺失统计只能报告输入稳定性及效果未知。费用包含缓存创建/读取、输出、失败请求和压缩；主要指标为质量、每次成功交付的全部成本、时间与人工介入，命中率作为诊断信息。

## 13. 复用矩阵与核验

|领域|拟复用能力|平台承担的部分|采用前核验|
|---|---|---|---|
|Desktop|Tauri、React、TypeScript|管理 UI、权限状态、同步与预览边界|Windows/Linux 打包、IPC、WebView 隔离|
|API/数据|FastAPI、Pydantic、SQLAlchemy、PostgreSQL、Alembic|领域命令、同库事务、版本、业务事件与授权|同事务入队、数据库角色、业务/DBOS schema 迁移与连接预算|
|工作流|DBOS Python、DBOSClient、持久队列/检查点/消息/定时|业务 workflow/step、WorkflowBinding、幂等与实时执行门禁|重放、消息等待、取消、应用版本、检查点保留及控制响应|
|Agent|可用 Runtime 或 provider adapter；局部可选 LangGraph/LiteLLM|工作项协作、上下文证据、权限与预算|真实工具循环、协议状态、许可证及 usage 语义|
|源码|系统 Git；可选 Gitea/GitHub|仓库归属、受控工具、合并队列|权限、过滤器、LFS/submodule、条件更新|
|执行与构建|Docker、受限 BuildKit、现成项目工具链|输入固定、资源、记录与证据|内核/cgroup/存储兼容、峰值与权限|
|交付|Docker Compose、归档；可选 Registry/CI|计划、审批、步骤核对与资源绑定|更新/依赖行为、制品身份、架构、回执查询|
|预览与观测|Caddy 或现有代理；可选专业后端|预览授权、有界采集、Incident|TLS/DNS、Cookie、配额与断线行为|

OpenHands、SWE-agent、Aider 可作为开发循环的参考，Coolify、Dokploy 可作为部署交互的参考。此次固定 DBOS 调度底座，不自动将某一 Agent Runtime 视为已选定或已集成。Agent Runtime 不建立另一套可绕过 DBOS/Operation 的副作用重试链。组件采用前核验接口、许可证、运行依赖与资源开销，接入范围由平台领域契约限定。

DBOS 接管通用持久调度，平台保留需求/契约、审批、资源、Git 集成、Release/Deployment 和真实操作核对。不得一边引入 SDK，一边继续实施旧的通用 WorkflowJob 队列和调度租约。官方依据由 D02 维护。

## 14. 需要在实现阶段冻结的选择

|选择|当前约束|冻结阶段与证据|
|---|---|---|
|具体组件与协议版本|不得用文档版本代替协议版本|P0/P1 兼容矩阵及 schema|
|DBOS SDK 与数据库接入|核验事务入队、持久等待、取消/恢复和版本接口；同库不同 schema|P0 锁版本，P1 验证 SQLAlchemy/驱动、角色权限和迁移|
|工作流身份、重放与队列|稳定 ID/摘要；当前门禁；单 worker 与四类容量分离|P0 契约，P1 崩溃、取消、队列和兼容升级证据|
|多 worker 与 Conductor|不属于 light 必需组件；必须先有故障转移方案|扩展前固定版本/许可/部署与安全范围，再验证恢复和容量|
|受限构建模式|优先核验按需 rootless BuildKit，不暴露宿主 socket|P1/P2 内核、配额、构建记录|
|预览 DNS/TLS 安装方式|不同主机名，证书可信，IP-only 不默默降级|P1/P2 安装预检及 P6 浏览器验证|
|模型及缓存能力|按实际提供方核验，不假定兼容接口完全一致|P3 能力表与 P7 实验|
|资源、告警和保留参数|采用专题初始建议，最终值需测量|P2 基础数据、P5 配额、P7 整机报告|
|外部 adapter 支持清单|按实际核验列明可用/受限/未实现|P6 兼容性记录|

未决项不能削弱安全、版本、授权和恢复不变量；需要改变不变量时按索引中的版本规则同步评审。

## 15. 答辩与最终交付

演示跨前后端需求、团队提问与契约修订、独立工作区、集成失败和修复、最终制品验证、个人模式部署批准及另一台机器运行。再展示关闭 Desktop 后工作继续、一个业务故障、获批处置以及断开 Hub 后业务仍可访问。

外部提交竞争、手工漂移、部分更新、旧备份恢复和预览隔离提供可复现专项记录，不要求全部挤入现场演示。多人独立审批需要不同真实参与者；单人演示仅声称个人流程成立。

最终交付包含软件、源码、独立部署包、安装升级与恢复说明、API/执行契约、用户手册、阶段记录、专项验收、资源与效果实验及论文。所有结论区分已实现、自动验证、人工验收和未完成范围。

## 16. 建议代码组织

实现代码按以下目录组织。运行入口与逻辑模块分开，逻辑模块可以共享进程部署。

```text
cloudhelm/
  apps/desktop/                 # 管理客户端
  services/hub-api/             # FastAPI + DBOSClient，不启动执行运行时
  services/hub-worker/          # 单 DBOS 运行时、队列与工作流注册
  services/dev-runner/          # 受信任开发执行器
  services/remote-agent/        # 目标机器执行与本地账本
  modules/identity/             # 身份、策略与审批
  modules/projects/            # 项目、仓库及需求版本
  modules/collaboration/       # 工作项、依赖、决策与消息
  modules/agent-runtime/       # Session、Run、请求与上下文
  modules/workflow/            # DBOS workflow/step 定义、WorkflowBinding 与恢复门禁
  modules/execution/           # Operation、Attempt、步骤及资源
  modules/workspaces/          # 工作区与沙箱生命周期
  modules/integration/         # 合并队列、验证和审查
  modules/tool-gateway/        # 工具鉴权及路由
  modules/delivery/            # 构建、Release 与 Deployment
  modules/operations/          # 观测、漂移及 Incident
  modules/artifacts/           # 内容存储、索引与清理
  integrations/                # DBOSClient 封装、Git、CI、模型、MCP 和观测适配
  packages/contracts/         # API、事件和执行 schema
  database/migrations/         # 业务 schema；DBOS 系统迁移单独受控执行
  infra/ops-hub/
  infra/remote-target/
  examples/standalone-project/
  docs/design/
  docs/acceptance/
  tests/
```

跨模块依赖通过明确接口和领域命令组织，避免循环导入与任意写表。实际存放方式可以根据语言和构建系统调整，但不得借移动目录改变 D01 的状态所有权。DBOS 运行时、SDK 管理接口及系统数据库仅位于受信任 Hub，Runner 与 Remote Agent 只实现平台执行协议。

## 17. DBOS 专项验收清单

以下为实施阶段必须形成的证据，本次文档修订不表示已经执行或通过。按所属阶段覆盖必要场景，不为每次普通改动重复运行整套故障实验。

|阶段|场景|退出证据|
|---|---|---|
|P1|业务写入后入队失败、事务回滚；入队提交后 API 回执丢失|业务与 DBOS 队列同提交/回滚；重投返回原身份，无孤立业务或重复流程|
|P1|同幂等键不同请求摘要；业务命令提交后 step 检查点丢失|摘要冲突拒绝，命令结果去重，业务版本不重复推进|
|P1/P2|worker 崩溃于步骤完成前后、远端启动后或回执返回前|完成检查点复用，未完成步骤先核对 Operation，不能重复启动未知进程|
|P1/P4|回复先到、通知重复、处理确认前崩溃、暂停期间消息积累|无丢失唤醒，processed 只依据业务处理提交，暂停不触发新模型或工具|
|P1/P2|主流程取消、旧进程仍运行、原始 resume 绕过队列|独立 control 核对继续；物理资源保持占用，实时门禁拒绝冲突启动|
|P2|批准后撤权、计划过期、环境变化；缓存批准被重放|每次新副作用重验当前策略与基线，过期结果不授予权限|
|P1/P7|编排父流程等待模型/重任务，重任务饱和，数据库连接紧张|控制操作可响应，父子不争用唯一槽，组合预留与真实占用一致|
|P3|模型已计费但请求/步骤结果未知，恢复后重试|保留原请求与未知费用，新增调用重新准入，不重复结算|
|P1/P5|兼容补丁升级、缺失旧代码、SDK/schema 回退不兼容|旧流程可重放或明确 waiting_upgrade，不能无条件使用新步骤序列|
|P5|从旧备份启动，远端业务已比备份更新|DBOS 自动执行被启动门禁阻止，新控制身份及逐资源核对完成后才恢复|
|P5/P7|历史与制品清理，长等待和未知步骤仍有引用|所需检查点/输入未丢失，去重窗口与制品引用仍有效|
|扩展前|多个 DBOS worker、新旧应用版本、Conductor 失联或故障|确认谁接管、兼容版本路由与物理执行核对；单 worker 结果不能代替此验收|
