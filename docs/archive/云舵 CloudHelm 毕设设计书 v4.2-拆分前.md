> 文档版本：v4.2  
> 修订日期：2026-10-07  
> 项目定位：基于独立 Ops Hub 的多 Agent 协作开发、远程交付与持续运维平台  
> 文档性质：目标架构与实施设计，不表示相关能力已经实现或通过验收。

## 1. 项目名称与设计摘要

**项目名称：云舵 CloudHelm——多 Agent 协作开发与远程交付运维平台。**

建议论文题目：**《基于多 Agent 协作的远程软件开发与运维平台设计与实现》**。

CloudHelm 由 Desktop、独立 Ops Hub 机器和独立远程交付机器构成。Desktop 提供需求输入、过程观察、讨论、审查、审批和管理；Ops Hub 承载 Agent 团队、源码、隔离开发环境、调试、测试、构建和发布调度；远程交付机器承载正式交付的业务项目，并通过 Remote Agent 与 Ops Hub 进行部署与运维交互。

代码生产采用围绕共享工程产物的多 Agent 协作。Agent 可以直接提问、交换实现信息、提出契约变更、提交审查意见和请求协助；平台通过任务依赖、独立工作区、版本化决策、集成验证与预算约束，使交流转化为可验证的工程结果。

### 1.1 核心架构决策

|主题|v4.2 决策|
|---|---|
|Desktop|作为观察与管理客户端，不承担代码生成、依赖安装、测试和构建|
|Ops Hub|部署在独立 Linux 机器，作为代码生产、调试与协作中心|
|交付位置|业务项目交付到另一台远程机器，标准验收不使用 Ops Hub 兼任交付目标|
|执行位置|代码生成、调试、测试和构建统一在 Ops Hub 执行，Desktop 不运行开发 sidecar|
|多 Agent|支持直接通信、动态分工、任务依赖与独立审查，而非固定角色顺序调用|
|流程责任|持久化 Workflow 推进业务流程，Agent 提议与分析，执行器完成受控副作用|
|业务生命周期|Task、Release、Deployment、Incident 分离，通过版本与引用建立关联|
|运维交互|Remote Agent 提供基础设施管理，业务应用可选提供健康、指标和诊断接口|
|独立交付|业务服务不依赖 Ops Hub 在线，不强制引入 CloudHelm SDK|

系统通过 Agent 运行与收信、分类任务依赖、版本化上下文、项目级集成、分场景审批、多服务 Release、部分部署失败处理、实际状态核对，以及预览与 Git 隔离完成工程闭环。默认个人项目自动验证和构建，由用户批准具体部署；独立审批和构建前审批按策略启用。

### 1.1.1 轻量部署目标

轻量部署以 4 核 4GB Ops Hub 为容量目标，支持范围通过代表性项目实测确定，不承诺任意项目均可在该配置构建。

默认使用外部模型 API、PostgreSQL 持久队列、系统 Git、按需构建容器、镜像归档及基础运维。Gitea、独立 CI 平台、Registry、Redis/Celery、Prometheus、Loki、Alertmanager 和 Alloy 均为可选集成。逻辑上的构建、观测能力仍保留，不要求每项能力对应一个常驻服务。

### 1.1.2 模型输入缓存设计

模型输入缓存设计包括：稳定前缀、追加式会话、版本化项目基线、定向与批量消息、稳定工具包、压缩检查点，以及供应商缓存统计和成本评估。文中缓存指模型供应商的输入/前缀缓存，不是复用旧回答；新请求仍执行推理并产生输出费用。

优先优化同一 Agent 会话的连续请求，跨 Agent 共享作为经供应商验证后的额外收益。不得为提高命中率延迟关键决策、继续使用失效契约、扩大工具权限或保留不必要的敏感上下文。具体缓存机制、期限和价格以所选提供方能力及实测为准，不在本设计中承诺统一命中率。

## 2. 用户场景与产品目标

### 2.1 典型使用过程

1. 用户在 Desktop 连接 Ops Hub，创建项目或接入已有仓库。
2. 用户提交功能目标、参考资料、技术约束和验收要求。
3. 协调 Agent 组织相关 Agent 讨论方案，形成任务图、接口契约与验收标准。
4. 开发 Agent 在 Ops Hub 的独立工作区和受限沙箱中并行实现。
5. Agent 在遇到接口冲突、依赖阻塞、测试失败时直接交流并调整工作。
6. 平台集成各任务的代码，验证 Agent 和审查 Agent 对精确版本提供独立证据。
7. 用户在 Desktop 查看 diff、测试结果和运行预览并提出修改意见；构建前审批仅在项目策略要求时执行。
8. 内置构建执行器或可选外部 CI 构建不可变制品，形成 Release。
9. 用户选择已配置的远程目标及环境，审查部署计划并批准部署。
10. Ops Hub 经 Remote Agent 部署项目，回收执行和健康检查结果。
11. 业务项目持续运行；告警进入 Ops Hub，由运维 Agent 分析并提出操作或修复任务。

### 2.2 功能范围

- 项目、仓库、团队、任务和版本管理。
- 自然语言需求、多轮澄清、方案讨论与验收标准管理。
- 多 Agent 动态调度、直接通信、任务委派与阻塞处理。
- Ops Hub 上的代码编辑、依赖安装、调试、测试、预览和代码集成。
- Git commit、diff、PR 或内部审查记录、构建与制品追踪。
- 远程机器接入、部署、健康检查、日志、监控、告警与受控运维。
- 用户、设备会话、项目与环境权限、审批和审计。
- Desktop 断线重连与 Ops Hub 持续运行。

### 2.3 完整目标与交付顺序

本文设计完整平台能力，实施采用逐步闭环方式。首条验收路径固定 Linux Ops Hub、另一台 Linux 交付机器、一个可扩展示例项目和 Docker Compose 部署。多项目、多团队、多目标和不同技术栈遵循相同领域契约逐步扩展。

Kubernetes、多云资源创建、跨区域高可用、任意远程终端及自动生产处置属于后续扩展。暂缓这些扩展不改变多 Agent 协作、独立远程交付和持续运维的核心目标。

## 3. 三端架构与信任边界

### 3.1 Desktop

Desktop 使用 Tauri、React 和 TypeScript，负责项目管理、需求讨论、Agent 团队视图、任务依赖、代码与 diff 浏览、运行预览、审批、部署和监控展示。

Desktop 不运行项目工具链，不执行 Git、测试、构建或 Agent 模型循环。文件上传和产物下载通过 API 完成。终端面板显示 Ops Hub 沙箱的输出；若提供交互调试，操作仍在授权沙箱中执行。

SQLite 仅保存草稿、界面配置、缓存和同步游标；登录凭据保存在操作系统凭据存储中。所有业务权威状态位于 Ops Hub，UI 隐藏按钮不替代服务端授权。

### 3.2 Ops Hub

Ops Hub 部署在独立 Linux 机器，包含四个逻辑区域：

|区域|职责|边界|
|---|---|---|
|控制面|API、身份授权、任务、工作流、协作、审批、发布、运维调度|持有平台状态，不直接运行生成的业务代码|
|开发执行区|worktree、沙箱、依赖、测试、调试、临时预览|每任务隔离，按资源和工具能力授权|
|工程基础设施|系统 Git、按需构建执行器、制品目录；可选 Git 服务/CI/Registry|使用独立服务账户和最小权限|
|观测存储|有界指标摘要、告警、调用统计；日志默认远程按需查询|专业观测后端可选，业务事件与遥测分流|

初期可在同一台 Ops Hub 机器部署上述区域，但它们不等于共享宿主权限。后续可独立扩展开发 Runner，不改变 Desktop 和业务领域契约。

### 3.3 远程交付机器

用户配置远程机器地址、连接方式、环境和访问凭据引用。Remote Agent 以独立 machine identity 接入 Ops Hub，执行批准的部署及运维操作，并报告实际状态。

每个业务项目拥有独立 Compose project、部署目录、配置、网络和持久卷。不同项目共享一台交付机器时，必须显式处理端口、资源配额及存储冲突。

Ops Hub 停机或网络中断不应停止已部署业务服务。Remote Agent 保存有限的操作结果与待上报状态，恢复连接后补报。

### 3.4 通信关系

|通信双方|协议与用途|
|---|---|
|Desktop → Ops Hub|HTTPS REST 提交操作，SSE 接收业务事件；必要时 WebSocket 显示沙箱交互会话|
|Ops Hub worker → 开发 Runner|内部认证执行协议，提交带身份、期限、资源限制的操作|
|Remote Agent → Ops Hub|主动建立认证长连接或长轮询通道，接收命令、回传结果和心跳|
|Remote Agent → 制品后端|拉取 Registry 制品或经受限 HTTPS 下载镜像归档并校验|
|Remote Agent → Ops Hub / 可选观测后端|默认传输有界指标摘要和告警状态，专业采集按需启用|

初次接入支持受限 SSH 引导安装和用户手动安装两种方式。SSH 不作为日常部署的第二条隐式通路，避免重复执行和审计分裂。

## 4. 领域模型与状态归属

### 4.1 主要对象

|对象|含义|
|---|---|
|Project|接入的平台项目及仓库、权限、默认工具链配置|
|Task|一次有边界的开发、诊断或修复目标|
|WorkItem|可分配给 Agent 的工作项，包含依赖、输入、产物和验收条件|
|AgentMember / AgentSession / AgentRun|项目成员配置、任务级会话和一次执行尝试；记录模型、权限、预算及运行状态|
|InboxDelivery / WaitCondition|收件箱交付、处理确认及可恢复等待条件|
|ContextPackage|一次执行的不可变审计快照，包含有效需求、权限与预算，以及实际模型输入引用|
|ProjectContextRevision / ToolBundleRevision|版本化公共项目基线及稳定工具包|
|ConversationEpoch / ModelRequestRecord|会话上下文代次、实际请求顺序、增量范围和缓存统计|
|Conversation / Message|团队主讨论与定向通信，记录参与者、消息类型和工程引用|
|Decision / ContractRevision|已采纳决策和接口契约的不可变修订|
|Workspace / SandboxSession|代码基础版本、独立 worktree 及受限运行环境|
|IntegrationAttempt / MergeQueueEntry|任务内集成结果，以及项目目标分支的候选合并队列|
|VerificationReport / Review|针对精确 commit 的验证与审查证据|
|ReleaseCandidate|绑定仓库、commit、审查证据和构建请求的候选版本|
|Release / ReleaseManifest|经过构建验证的完整项目版本，绑定各服务制品、运行契约及来源证据|
|Environment / RemoteTarget|逻辑运行环境及实际承载机器|
|Deployment|将某个 Release 应用到一个环境的过程|
|ServiceInstance|具体运行的业务服务实例|
|DesiredState / ObservedState / DriftRecord|批准的期望状态、带时间的实际观测和差异记录|
|Incident|运行故障及其诊断、处置与恢复过程|
|Operation|具有副作用的执行请求及其远端实际状态|
|BuildRun / ResourceReservation|提供方无关构建记录及资源预留、回收状态|
|Approval / PolicyDecision|审批证据和规则判断记录|

### 4.2 生命周期分离

Task 可依次经历 draft、planning、running、waiting_input、integrating、verifying、reviewing、completed、failed、cancelled。waiting_input 保留等待原因和恢复点，不能仅用一个状态推断当前工作项。

WorkItem 采用 pending、ready、running、blocked、submitted、accepted、failed、cancelled；依赖满足后才进入 ready。一个 Task 可以同时拥有不同状态的 WorkItem。

ReleaseCandidate 经 created、policy_check、building、verified 或 failed；策略要求人工构建批准时进入 pending_approval，批准后再进入 building。verified 后形成 Release。Release 内容不可原地覆盖；废弃只改变可用性，不修改原制品。

Deployment 经 planned、pending_approval、queued、preflight、applying、verifying，最终进入 succeeded、failed、partially_applied 或 cancelled。needs_reconciliation 是可恢复的非终态，表示实际结果待核对，查询后再回到执行、验证或确定的终态。历史部署是否成功与服务当前健康状态分别记录；不得以 succeeded 推断服务始终健康。

Incident 经 open、investigating、action_pending、mitigating、resolved、closed。修复代码时创建新 Task，关联故障和受影响版本，不重新打开原开发 Task。

同一 Release 可以部署到多个环境，各 Deployment 独立推进。开发任务完成后，监控继续存在，不依赖 Task 保持 running。

### 4.3 状态推进责任

- Workflow 是业务步骤推进与恢复的唯一调度者。
- Agent Runtime 负责一次有预算的推理和工具循环，返回结构化结果或提议。
- Tool Gateway 验证身份、授权、参数和审批，路由并审计工具调用。
- Executor / Deployment Controller 执行或协调操作，返回实际状态及证据。
- API 接收命令，在事务中写业务状态、事件和待执行工作，不在请求事务中直接部署。
- Agent 消息不直接改变发布状态；消息中包含的建议必须转为经过校验的业务命令。

## 5. 多 Agent 协作开发机制

### 5.1 团队组成

|角色|职责|主要约束|
|---|---|---|
|协调 Agent|理解目标、组织讨论、维护任务依赖、分工、解决阻塞和汇总交付|不能凭总结替代测试与审批|
|开发 Agent|承担前端、后端、数据或其他具体模块，实现和局部验证|独立工作区，不能自行提升权限|
|验证 Agent|根据验收标准设计验证、复现问题、检查集成版本|保留独立上下文，不只执行开发者提供的验证路径|
|审查 Agent|检查需求遗漏、代码风险和契约变化|对候选版本只读，不直接修订被审代码|
|发布 Agent|解释发布风险、提出部署计划、分析发布异常|不替代 Controller 的确定性校验|
|运维 Agent|分析告警、日志、版本和指标，提出诊断、runbook 或修复任务|环境变更必须通过既定授权与审批|

设计、需求分析、脚手架等能力可由协调与开发角色承担；复杂任务可创建专门 Agent。团队大小按任务依赖、上下文独立性和资源预算决定，不强制每个任务运行所有角色。

### 5.1.1 成员、会话与执行模型

|层级|内容|生命周期|
|---|---|---|
|AgentMember|角色、专业能力、模型配置、工具能力上限|项目级，可参与多个任务|
|AgentSession|成员在指定 Task 中的消息、上下文及恢复点|任务级，跨任务上下文默认隔离|
|AgentRun|一次获调度的推理及工具循环|执行尝试级，记录输入版本与结果|

同一会话同时最多一个活跃 AgentRun，以数据库唯一约束和执行租约落实。成员可在不同任务拥有独立会话；跨会话执行仍受成员和项目并发预算限制。会话状态包括 idle、queued、running、waiting、paused、completed、failed；运行尝试单独保存结果，恢复创建新尝试而不覆写历史。

协调 Agent 提出工作项创建、依赖修改、分配和返工命令；Workflow 调度器校验版本、权限、依赖环、重复分配和资源限制后事务应用。协调 Agent 不直接操作调度器内部状态。

协调会话失败后，新尝试从任务图、有效决策、待处理消息和 ContextPackage 恢复。接管者使用新的执行代次；旧执行提交的过期修改被拒绝。等待条件和工程结果持久化，不依赖模型进程一直在线。

### 5.2 工作项契约

每个 WorkItem 至少包含：目标、负责 Agent、输入产物版本、基础 commit、可修改范围、依赖工作项、约束、验收条件、预期产物、预算和截止条件。

共享目录的修改范围属于调度约束，不是独立安全边界；执行器还必须限制实际可访问路径。涉及共享接口或数据库结构的变更需产生 ContractRevision，并标记受影响的工作项。

### 5.2.1 分类依赖与解锁条件

|依赖类型|示例|满足条件|
|---|---|---|
|contract|前端等待接口约定|指定 ContractRevision 已生效|
|artifact|调用方等待 SDK|指定产物版本已提交且符合交付要求|
|integration|联调等待前后端结果|所需候选提交已就绪|
|environment|测试等待数据库或服务|目标测试环境准备完成且未过期|

依赖记录 producer、consumer、类型、所需版本或条件、失效规则和满足证据；不以生产者整个 WorkItem 完成作为所有依赖的共同条件。调度器根据当前工作阶段所需条件解锁执行，后续联调条件不阻止前期基于契约的实现。

例如前后端确认接口 v1 后，后端实现真实接口，前端使用从 v1 生成的 mock，验证 Agent 同时准备验收用例。双方代码就绪后进入真实联调，mock 通过不代替集成通过。

契约修订生成新版本并计算消费者影响。兼容变更可依据明确规则继续，破坏性或无法确定兼容性的变更进入复核和任务调整。不能把“最新契约”静默替换为所有正在执行工作项的输入。

### 5.3 直接通信

Agent 通过平台消息工具直接向指定 Agent 或主题会话发送消息。平台持久化消息并提供送达状态；发送成功不等于对方已经处理。

|消息类型|用途|需要的工程引用|
|---|---|---|
|question / answer|澄清接口、需求和实现限制|work_item_id、contract_revision 或代码位置|
|change_proposal|提出共享契约或设计变更|当前版本、建议差异、影响范围|
|blocker / unblock|报告阻塞及解决条件|依赖项、失败证据、需要的输入|
|review_feedback|提交审查问题|精确 commit、位置、原因和验收要求|
|handoff|交付代码或报告|commit、artifact、验证范围|
|decision_notice|通知已采纳结论|decision_id 和生效版本|

每条消息具有 message_id、发送与接收身份、task_id、conversation_id、correlation_id、created_at 和结构化引用。重复投递按 message_id 去重。紧急阻塞消息可在安全执行边界唤醒 Agent，不随意中断正在产生副作用的操作。

### 5.3.1 收件箱、唤醒与等待

消息正文不可变，每个接收者具有独立 InboxDelivery，分别记录 queued、delivered、processed；按 message_id + recipient_session 去重。processed 表示一次执行已处理该消息，不表示同意提议或完成工程动作。模型读取但尚未提交处理结果即崩溃时可重新投递；由消息衍生的业务命令另以幂等键去重。

空闲会话收到需要处理的消息后进入调度队列；运行中会话在模型回合或工具安全边界读取。低优先级通知允许合并唤醒，但保留原始消息。暂停的任务只累计消息，不自动恢复。

等待回复时保存 WaitCondition，包含等待对象、correlation_id、所需结果、超时和升级规则；释放执行名额并保留工作区。回复满足条件后调度器唤醒会话。超时提交协调会话处理，不能假定无回复代表同意。

平台维护等待关系并检测循环等待。出现循环时让协调 Agent 调整分工、拆分依赖或提出待决问题；达到无进展阈值后请求用户决策。消息只能发往获授权的会话与资源范围。

### 5.4 讨论与正式决策分离

讨论消息记录探索过程；Decision 保存已采纳结论、依据、替代方案、影响范围和关联契约版本。平台先检查最新有效决策与当前基线的差异，再以显式替代通知追加给 Agent；不每轮改写公共前缀。必要时检索原讨论。重大变化或累积差异过多时切换新的上下文代次。

重要契约变更由协调 Agent 组织相关角色确认，涉及用户目标、兼容性或风险升级时请求用户决策。不能以消息数量或多数 Agent 同意代替证据。

所有 Agent 在每次执行前检查输入版本。运行期间出现契约修订时，当前产物标记需要复核；不能把旧上下文生成的代码直接当作符合最新契约。

### 5.4.1 版本化执行上下文包

每个 AgentRun 启动前生成不可变 ContextPackage，保存 package_id、session_id、工作项版本、需求与验收版本、决策和契约引用、基础 commit、相关代码索引、待处理消息、未决问题、历史失败引用、工具能力、预算快照及内容摘要。该对象是完整审计快照，不直接整体序列化到每次模型请求中；实际输入由第 5.8 节的前缀、会话历史及增量组装。预算快照只作解释，实际扣费仍检查当前额度。

|信息层|内容|规则|
|---|---|---|
|权威信息|用户约束、验收标准、正式契约、决策、代码版本|明确版本引用，不允许仅以模型摘要替代|
|过程记录|消息、工具输出、尝试和审查历史|按关联任务和代码检索，保留来源|
|恢复摘要|长会话压缩和进展概要|附原始记录引用及覆盖范围，可重新生成|

敏感信息过滤和资源权限检查先于上下文组装。长输出保留制品引用，避免所有会话加载全项目聊天。AgentRun 的交付绑定 ContextPackage；期间需求或契约改变时标记受影响结果待复核。

验证 Agent 从相同的权威需求和精确代码版本独立形成验证方法；开发 Agent 总结仅为参考。独立上下文不意味着忽略已确认契约，也不保证模型判断在统计上独立。

### 5.5 动态协作过程

1. 协调 Agent 从目标生成验收标准和初步任务依赖。
2. 相关角色讨论模块边界，固定初始契约。
3. 就绪工作项分配独立 worktree，并行启动。
4. Agent 直接提问和提交建议；阻塞时让出执行资源。
5. 协调 Agent 根据证据调整任务图，记录新增范围及原因。
6. 开发 Agent 提交代码版本与局部验证证据。
7. 集成器合并候选版本，验证与审查角色检查集成结果。
8. 失败反馈形成明确返工项，返回对应开发 Agent。
9. 满足验收条件后形成候选版本与交付报告。

### 5.6 收敛、预算与暂停

任务配置最大活跃 Agent 数、token/费用预算、执行时间、重试次数和无进展阈值。计费预留与结算必须在并发情况下保持一致。

反复讨论没有新增证据、连续修复无改善或依赖环无法解除时，协调 Agent 提交明确的待决问题。超过预算后保存上下文和产物，进入可恢复等待状态，不继续无界衍生子任务。

用户暂停意味着停止分配新工作，并在安全点暂停运行；取消不代表撤销已完成的文件、提交或远端变更。必要补偿操作单独生成并审计。

### 5.7 模型并发与重执行分离

模型调用、工作区、工具执行和预览分别配额。会话存在不意味着容器常驻。轻量模式建议初始上限为 3 个并发模型调用、2 个活跃开发 Task、1 个重任务执行槽、1 个按需集成预览；这些是待实测修订的起点，不能代替实际资源准入。

依赖安装、编译、镜像构建、浏览器测试和全栈联调进入同一重任务队列，每次最多执行一项。其他 Agent 可以继续讨论、阅读和受控编辑。预览同样计入预算，资源不足时按用户可见策略暂停可重建预览或让重任务等待。

工具声明 CPU、内存、磁盘、超时及任务类别。调度器原子预留 ResourceReservation，Runner 通过 cgroup 限制全部子进程。未知项目使用保守限额，记录峰值及失败原因，不无限提高限额重试。

不足时工作项进入 blocked 并记录 reason=waiting_resource、请求量和恢复条件。超出整机能力时明确提示更大机器或外部 Runner，不无限排队。控制面资源优先保留；取消、崩溃和超时必须回收执行租约、容器与资源预留。

### 5.8 缓存友好的输入与会话机制

#### 5.8.1 稳定前缀与增量分层

模型输入由版本化稳定内容与追加内容组成。不同提供方对 system、tools、messages 的处理顺序不同，由 adapter 映射到对应 API；目标是相邻请求拥有尽可能长的完全一致前缀。

|逻辑顺序|内容|变化策略|
|---|---|---|
|平台层|平台规则、协作协议、输出约定、稳定工具定义|协议或工具包升级时变化|
|项目层|技术约束、基础目录说明、已确认基础契约|ProjectContextRevision 切换时变化|
|角色与任务层|角色职责、任务初始目标及输入引用|角色或任务实质变化时更新|
|历史层|本会话已发送消息、模型输出和工具结果|原内容保留，按协议尾部追加|
|增量层|新消息、代码差异、工具结果、执行提醒|本轮按需追加|

时间戳、随机请求标识、剩余预算、队列位置、在线成员列表、工作区即时状态和最新消息摘要不写入稳定前缀。必要的当前状态放在尾部增量；用于审计的完整快照留在 ContextPackage。硬权限、资源和费用规则由服务端执行。

不为跨角色共享强行改变提供方要求的消息顺序，也不为扩大可缓存前缀增加无关文本。按精确内容复用；相似语义不能被假定为命中。

#### 5.8.2 追加式会话与请求重建

同一 AgentSession 的同一 ConversationEpoch 使用固定模型配置、前缀版本和工具包。后续请求复用已发送前缀及历史，追加新用户/团队消息、模型返回项和工具结果，不重新措辞、排序或汇总已有项。

不支持服务端会话的提供方由平台重传一致历史；支持会话引用的提供方按协议追加。会话引用不保证缓存命中，也不代表无需计费，必须依据实际 usage。提供方要求的 tool-call ID、输出项和其他协议状态按其格式保留，不暴露模型内部推理作为团队消息。

记录 committed history 与 pending delta。重试前固定本次输入，失败或流中断不重复追加半截模型输出；是否接纳部分结果依 provider 协议处理。已执行工具仍按 Operation 查询和去重，不能因模型请求重试再次产生副作用。

ModelRequestRecord 保存 provider、model/revision、模型配置摘要、epoch_id、prefix/template/tool bundle/project revision、实际输入摘要、历史边界、增量消息 ID 和 usage。摘要和缓存路由标识不含密钥。排障依照原始请求结构复现，不仅比较自然语言摘要。

#### 5.8.3 定向消息与批量交付

定向问题只投递相关成员；契约变化依据依赖关系通知受影响消费者；真正全局生效的决策才广播。大型工具输出默认保存制品，发送相关摘要及引用，由需要的 Agent 查询。

空闲会话的普通消息可使用有上限的短批量窗口合并唤醒；初始建议最多等待 1～2 秒，并通过延迟实测调整。运行中的普通消息在下一安全边界成批追加。保留每条原消息 ID、来源及处理状态，批量不等于丢弃细节或自动压缩事实。

关键阻塞回复、权限撤销、取消和破坏性契约变化绕过普通批量窗口；仍不得强行打断正在产生副作用的工具操作。任务暂停时累计消息，不因批量窗口到期恢复执行。容量与公平调度优先于缓存连续性。

#### 5.8.4 项目基线冻结与变更补丁

ProjectContextRevision 保存冻结的公共项目说明及其来源版本。会话开始选择一个基线；新 Decision 或 ContractRevision 通过明确变更消息追加，注明被替代的约定、作用范围、生效版本和受影响工作项。

例如基线 Revision 12 之后追加“接口 v3 被 v4 替代”和“决定 D-28 禁止新增 Redis”。这些不是两个同时有效的约定；输入组装器在执行前验证当前有效规则已送达，未送达时先交付变更或阻止相关操作。

破坏性重大变更、补丁积累过多或压缩触发时生成新基线并启动新 ConversationEpoch。接受一次缓存失效以保证正确性。首次切换后再保持稳定，不为了缓存沿用失效需求。

#### 5.8.5 稳定工具包与确定性组装

开发、验证、审查、运维使用少量版本化 ToolBundleRevision。每个会话代次固定工具排列、描述、输入输出 schema；不随在线状态或剩余预算动态改写工具列表。Gateway 每次执行实时判断资源授权和额度。

确定性组装固定字段顺序、换行、工具排序和模板版本；实际发送内容保存稳定表示。新增内容在追加前规范化，已经发送的历史保留其原表示，不通过每次重新格式化破坏前缀。非必要时间和随机字段只写请求记录，不混入模板。

权限撤销立即在 Gateway 生效，并通过高优先级增量通知模型。必须收回工具暴露、删除敏感上下文或模型能力不再兼容时，切换工具包和会话代次，接受缓存失效；不能以保持工具列表稳定为由保留实际访问能力。

#### 5.8.6 压缩作为显式检查点

触发条件综合有效上下文窗口、输入增长、无关历史比例、累计费用及提供方缓存价格，而非机械按固定轮数。到达检查点后：

1. 生成冻结摘要，保存覆盖的历史范围及原始记录引用。
2. 原样保留当前验收要求、有效约束、契约、未决问题和关键证据引用。
3. 创建新的 ConversationEpoch，绑定新的基线和摘要版本。
4. 后续继续追加，不每轮重写摘要。
5. 记录压缩前后 token、费用、缓存损失和验证结果。

缓存命中历史仍有读取成本和上下文开销，不能无限携带无关内容。摘要经一致性检查后采用，来源不可访问或关键约束丢失时不得宣称可安全恢复。

#### 5.8.7 会话内复用优先、跨 Agent 复用可选

连续请求优先保持相同模型、工具包和会话前缀。相同角色和项目基线可共享内容完全一致的公共前缀，但角色、工具或 API 处理顺序不同会限制共享长度。

跨模型、跨提供方、跨账号、跨租户不假定共享缓存。公共前缀只含接收方有权访问的信息，不能为共享命中扩大可见范围。若使用显式缓存资源，应绑定项目/权限范围及删除策略；访问撤销或内容删除时依提供方能力处理，不宣称平台能即时清除所有外部物理缓存。

调度可连续处理同会话的就绪工作，但不得饿死其他任务，也不得单为缓存保温发送无意义模型请求。

## 6. Ops Hub 开发、调试与集成

### 6.1 仓库与工作区

每个 Project 指定唯一权威 Git 远端及目标分支，可以是已有 GitHub/Gitea 或 Ops Hub 提供的 Gitea。Ops Hub 的镜像和开发副本属于执行副本，不构成第二套隐式权威；更换权威远端需要显式迁移。

分支分为项目目标分支、Task 集成分支和 WorkItem 分支。每个工作项从指定 commit 创建 worktree；Agent 的可写工作文件互相独立，不共享可写依赖目录。共享缓存采用只读挂载或受控磁盘缓存，不要求独立缓存服务。

Workspace 记录 repo、base_commit、branch、owner、sandbox、状态、配额和保留策略。清理前保留需要的 patch、commit、报告和未完成任务恢复信息。

### 6.1.1 Git 元数据与工作文件隔离

受信任 Workspace/Git 服务管理 worktree、共享 Git 元数据与仓库凭据。沙箱只挂载工作文件，不暴露共享 Git 目录、指向共享元数据的 .git 文件或远端凭据。实现应由 Runner 构造排除元数据的工作文件视图，而非直接把含 .git 的 worktree 原样挂载。

Agent 通过受控工具请求 status、diff、commit 等版本操作。Git 服务验证工作区归属和参数，禁用仓库提供的 hooks、外部 diff、textconv、过滤器等不受信任执行配置，不在控制面身份下执行仓库脚本。

提交与制品快照采集前，Runner 停止或冻结该工作区的所有写入者；采集完成后再恢复。仅限制 Agent 工具调用不足以阻止测试进程写文件。无法冻结时使用不可变文件快照再由 Git 服务提交。

确需沙箱内完整 Git 的项目采用独立 clone 模式，Git 命令在沙箱权限下执行且不注入长期远端凭据；推送仍由受信任服务完成。此模式不共享可写 Git 元数据。

### 6.2 沙箱

初期采用 Docker 开发沙箱及受信任宿主 Runner。沙箱限制 CPU、内存、进程数、磁盘、执行时间、用户权限、挂载和网络出口。Docker 提供实用隔离，但不宣称足以隔离任意恶意多租户代码；更强场景可采用 gVisor 或 microVM。

沙箱不能访问控制面数据库、远端管理凭据或宿主 Docker socket。若需要镜像构建，使用按需启动的受限构建执行器；其隔离边界不要求独立常驻服务。工具链根据项目配置选择受维护的基础镜像，依赖锁文件随项目提交。

### 6.3 调试与预览

应用预览运行在 Ops Hub 沙箱，通过认证反向代理暴露临时地址，并绑定项目、任务和沙箱。代理限制可访问端口和协议；预览具有有效期和资源清理策略。

Desktop 展示预览、输出、错误堆栈和调试会话。预览使用独立测试数据及凭据，不连接交付环境的业务数据库。远端交付机器不承担开发环境的临时调试工作。

### 6.3.1 预览浏览器隔离

预览与管理后台使用独立 origin，优先使用不同站点域；每个预览实例再分配独立 origin，避免不同项目共享浏览器存储。管理 cookie 为 host-only，管理 API 不向任意预览域开放带凭据 CORS，并保留 CSRF 防护。

预览认证由代理完成，访问票据短期有效且绑定用户、实例和权限；交换后使用预览专用会话，不向生成应用暴露管理 token。代理同时限制目标端口、实例归属和访问期限。

Desktop 通过无 Tauri 原生能力的受限 WebView 或外部浏览器展示预览。禁止预览访问主窗口 IPC、导航到带原生能力的页面或获得管理会话。预览终止后撤销路由和票据并清理相关会话。

### 6.4 集成规则

集成服务在专门工作区按依赖顺序应用候选 commit 或 patch，并保存 IntegrationAttempt。冲突可交给开发 Agent 修复，但修复结果仍需重新验证。

所有测试和审查绑定精确集成 commit；代码发生变化后，受影响证据失效或重新计算。完成条件是集成版本通过验收，不是每个开发 Agent 分别报告完成。

重要共享文件可采用调度层串行修改；不依赖“大家自行避免冲突”。验证工具输出为事实证据，Agent 对输出的解释单独记录。

### 6.5 项目级合并队列

任务内集成产生候选提交，项目级 MergeQueue 按目标分支串行推进候选。队列记录候选版本、预期基线、实际集成 commit、所需验证、状态和失败原因。

1. 从权威远端读取当前目标分支。
2. 在专门工作区合并候选，形成精确集成 commit。
3. 按变更影响执行验证与审查；核心验收无法证明可复用时重新执行。
4. 使用预期旧 SHA 的条件更新或具备等价保证的受保护合并机制更新目标分支。
5. 分支已经变化则重新集成和验证，不强制覆盖，不沿用旧 commit 的通过结论。

外部人员提交通过 webhook 和周期同步发现；事件去重后标记受影响任务基线变化。发布候选只引用通过项目级集成的精确 commit。首版不自动将所有长期任务 rebase 到最新版本，由影响判断决定更新。

PR 合并如会重写 commit，必须验证最终实际生成的 commit；平台不能把合并前的验证记录冒充最终合入版本的记录。

## 7. Workflow 与可靠执行

### 7.1 持久工作流

PostgreSQL 保存 WorkflowJob、步骤状态和恢复点。API 在同一事务写入业务修改、EventLog 和 Outbox；worker 领取任务后执行。轻量模式不部署 Redis/Celery；worker 使用 PostgreSQL 事务领取、SKIP LOCKED 和租约续期，周期扫描负责恢复，通知仅作唤醒优化。扩展模式可接入 Redis/Celery 分发，但不改变数据库权威状态。

业务状态机由领域 Workflow 管理。LangGraph 如被采用，只管理 Agent 内部推理循环和上下文恢复，不能与领域 Workflow 同时拥有 Deployment 等业务状态。

### 7.2 操作契约

Operation 包含 operation_id、业务幂等键、请求摘要、资源目标、有效期、执行代次、授权引用及实际状态。执行端持久保存去重记录和结果，至少保证在规定保留窗口内重复请求不会重复产生同一副作用。

系统允许消息重复投递，不宣称跨数据库和远端系统天然具有端到端 exactly-once。Gateway 不对所有写工具统一自动重试；Workflow 根据操作类型、幂等支持与实际状态决定恢复方式。

### 7.3 故障处理

|情况|处理|
|---|---|
|worker 执行中崩溃|租约到期后接管，查询既有 operation，再决定继续|
|请求超时但远端可能成功|标记结果未知，查询 operation 与实际服务状态|
|同一环境并发部署|按项目与环境串行化；对共享主机资源额外检查冲突|
|旧 worker 恢复|以执行代次或 fencing token 拒绝过期变更|
|审批后请求内容改变|原审批失效，重新生成计划与审批|
|CI 触发回执丢失|先按关联标识查询已有 run；提供方无法可靠识别时进入人工核对，禁止盲目再次触发|
|Desktop 断线|工作流继续；新的人类决策进入等待|
|Remote Agent 离线|保留待执行请求，过期后重新校验授权与环境状态|

## 8. Tool Gateway 与工具体系

Gateway 是统一策略入口，支持进程内工具、内部执行协议和外部 MCP Server。内部业务操作不必全部拆成独立 MCP 服务。

|工具域|能力|
|---|---|
|协作|消息、任务委派、依赖查询、决策提议、阻塞通知|
|项目与规格|需求、契约、验收标准、模板与设计产物|
|代码|限定路径读写、搜索、diff、commit、集成提交|
|执行|沙箱命令、测试、浏览器验证、构建和报告采集|
|交付|BuildRun 与可选 CI 查询、DeploymentPlan 提议、部署请求和实际状态查询|
|运维|受限日志、指标、诊断、runbook 提议与执行|

工具描述包括输入输出 schema、运行位置、超时、风险、权限、输出上限、敏感信息处理和幂等语义。工具权限根据用户授权、Agent 能力、资源属性、环境策略共同计算。

风险等级仅用于分类，不能替代资源授权。只读工具也可能读取敏感日志；安装依赖和运行测试也可能执行不可信代码。

## 9. 发布与独立远程交付

### 9.1 个人与协作审批策略

|模式|开发与构建|部署|
|---|---|---|
|个人项目|默认自动开发、验证、审查和构建|所有者可批准自己发起的版本|
|团队协作|按项目要求独立代码审查|由环境策略确定有权审批者|
|重要环境|要求完整验证和来源证据|可强制独立人类审批和禁止自批|

默认个人路径只在具体部署前请求用户批准。构建前审批为可选策略，适用于受保护仓库写入、昂贵资源等明确约束；不强制每次迭代两道人工审批。

代码审查绑定 commit。可选构建批准绑定仓库、commit、受控 ref 和验证证据摘要。deployment 审批绑定 Release、环境、机器、DeploymentPlan 摘要、配置与 secret 引用版本、迁移及执行策略。对象实质改变后原批准失效。

策略具有版本和授权修改权限，执行前重新检查当前策略，不能通过临时切换个人模式绕过环境约束。重要环境规则优先于个人项目默认值。禁止自批策略启用时，System Owner 同样受约束；个人模式允许所有者审批不是例外绕过。

Agent 可请求审批，永远不代表人类作出批准。多人职责分离验收使用不同真实参与者；单人演示只声称验证个人流程，不以多个账号冒充独立人员审查。

### 9.2 确定性发布链路

1. 集成版本固定为 ReleaseCandidate。
2. 校验构建策略；仅在要求时等待构建前批准。创建 BuildRun，资源就绪后由内置执行器或外部 CI 对精确输入验证、扫描和构建。
3. 构建输出 manifest、报告、SBOM 及不可变镜像身份；按 Registry 或归档模式记录相应摘要。
4. 程序校验源码、BuildRun、执行提供方及制品来源与摘要，创建不可变 Release。
5. 发布 Agent 基于事实提出部署说明和策略建议。
6. Controller 生成规范化 DeploymentPlan，用户批准绑定该计划的部署请求。
7. Workflow 创建 Operation，Remote Agent 获取并复核执行计划。
8. 目标端执行配置检查、制品拉取、迁移前置步骤、服务更新和健康检查。
9. 结果与实际状态回传，平台注册服务实例和观测关联。

审批通过后的固定操作不需要重新请求 LLM 决定每条命令。内置构建执行器和外部 CI 只负责验证和制品交付，不持有目标机器部署权限。

### 9.3 业务项目契约

项目至少提供源码、依赖锁文件、README、测试、Dockerfile、standalone Compose、配置样例和数据库迁移说明。

受管部署必须具有规范化 ProjectDescriptor。接入向导读取现有 Dockerfile、Compose 和服务配置后生成草案，经审查保存；不能每次发布重新猜测运行方式。描述可以存于仓库的 `cloudhelm.project.yaml`，或存于平台版本化记录，项目必须明确选择权威来源，切换来源需显式迁移。`cloudhelm.env.schema.json` 或等价平台记录描述配置类型与敏感字段，不保存实际密钥。

通用 renderer 从受控 schema 生成部署清单，不接受任意宿主挂载、特权容器或未审核的宿主命令。平台从同一 Release Manifest 导出 standalone 部署包，包含固定制品身份的 Compose、配置样例及迁移说明（Registry 固定 digest；归档使用专属标签、image ID 校验并禁止自动拉取/构建）；导出后无需平台 renderer 或 adapter 即可运行。原项目已有 standalone 配置仍可保留，发布验收检查它与本次导出制品版本是否一致。

### 9.3.1 多服务 Release Manifest

Release 表示完整项目版本，绑定不可变 manifest 与摘要，而非单个镜像地址。

|内容|要求|
|---|---|
|source|权威仓库、精确 commit、BuildRun、执行提供方和构建工具链引用|
|services|稳定 service key、支持架构；Registry 模式 index/platform digest，归档模式 archive SHA-256 与 image config digest|
|runtime|启动参数、端口、健康检查、资源和依赖|
|migrations|不可变迁移制品、顺序、适用数据库版本和兼容约束|
|verification|最终版本测试、扫描、审查及来源证据|
|configuration|配置 schema 与 ProjectDescriptor 版本，不含实际凭据|

只更新某个服务时也生成完整新 Release，其他服务沿用原不可变制品身份。数据库等第三方运行依赖同样固定镜像版本并声明数据卷要求。

DeploymentPlan 绑定 Release 和具体环境，确定目标平台制品、配置版本、secret 引用版本、依赖顺序、迁移、健康窗口和补偿方案。预检拒绝目标架构无匹配制品的发布；不允许目标机器临时从源码重新构建冒充原 Release。

standalone 与 managed 从相同 manifest 引用同一组制品。独立交付包包含所需镜像导出包，或明确可用的外部 registry 和访问安排，避免 Ops Hub 私有 registry 消失后无法重建环境。

### 9.4 回滚与数据迁移

用户单独发起的回滚作为新的 Deployment，引用历史 Release 和新的审批，保留原失败记录。原部署计划已批准的失败补偿作为原 Operation 的具名子步骤执行，记录目标版本和结果；不得将其扩展为未授权的新变更。镜像可回滚不代表数据库可回滚。

每个数据库变更声明兼容性、备份要求、验证步骤和恢复策略。不可逆迁移不得承诺自动恢复；必要时使用向前修复或维护窗口。失败后能否自动执行补偿由明确策略与事先授权决定。

### 9.5 原地更新、部分失败与健康窗口

首版明确支持允许短暂停机的原地更新，不承诺跨服务原子切换或零停机。DeploymentPlan 在批准前固定更新顺序、允许停机范围、预检、迁移、健康窗口和失败策略。

执行顺序为：验证机器能力及当前状态 → 预拉取全部制品 → 配置/端口/磁盘/备份检查 → 迁移与有序服务更新 → 就绪和关键业务探测 → 在固定观察窗口内确认结果。迁移顺序依兼容性在计划中确定，不统一假定迁移总能在更新之前执行。

|失败情形|动作|
|---|---|
|变更前预检失败|不更新服务，记录失败原因|
|部分服务更新失败|停止后续更新，采集每服务实际版本，记录 partially_applied|
|已批准且适用的补偿可执行|按原计划执行并记录每步结果，原更新失败事实保留|
|迁移不可逆或实际结果不明|停止盲目回退，进入人工处理或 needs_reconciliation|

平台分开记录期望 Release、各服务 ObservedState 和本次 Operation/Deployment 结果。部分更新可能出现新旧版本混合，UI 必须展示差异。

健康检查参数包括启动超时、探测间隔、成功阈值和观察窗口，保存到计划。窗口内未达到标准属于部署失败；部署完成后出现异常创建 Incident，不覆写历史 succeeded。后续迟到证据可追加更正记录，但保留原审计链。

### 9.6 内置构建与双制品交付后端

BuildRun 统一保存 repo/commit、工具链镜像、执行步骤、资源限额、运行结果、报告、制品及提供方 run 引用。默认复用 Workflow 和 Runner 调度按需构建容器，不另行部署完整 CI 产品。项目构建脚本不在 API 或 worker 宿主权限下运行。

|模式|流程|校验|
|---|---|---|
|Registry|推送外部 Registry，Remote Agent 按 digest 拉取|核对获准 index/platform digest、架构及容器镜像身份|
|归档|构建后导出 Docker 镜像归档，目标端下载并 load|先核对归档 SHA-256，再核对 image ID/config digest、OS 和架构|

归档 SHA-256、image config digest 和 Registry manifest digest 是不同字段，不能互换，也不能假设 docker load 后具有 RepoDigests。归档模式使用 Release/服务专属本地标签，经 inspect 绑定获准 image ID；Compose 更新禁止自动 pull/build，启动后再检查容器实际 image ID。受管操作在部署锁内防止标签被改写，外部管理员变更由漂移检查识别。

归档通过受限 HTTPS 下载，授权绑定目标与 Release。支持断点续传、临时文件、磁盘预检、限速、超时和过期清理；完整摘要校验前不加载。传输清单绑定同一归档摘要，不把部分下载当作有效产物。

standalone 和 managed 使用同组制品。归档部署包包含镜像、Compose、配置样例和加载校验步骤；Registry 部署包明确外部地址与独立访问安排。运行后不依赖 Ops Hub 在线，重新安装也不能隐式依赖已经移除的平台私有 Registry。

制品、工作区、镜像层和缓存分别设容量上限。清理前检查当前运行、回滚候选及进行中操作引用。磁盘预检包含归档、解包和镜像加载的并存峰值，归档模式减少常驻服务但不消除磁盘成本。

## 10. 远程运维与故障反馈

### 10.1 Remote Agent 职责

负责 machine identity、心跳、操作去重、受控部署、服务检查、有界日志查询和固定 runbook。模型推理在 Ops Hub 完成，Remote Agent 不自行解释自然语言并执行任意命令。

Remote Agent 运行身份仅获得受管资源所需权限；Docker 管理权限具有较高宿主影响面，不能以项目目录隔离推断完全的主机安全隔离。

### 10.2 应用交互

基础能力通过容器、进程、日志和网络探测实现。业务应用可以增加 `/health`、`/ready`、`/metrics`、优雅退出及受鉴权的诊断接口。平台不强制统一业务数据库或植入 CloudHelm SDK。

运维上下文关联 project、environment、service、deployment；跨版本故障允许关联多个 Deployment，不能强行归属一个开发 Task。

### 10.3 告警闭环

告警经过分组、去重、静默和持续时间判断后创建或更新 Incident。运维 Agent 读取有界时间窗内的日志、指标、版本变化和历史操作，给出假设、证据及不确定性。

固定只读诊断可按策略自动执行。重启、配置修改、回滚或数据操作生成 runbook proposal，经过授权和审批后由确定性执行器完成。需要改代码时创建关联修复 Task，重新走集成、验证与交付流程。

### 10.4 期望状态、实际状态与漂移

Remote Agent 定期上报目标、服务标识、实际镜像身份（Registry digest 或归档模式 image ID）、配置摘要、健康、最近 operation、执行代次和 observed_at；Ops Hub 记录 received_at 和观测来源，以处理时钟偏差及迟到消息。secret 不上传原值或易枚举的明文哈希，使用受控版本标识。

DesiredState 绑定批准的 Release 和配置版本，ObservedState 保存实际观测，DriftRecord 保存差异和处理状态。新期望版本不会令旧观测立即成为“部署失败”；根据操作进度和观察窗口判断。

默认只报告漂移。用户可选择恢复批准版本，或审查外部变更后创建新的受管版本/配置记录；不能原地修改历史 Release 以掩盖差异。无法验证来源的外部镜像标为未验证，补齐证据前不作为可信回滚版本。

Remote Agent 离线显示状态未知及最后观测时间。独立 HTTP 探测可能显示业务仍在线，两种证据分别呈现；不把管理通道失联直接解释为业务故障。

重新连接后先同步实际状态、执行代次与未完成 operation，再处理待执行请求。旧请求的目标版本或前置条件已变化时失效，禁止对新版本继续执行面向旧容器的动作。自动纠正仅开放明确事先授权、具有限流与冷却条件的固定 runbook，默认不自动覆盖人工修改。

### 10.5 基础运维内置、专业观测可选

轻量模式由 Remote Agent 采集服务状态、CPU、内存、磁盘及受限错误摘要；Ops Hub 提供短期指标聚合、告警规则和 Incident。默认不安装 Prometheus、Loki、Alertmanager、Alloy。

日志在目标端轮转，按时间、行数、字节和并发限制查询；初始单次上限建议 500 行、1MiB。实时尾随有速率、缓冲和会话期限，不能无限占用内存。需要保留的诊断证据脱敏后按制品容量管理。

初始建议每 30 秒采样，保存 1 分钟聚合 24 小时与 5 分钟聚合 7 天；设置有界指标集合、全局行数/字节配额和定期清理，不接收任意高基数标签。接近配额时降采样并标记缺口，数据过期显示未知。此参数在容量验收后修订。

基础规则支持阈值、持续窗口、去重、冷却和恢复。原始采样不逐条写 EventLog，只有状态变化与 Incident 进入业务事件。告警历史单独设置保留期。

需要长期指标、集中日志或复杂路由时，通过 adapter 接入专业后端。业务查询接口保持一致并返回数据窗口、来源及证据引用。轻量模式不宣称提供完整专业观测产品的功能。

## 11. 数据、事件与制品存储

|存储|数据|
|---|---|
|PostgreSQL|项目、任务、协作、决策、权限、工作流、审批、版本、部署、故障和审计索引|
|对象或文件制品存储|附件、patch、大型工具输出、截图、测试与扫描报告|
|本地制品目录 / 可选 Registry|默认镜像归档，或外部 Registry 制品|
|PostgreSQL 有界聚合 / 可选 Prometheus|短期指标摘要，或专业时序存储|
|目标端轮转日志 / 可选 Loki|默认远程按需查询，或集中日志检索|
|Desktop SQLite|可重建缓存、草稿和同步游标|

系统采用当前业务状态表加事务事件、Outbox 的设计，不要求依靠全部事件重建所有业务表。EventLog 记录业务变化，Audit 记录谁在何时对什么资源做了什么；原始日志和每个指标采样不逐条进入业务事件流。

关键约束包括：消息去重键、操作幂等键、工作项版本、产物内容摘要、审批请求摘要、环境执行代次以及验证报告对应 commit。大型消息正文和输出需要大小限制与制品引用。

### 11.1 新增一致性约束

- 同一 AgentSession 最多一个活跃 Run；接管依赖租约和执行代次。ConversationEpoch 是上下文代次，不等同于用于拒绝过期操作的执行代次。
- InboxDelivery 对 message_id + recipient_session 唯一；业务处理结果与处理确认事务提交。
- ContextPackage 不可变，Run、交付和报告保存其引用。
- WorkItem 依赖保存类型、目标版本、满足证据和失效状态。
- MergeQueue 按项目目标分支管理，分支更新校验预期 SHA。
- Release Manifest 不可变，DeploymentPlan 绑定其摘要和环境配置版本。
- ObservedState 按目标执行代次与观测序列处理迟到数据，不以到达顺序覆盖较新状态。
- DesiredState、DriftRecord 与历史 Deployment 分离，采集故障不改写已批准的期望。

### 11.2 缓存与上下文记录

ContextPackage 追加 epoch_id、project_context_revision、tool_bundle_revision、template_revision、prefix_digest、history_boundary、delta_message_ids 和 model_request_id。预算、权限快照为审计字段，不要求全部进入模型输入。

ConversationEpoch 保存基线、冻结摘要、起止消息、切换原因及模型配置；ProjectContextRevision/ToolBundleRevision 不可变。ModelRequestRecord 保存实际请求结构引用、provider usage 原始有界字段与规范化统计。请求正文仍需敏感信息过滤、访问控制及保留期限，不能为缓存诊断无限保存全部代码和聊天。

记录 total_input_tokens、cached_input_tokens、uncached_input_tokens、output_tokens、cache_creation_tokens（若提供）、请求延迟及实际/估算费用。提供方缺失统计时为 null/unknown，不能当作零或猜测命中。

当提供方 total_input 定义包含 cached_input 时，规范化命中率为同一统计覆盖范围内 sum(cached_input_tokens) / sum(total_input_tokens)。不满足此语义时先映射或单独展示。报告同时标明可用统计覆盖率；缺失记录不得悄悄计入零命中。

## 12. API 与同步契约

以下接口按领域资源组织，实施前统一冻结路径、请求响应 schema 与权限契约。

|资源|主要接口|
|---|---|
|项目|`/api/projects`、`/api/projects/{id}/repository`|
|任务与工作项|`/api/tasks`、`/api/tasks/{id}/work-items`、`/pause`、`/resume`、`/cancel`|
|协作|`/api/tasks/{id}/conversations`、`/api/conversations/{id}/messages`、`/api/tasks/{id}/decisions`、`/api/agent-sessions/{id}/inbox`、`/api/context-packages/{id}`|
|开发环境|`/api/workspaces`、`/api/sandboxes/{id}`、`/api/previews/{id}`|
|集成与验证|`/api/integrations`、`/api/projects/{id}/merge-queue`、`/api/verifications`、`/api/reviews`|
|交付|`/api/release-candidates`、`/api/releases`、`/api/deployments`|
|目标与运维|`/api/remote-targets`、`/api/environments`、`/api/operations`、`/api/incidents`、`/api/environments/{id}/observations`、`/api/drifts`|
|权限与审批|`/api/auth`、`/api/role-bindings`、`/api/approvals`|
|同步|`/api/snapshot`、`/api/events`|

写入命令支持请求幂等键和必要的 expected_version，返回业务标识及异步操作位置。审批端点不接受客户端自行声明的执行权限。

Desktop 使用一致性 snapshot 加事件游标恢复。服务端需要保证快照与后续事件边界无缺口；不能仅使用可能乱序提交的数据库自增序列推断提交顺序。可采用提交后有序分发与持久游标机制。客户端按事件标识去重，按聚合版本防止旧状态覆盖。

游标超过保留窗口时返回重建指令。每次订阅与补发均重新鉴权；权限撤销后关闭不再授权的数据流并清理对应缓存。

## 13. Desktop 交互设计

主要视图包括项目列表、需求与团队讨论、任务依赖、Agent 状态、代码 diff、集成报告、沙箱预览、发布审批、远程环境和 Incident。

团队视图应展示“谁负责什么、依据哪个版本、正在等待谁、交付了什么”，不只展示聊天气泡。默认显示决策、阻塞、交付和关键反馈；原始工具输出按需展开。

用户可以向团队补充约束、定向提问、要求重新规划、评论具体 diff、暂停任务或撤销未执行操作。用户新要求进入需求版本与影响分析，不应悄悄覆盖所有正在执行的 Agent 上下文。

部署界面展示版本、目标、计划、配置变化、数据库影响和已有验证证据。审批记录清楚说明批准的精确对象，不能用一个通用“同意”按钮混淆设计审查、发布候选和部署审批。

Desktop 同时展示 Agent 成员、任务会话与当前 Run；等待状态说明等待对象及条件。上下文视图可追溯执行使用的契约、需求和代码版本，合并队列展示候选与项目最新基线的关系。

部署页分别展示期望版本、每服务实际版本、观测时间和操作结果；状态未知、部分更新和配置漂移不能只用一个成功/失败图标代替。个人与协作模式显示当前生效策略，只有真正需要审批的步骤才请求用户确认。

## 14. 安全与权限

身份分为人类 User、Desktop Device/Session、Agent 执行身份、开发 Runner 和 Remote Agent machine identity。身份不可混用，Agent 权限不能超过其发起者及任务授权范围。

系统采用 system/project/environment scoped RBAC，并结合资源属性、操作风险和版本化审批策略。角色示例包括 owner、developer、reviewer、operator、deployment_approver、auditor。职责分离按第 9.1 节启用；个人项目所有者可批准自己的部署，但不能绕过更严格的环境策略。

仓库内容、附件、日志、网页和其他 Agent 转述均作为数据处理，不能据此绕过权限或获得凭据。密钥由受控凭据服务按用途注入，模型上下文、消息、日志、SQLite 和制品中禁止保存明文密钥。

首次机器配对使用短期单次挑战，长期 machine credential 支持轮换与吊销。Remote Agent 对命令验证身份、目标、期限、请求摘要与执行代次。

审计记录覆盖操作发起者、代表的人类身份、Agent lineage、策略判断、审批对象、输入摘要、结果和版本。敏感输出在进入模型和存储前脱敏，并限制保留范围。

## 15. 技术选型与复用策略

|领域|建议选型|复用方式|
|---|---|---|
|Desktop|Tauri + React + TypeScript|复用桌面壳、现有 UI 和 API 客户端，移除本地执行依赖|
|API 与领域服务|FastAPI + Pydantic|按领域组织业务 API，明确状态所有权|
|持久化|PostgreSQL + Alembic|复用模型与迁移机制，增补协作及版本约束|
|后台调度|PostgreSQL WorkflowJob + 单 worker|事务领取、租约和恢复；默认无 Redis/Celery|
|Agent 循环|现有 Runtime；LangGraph 可用于局部循环|复用模型工具调用能力，新增团队消息与任务图|
|模型接入|LiteLLM 或现有 provider adapter|能力分级、缓存 usage 映射、稳定请求与预算；未知能力不假定支持|
|工具接入|统一 Gateway + MCP adapter|内部工具保留直接调用，外部生态使用 MCP|
|源码与构建|系统 Git + 按需受限构建执行器|Gitea、外部 CI 与 Registry 均可选|
|开发隔离|Docker + 受信任 Runner|管理沙箱，不自研容器运行时|
|远程部署|Remote Agent + Docker Compose|复用 Compose，自己实现授权与操作协议|
|测试与扫描|按项目使用 pytest/vitest/Playwright、Semgrep/Trivy|工具执行产生事实，Agent 分析结果|
|观测|Remote Agent + 有界摘要与告警|专业观测栈通过 adapter 可选接入|
|代理与预览|Caddy 或现有反向代理|复用 TLS 与路由能力，增加项目访问控制|

轻量 Ops Hub 常驻模块化 API、单 worker、受信任 Runner、小连接池 PostgreSQL 和轻量反向代理。构建容器、浏览器、扫描器和预览按需启动。Remote Agent 位于交付机器；单 worker 可异步管理外部模型调用，重执行槽单独限流。逻辑模块不逐个拆成常驻服务。

OpenHands、SWE-agent、Aider 可用于研究工作区和开发循环；LangGraph 用于参考有状态推理；Coolify、Dokploy 可用于参考部署体验；MCP 用于外部工具协议。引用这些项目不代表已经完成兼容性、许可证或集成验证。

### 15.1 Provider 缓存能力适配

Provider Adapter 维护经文档和实际请求验证的能力配置，记录核验日期和适用模型：自动前缀缓存或显式缓存、usage 字段映射、最小缓存长度、期限、价格、路由提示、请求格式限制及账号边界。未知能力显示未知，不推断所有兼容接口行为一致。

支持缓存路由提示时，以稳定、不含敏感信息的项目/模板范围标识映射；该提示仅是优化，不是命中保证。显式缓存创建、读取、续期、删除与失败回退由 adapter 管理，失效后回到正常完整请求。切换提供方可能需要新会话代次，不强行复用不兼容协议历史。

费用计算区分输入、缓存读取、缓存创建、输出及其他可计费项；字段和价格随提供方实际语义解释，避免把同一 token 重复计费。缓存期限不写死为统一值，不默认付费预热或自动续期。

## 17. 部署与生命周期管理

### 17.1 标准部署拓扑

Desktop 位于用户电脑；Ops Hub 位于独立 Linux 机器；远程业务位于另一台 Linux 机器。桌面用户不需要安装 Docker、Python、Node、PostgreSQL 或 Redis。

轻量 Ops Hub 安装 TLS、API/单 worker、PostgreSQL、开发 Runner、系统 Git 和制品目录；默认不安装 Gitea、独立 CI、Registry、Redis 与完整观测栈。4GB 方案调用外部模型 API，不承诺本地模型推理。

远程目标安装 Remote Agent、Docker/Compose 和 machine identity；基础采集包含在 Remote Agent 内，专业采集器可选。业务项目发布不重复初始化整台机器。

### 17.1.1 部署配置和容量预算

|配置|目标|负载与依赖|
|---|---|---|
|light|4 核 4GB Ops Hub 待验证目标|外部模型、少量任务、重执行串行、单预览、基础运维|
|standard|按实测增加内存和磁盘|更多执行槽及可选 CI/Registry/观测后端|
|extended|控制面和开发执行器分离|独立 Runner 与外部基础设施，按项目配额调度|

4GB 仅指 Ops Hub，不包含 Desktop 和独立交付机器。light 主要验证小型 Python/Node Web 项目，不承诺大型 Java、复杂前端、长浏览器套件或完整多服务联调均可执行。项目超限时明确建议更大机器或外部 Runner。

初始目标是常驻平台合计约 1～1.5GB，另为操作系统、文件缓存和突发至少预留约 0.75GB，其余才供开发任务使用。这是预算而非已测数据；启动时检查可用内存，运行中根据系统压力与容器峰值准入。预览不能额外突破总预算。

控制面与数据库保留资源，小连接池、受控日志与单 worker 避免多进程放大内存。工具使用硬限额与超时。Swap 只缓冲短时峰值，不计入正常可承诺容量。

磁盘需求依代表性项目实测确定，安装及执行前检查工作区、镜像、归档和临时空间。容量不足可以排队、暂停预览、清理无引用缓存或扩容，不能隐式同时启动更多重任务。

### 17.2 升级、备份与卸载

分别管理 Desktop、Ops Hub、Remote Agent 和业务项目版本。执行协议有 schema_version 与兼容检查，不兼容时停止新变更并显示升级要求。

备份覆盖 PostgreSQL、仓库、制品索引与必要内容、凭据恢复机制。业务数据由对应项目单独备份。备份可用性通过恢复演练验证，不以“文件已生成”作为恢复成功依据。

卸载业务项目不得删除 Ops Hub、Remote Agent 或共享审计。是否删除业务卷需要明确选择；默认保留需要恢复的数据和发布记录。

## 19. 测试、实验与验收

### 19.1 验证原则

按变更范围执行有意义的检查，避免为了增加数量重复运行宽泛测试。协议、权限、并发、恢复和制品绑定是重点；UI 文案和低影响展示修改采用针对性检查。

### 19.2 核心验收项目

1. Desktop 在无开发环境的用户电脑上连接 Ops Hub 并管理项目。
2. 代码、依赖安装、调试、测试和预览实际运行于 Ops Hub 沙箱。
3. 至少两个开发 Agent 使用不同工作区，围绕真实依赖进行直接交流。
4. 共享接口变更进入正式契约版本，并影响相关工作项。
5. 验证与审查针对集成后的精确 commit，失败可以形成返工闭环。
6. 用户可观察职责、依赖、阻塞、决策、产物、费用和执行状态。
7. Desktop 退出后，Ops Hub 继续已授权工作；需要新决策时等待。
8. 内置或外部构建输出不可变制品，与源码和报告绑定；light 不依赖独立 CI 平台。
9. 项目部署到独立于 Ops Hub 的另一台机器。
10. Remote Agent 重复接收操作不会重复实施同一变更；超时进入查询核对。
11. 同一环境并发部署和过期 worker 不会覆盖更新的版本。
12. 服务健康、日志、指标和告警能够回到 Ops Hub。
13. 故障可以生成受控运维操作或新的修复 Task。
14. Ops Hub 断线不影响已交付业务运行；恢复后状态可补报。
15. 审批精确绑定内容、目标和身份；个人所有者可批准自身部署，独立审批策略启用时自批被拒绝，项目设置不能弱化重要环境要求。
16. 删除 CloudHelm adapter 后，项目仍可独立构建、部署和运行。
17. 备份可恢复，卸载单个业务项目不破坏平台或其他项目。

### 19.2.1 九项机制专项验收

|问题|验收场景与通过条件|
|---|---|
|1. Agent 运行模型|重复唤醒仍只有一个活跃 Run；等待释放名额；回复恢复；协调崩溃后接管不重复执行已完成操作|
|2. 分类依赖|前后端在契约确认后并行，真实联调等待产物；破坏性契约修订使受影响结果进入复核|
|3. 上下文|每次交付可追溯 ContextPackage；摘要可回溯来源；验证角色以原始验收和代码独立检查|
|4. 项目集成|两个 Task 与外部提交竞争时不覆盖分支，最终合入 SHA 有对应验证记录|
|5. 审批策略|个人流程自动构建并由所有者批准部署；团队/重要环境执行独立审批；Agent 无批准能力|
|6. 项目 Release|前后端及迁移制品固定版本；不匹配架构拒绝部署；standalone 与 managed 使用同组制品|
|7. 部分部署失败|制造中间服务更新失败，显示每服务实际版本；补偿只执行预授权范围；历史成功与当前健康分离|
|8. 持续核对|手工变更被识别为漂移但不被静默覆盖；断线显示未知；重连后过期操作被阻止|
|9. 执行隔离|预览无法读取管理会话或调用原生接口；沙箱无法访问共享 Git 元数据；快照期间后台写入被阻止|

验收结论以实际执行记录和证据为准。

### 19.2.2 4 核 4GB 专项验收

在整台限制为 4 vCPU、4GB RAM 的 Linux Ops Hub 上，使用外部模型及另一台交付机器，记录 OS、CPU 架构、磁盘、swap、项目 commit、依赖与模型并发。不能只限制高配机器中的某个容器便声称整机满足目标。

|场景|要求|
|---|---|
|常驻与空载|列出全部进程/容器占用、系统可用内存，说明与 1～1.5GB 预算的偏差|
|多 Agent|至少两个开发会话真实交流和编辑，重任务串行，记录完成和排队时间|
|构建测试|记录依赖安装、前端构建、后端测试和一次浏览器验证的峰值内存、磁盘与耗时|
|预览竞争|预览与构建争抢时按策略排队或暂停，API/数据库保持可用|
|轻量交付|不安装 Gitea、独立 CI、Registry、Redis 或专业观测栈，完成归档交付与健康回报|
|超限处理|明确拒绝或提示扩容，无无限重试，无控制面 OOM|
|保留与清理|指标降采样、日志容量和制品清理有效，当前及回滚引用不被误删|
|持续运行|不少于 24 小时代表性任务与空闲混合观察，记录增长、泄漏和残留任务|

报告区分通过、受限通过与不支持，记录 API 延迟和资源峰值。“组件能启动”不等于“开发闭环可工作”。若项目超出容量，修订实现或支持范围后重新验证，不将尚未完成实测的 light 标记为已支持。

### 19.3 多 Agent 效果评估

多 Agent 是否优于单 Agent 必须通过实验验证。选取相同仓库、需求和验收集，在尽量一致的模型能力、工具权限、总预算与运行环境下比较单 Agent 和多 Agent 两种执行方式。

记录任务通过率、人工介入次数、完成时间、token/费用、集成冲突、返工次数、独立验证发现的问题及无效通信比例。固定一组任务并重复运行，记录波动；不能以一次成功演示证明普遍优势。

可增加禁用直接通信、禁用独立审查等对照，观察收益来自并行、信息交换还是验证机制。若多 Agent 在简单任务上成本更高，调度器应允许缩小团队规模。

### 19.3.1 缓存效果专项对照

在相同任务集、模型版本、权限、验收标准和预算约束下，对比“每轮重拼上下文”与“稳定前缀、增量追加”两种方案。分别记录冷启动和连续请求，控制调用间隔、历史长度及提供方缓存条件，并重复运行说明波动。

|验证项|证据与判断|
|---|---|
|前缀稳定|无需求/模板变更时，相邻请求已有前缀与历史内容保持一致，动态预算等不污染前部|
|增量收信|批量保留原消息 ID，紧急变更及时送达，无旧契约执行|
|工具包稳定|正常会话不因瞬时状态重排工具；撤权后调用仍被即时拒绝|
|压缩检查点|只在显式代次切换重建，当前验收和约束保留；记录缓存失效成本|
|缓存统计|取自真实 provider usage；未知字段保持未知，覆盖率可见|
|总效果|比较每个验收通过任务的总费用、延迟、输出 token、人工介入、返工与质量|

汇总输入缓存命中率只作为诊断指标。主指标是每个完成且验收通过任务的总费用与完成时间，并核对质量未因信息遗漏下降。缓存读取价格、显式创建成本和压缩额外请求均计入总费用。

同会话缓存是基础验收对象；跨 Agent 命中单独报告，未观察到时不能承诺收益。测试中如提供方不返回 usage，则只能验证输入稳定性并报告缓存效果未知，不虚构命中百分比。

### 19.4 答辩演示

以包含前后端和数据库的示例项目为基础，增加一项需要跨模块协作的功能。展示团队讨论、接口提问、契约修订、并行实现、集成失败及修复、预览与审查。随后展示个人模式自动构建和用户部署批准，将版本交付到另一台机器；另以协作策略演示独立审批约束。

关闭 Desktop 展示 Ops Hub 继续运行；制造一个可控业务故障，展示日志、指标、Incident 和运维建议。完成批准的处置后，断开 Ops Hub 验证业务仍可访问。最终提供源码和 standalone 部署说明。

演示补充两个故障片段：在并行任务期间引入外部提交，展示项目合并队列重新验证；在交付机器修改服务配置，展示漂移识别和用户决策。部分更新失败、收件箱恢复和预览隔离保留可复现专项记录，不要求全部挤入一次现场演示。

## 20. 风险与应对

|风险|应对|
|---|---|
|Agent 交流很多但没有进展|工作项产物约束、无进展阈值、正式决策与预算|
|多个 Agent 共享错误假设|独立验证上下文、证据引用和对照实验|
|并行修改无法集成|独立 worktree、契约版本、集成队列与精确 commit 验证|
|Ops Hub 资源争抢|沙箱配额、并发上限、队列和后续独立 Runner|
|生成代码影响控制面|运行隔离、受限网络、独立凭据和受信任 Runner|
|部署超时导致重复操作|持久 operation、去重、实际状态查询与人工核对|
|数据库迁移无法回滚|兼容性设计、备份、维护窗口和向前修复|
|观测数据拖垮业务数据库|遥测分流、有界查询、分层保留策略|
|长期无人值守发生权限漂移|执行前重新授权、凭据轮换和审批内容绑定|
|设计与实现脱节|契约同步、阶段证据与未完成项明确记录|

### 20.1 轻量配置风险

多 Agent 会话与沙箱并发混用会导致失控，必须独立配额；归档减少服务但增加磁盘峰值；基础观测必须明确查询窗口与缺口。内置构建复用 Workflow 和 Runner，不为减少服务把仓库脚本直接放入 API 宿主执行。4GB 支持结论以第 19.2.2 节证据为准。

### 20.2 缓存优化的边界

高命中率可能来自携带过多历史，不等于低总成本；跨角色强行共享可能扩大工具暴露；频繁切换模型会丢失可复用前缀。平台以正确性、权限、任务质量和总费用优先，明确记录缓存能力差异，不承诺统一命中率，不做无意义保温调用。

## 21. 创新点与预期成果

研究重点包括：围绕版本化产物的 Agent 直接协作机制；任务依赖与动态调度；独立验证驱动的集成返工；从开发版本到远程运行版本的证据关联；具有审批、幂等和恢复语义的人机协同执行。

预期软件成果为 Windows/Linux Desktop、独立 Ops Hub、开发 Runner、Remote Agent、多 Agent 协作系统、远程部署运维闭环及可独立运行的示例项目。

预期文档包括需求分析、架构与领域模型、协作协议、执行协议、权限设计、API 与数据契约、安装运维说明、测试与实验报告、用户手册及论文。

CloudHelm 的最终目标是让用户通过 Desktop 管理持续在线的 Agent 工程团队，由团队在 Ops Hub 上协作生产和验证代码，再把可追溯版本交付到独立远程机器，并持续掌握其运行状态。
