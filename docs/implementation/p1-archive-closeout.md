# P1 原归档操作的受控收尾

本文件固定 P1-CLOSE C06/C07 的实施输入与文件分工。规则归属 [D02](../design/02-execution-recovery.md) 与 [D04 §9.4](../design/04-release-deployment.md#94-首次安装进入运行前的受控收尾)，实际结果另见进度和本轮验收记录。

## 支持范围

仅支持 `expected_state.environment_revision=0` 且起始环境为空、尚未进入 `runtime_input_check`、数据库迁移或服务更新的首次归档交付。允许 `artifact_prepare` 已开始而结果仍为 unknown；不把该结果改成 failed 或 succeeded。旧许可过期、进程消失或部分归档本身均不是收尾依据。

本轮不恢复原 Hub 备份、不升级原安装、不启动真实交付、不重启目标机器。旧库 `0008` 的恢复/升级与当前库准备另属下一步；本轮新数据库迁移只在隔离开发库验证。原私有账本和制品按原路径保留。

## 执行次序与契约

1. 运维人员主动调用独立维护命令，指定原 `operation_id`。命令从原 SQLite 读取完整计划，在与正常启动相同的 binding 文件锁内核对安装身份、原摘要、空起始环境和全部本地意图。存在后续步骤意图、原库不完整或物理边界不可核实时拒绝。
2. 在原 SQLite 事务中先写永久封闭记录，封闭全部原许可，并用持久 SQLite 触发器阻止旧版本程序为该 Operation 插入新的许可或步骤。封闭先于物理取证；取证失败仍保持封闭和绑定占用，重新调用只核对，不恢复普通推进。
3. 维护命令核实原专属 cgroup 无进程、daemon 已停用且不会自动重启、daemon PID 不存活，以及同一有界文件系统内的 Docker 容器/业务卷为空。只读取物理事实，不启动 daemon、不删除归档、不调用模型。范围限定在原安装的已知维护路径；不把调用方布尔声明当作停止证据。
4. 固定 `RemoteCloseoutReceipt`，绑定原 Operation/plan/binding/target/installation/executor/generation，以及封闭、账本和物理证据摘要。进程三维占账归零；磁盘按原批准的完整有界文件系统额度继续保留。原 `unknown` 步骤、许可和归档均不删除。SQLite 保存同一回执，重投原样返回。
5. 原安装认证通道将回执追加到 Hub。此时停止该 Operation 的 poll、许可、归档新读取、preflight 和重新登记；尚未完成人类命令前，Hub 仍保留原绑定及完整资源占账。回执上传不要求旧批准未过期，但必须校验当前安装认证、原计划及完整身份。它不授予新步骤许可。
6. 当前具有 `deployment.approve` 的已认证人类提交 `CloseDeploymentRequest(plan_digest, receipt_digest)`。Hub 在统一短事务中核对原计划、绑定、登记修订、远端回执及当前权限，追加唯一 `DeploymentCloseout`、命令结果和事件，再解除原 Operation 的冲突绑定。同键重投返回完整原命令结果；新键仍有新的命令回执，但返回同一收尾事实且不重复领域事件；更换摘要/回执拒绝。原步骤历史只保留为历史事实。
7. 环境计数保持单调，已登记的修订不回退；该修订对应“空运行环境、磁盘保留”的已核对基线。后续新计划必须使用新快照、新准确摘要、新的人类批准及当前时钟/执行代次。容量计算继续纳入 `retained_resources`，同一文件系统额度与新配置逐维取较大值，不重复记账或释放未回收磁盘。

回执丢失按原身份重发；本地封闭、Hub 接收和人类收尾为三个独立事实，不宣称跨 SQLite/PostgreSQL 原子提交。已进入迁移/服务变更、非空起始环境、账本丢失、其他物理写入或资源未知继续阻塞，完整 P4 恢复另行实施。
