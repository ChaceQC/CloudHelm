# P1.5-02 worker 恢复与控制通道

本记录绑定本轮 `0.8.1` 开发源码、独立工作流应用 `cloudhelm-hub/0.7.0`、DBOS `3.2.0` 和业务迁移 `0009_p1_5_sync`。以 [PROJECT_PROGRESS.md](../../../PROJECT_PROGRESS.md) 的实际结果为准，P1.4 受限出口、P1 整体和人工产品验收分别维护。

## 输入、环境与方法

在 WSL Ubuntu-24.04 的 `/mnt/e/Project/CloudHelm` 使用根锁定环境，每次建立独有临时 PostgreSQL 项目并使用 loopback `55437`。实际内核为 `6.18.33.2-microsoft-standard-WSL2`，Python `3.12.13`。用户、项目、声明、资源身份与故障点均由该隔离方法生成，凭据只在夹具私有目录和进程内使用。Task 的来源、验收和策略 metadata 明确标记为 `protocol_validation`，不表示真实开发或人测资产。

本机方法位于忽略目录 `.thesis-work/p1-5-02/`。`run.py` 依次调用 `worker_cases.py` 和 `control_cases.py`；`input-manifest.json` 固定代码、依赖和方法摘要，`result.json` 保存 UTC 时间、原业务身份、耗时与结果，不保存凭据。首轮 worker 小组通过，后续资源准备缺少显式工程授权导致整体 failed；补齐隔离输入的 developer/operation.request 后，仅以 `control_run.py` 补充资源和恢复小组，保存 `control-input-manifest.json` 与 `result-control.json`。未重跑已通过组；两次产品文件摘要相同，方法/输入各自绑定。方法不入库，不作为日常 CI 回归入口。

```bash
uv run --locked --offline --no-sync python .thesis-work/p1-5-02/run.py
# 本轮授权修正后，只补充资源与恢复小组；不覆盖首轮结果。
uv run --locked --offline --no-sync python .thesis-work/p1-5-02/control_run.py
```

故障 worker 使用真实 `services.hub-worker` 的构造、DBOS 注册和执行入口；临时 launcher 只在选定调用点暂停或退出。先确认原进程退出，才启动同一安装身份的后续 worker。使用 SDK 公共查询观察 workflow，不直接改写 DBOS 内部表。

## 实现与兼容

Desktop 的本机 IPC 增加连接代次和按账户读取原命令的重投入口；已验证凭据与会话身份一起保存于原生进程内。旧连接的请求、订阅和回调不得覆盖新连接，日志不因无 command_id 的 schema 拒绝而清除。SQLite 增加确定回执表，沿用已有原命令表；不迁移或重写服务端业务命令、HTTP schema 或 DBOS 持久步骤。

Task 对独立资源预留按实际 `task_id` 读取权威占账和回执。未确认执行收尾的资源阻止取消终态及完成；已确认进程释放但仍保留磁盘的情况分开处理。资源与既有 Operation 同身份时采用保守投影，不以重复 ID 抛错或用旧闭合结论覆盖新的未知事实。阻塞对象仍经当前 `resource.read` 授权过滤。

## 支持边界与后续入口

本轮只验证当前单 API/单 worker 的固定开发输入，不是压力、整机重启、独立目标交付、多 worker、高可用、跨版本恢复或原生/人工验收。

`recovery_required` 注入只证明显式门禁的拒绝路径。当前没有已交付的旧备份自动识别或受支持的自动恢复入口；不得把带有 `ready` 行的旧库直接接到普通 worker，也不得用 initialize 解除恢复门禁。真实旧备份的实例隔离、外部新鲜度、远端核对和明确交还仍属 P4，当前不开放此类自动执行。
